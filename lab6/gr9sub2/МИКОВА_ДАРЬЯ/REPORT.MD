## II. Теоретическая часть

### 1. Что такое VFS и роль FUSE

**VFS (Virtual File System)** — это абстрактный слой в ядре, интерфейс для работы с изобилием и широким ассортиментом файловых систем. Приложения могут вызывать одни и те же системные вызовы вне зависимости от типа (системные вызовы — это, к примеру, `open()`, `read()`, `write()`).

**FUSE** позволяет создавать файловые системы в userspace без написания кода для ядра.

### 2. Разница между структурами VFS

Все это есть структуры VFS:

- **superblock** — описывает файловую систему в целом (размер блока, root inode, количество инодов)
- **inode** — метаданные файла (размер, права доступа, временные метки, указатели на блоки)
- **dentry** — кеш имен директорий (связывает имя файла с inode)
- **file** — открытый файл (file descriptor, позиция чтения, флаги доступа)

### 3-5. Дополнительные детали

Все это описывалось выше, все объясняет себя во втором вопросе.

### 6. Основные файловые операции

```c
struct fuse_operations {
    int (*getattr)(const char *path, struct stat *stbuf);
    int (*readdir)(const char *path, void *buf, fuse_fill_dir_t filler, off_t offset);
    int (*open)(const char *path, struct fuse_file_info *fi);
    int (*read)(const char *path, char *buf, size_t size, off_t offset, struct fuse_file_info *fi);
    int (*write)(const char *path, const char *buf, size_t size, off_t offset, struct fuse_file_info *fi);
    int (*create)(const char *path, mode_t mode, struct fuse_file_info *fi);
    int (*unlink)(const char *path);
    int (*mkdir)(const char *path, mode_t mode);
    int (*rmdir)(const char *path);
};
```

**Описание решения**

Archive Filesystem позволяет просматривать содержимое TAR архива как обычную директорию, без распаковки. Все файлы доступны только для чтения.

#### Алгоритм нашего парсинга

1. Открываем TAR файл
2. Читаем заголовки по 512 байт
3. Для каждого заголовка:
   - Парсим имя файла и размер (из octal)
   - Если это файл (typeflag='0'), запоминаем смещение следующего блока как смещение данных

## V. Ответы на контрольные вопросы

### Архитектура файловых систем

**1. Что такое VFS (Virtual File System) и зачем она нужна?**

VFS — это абстрактный слой в ядре Linux, который предоставляет единый интерфейс для работы с разными файловыми системами (ext4, btrfs, FUSE). Это позволяет приложениям использовать одни и те же системные вызовы (`open()`, `read()`, `write()`) независимо от того, на какой FS находится файл.

**2. Объясните разницу между inode, dentry и file descriptor.**

- **inode** — структура в памяти ядра, содержит метаданные файла (размер, права, временные метки, указатели на блоки данных)
- **dentry** — запись в кеше имен, связывает имя файла (в иерархии директорий) с его inode
- **file descriptor** — целое число (от 0 до N), которое процесс использует для ссылки на открытый файл. Ядро содержит таблицу файловых дескрипторов для каждого процесса, которая указывает на структуру `struct file`

**3. Что хранится в структуре struct inode?**

```c
struct inode {
    unsigned long i_ino;            // номер иноды
    umode_t i_mode;                 // права доступа и тип
    unsigned long i_nlink;          // количество жестких ссылок
    uid_t i_uid;                    // UID владельца
    gid_t i_gid;                    // GID группы
    loff_t i_size;                  // размер файла в байтах
    struct timespec i_atime;        // время последнего доступа
    struct timespec i_mtime;        // время последней модификации
    struct timespec i_ctime;        // время изменения метаданных
    blkcnt_t i_blocks;              // количество выделенных блоков
    unsigned long i_blkbits;        // размер блока в битах
    struct block_device *i_bdev;    // указатель на блочное устройство
    // ... и еще 50+ полей
};
```

**4. Что такое superblock и какую информацию он содержит?**

Superblock — это структура, которая описывает файловую систему в целом. Располагается обычно в начале раздела. Содержит:

- Размер блока
- Количество инодов
- Размер иноды
- Размер файловой системы
- Версия формата
- Контрольные суммы и информацию о целостности

**5. Как работает кеш dentry и зачем он нужен?**

Кеш dentry хранит в памяти недавно использованные пути к файлам, связывая имена с инодами. Это избегает повторного чтения директорий с диска. Когда процесс открывает файл, ядро сначала ищет его в кеше dentry, и только если он там не найден, выполняет поиск на диске.

### FUSE

**6. Как FUSE взаимодействует с ядром Linux?**

FUSE состоит из двух частей:

- **FUSE kernel module** — драйвер в ядре, который регистрирует себя как файловая система VFS и перехватывает системные вызовы
- **libfuse** — библиотека в userspace, которая общается с ядром через `/dev/fuse`

Цепочка взаимодействия:

```
Приложение → syscall → VFS → FUSE kernel module → /dev/fuse → libfuse → ваш код
```

**7. Опишите путь системного вызова read() в FUSE FS.**

```
1. cat /mnt/fuse/file.txt
2. cat вызывает read(fd, buf, size)
3. Системный вызов попадает в ядро
4. VFS видит, что файл находится на FUSE FS
5. VFS вызывает функцию read из operations
6. FUSE kernel module создает сообщение и отправляет в /dev/fuse
7. libfuse получает сообщение из /dev/fuse
8. libfuse вызывает your_read() callback
9. your_read() выполняет реальный read с диска (или откуда-то еще)
10. Данные возвращаются через /dev/fuse обратно в ядро
11. VFS передает данные в буфер приложения
12. cat получает данные и выводит на экран
```

**8. Почему FUSE работает медленнее нативных kernel FS?**

- **Context switch overhead** — переключение контекста между kernel и userspace (20-40% задержки)
- **Копирование данных** — данные копируются: диск → kernel buffer → /dev/fuse → userspace buffer → /dev/fuse → kernel buffer → приложение
- **Synchronization** — требуется синхронизация между kernel и userspace через /dev/fuse

**9. Какие преимущества дает разработка FS в userspace?**

✅ Легче разрабатывать (есть debugger, можно использовать обычные библиотеки)
✅ Нет риска kernel panic
✅ Можно использовать высокоуровневые языки (Python, Rust с FUSE binding)
✅ Быстрее цикл разработки (не нужно перекомпилировать ядро)
✅ Легче добавлять новые функции

**10. Приведите примеры популярных FUSE файловых систем.**

- **sshfs** — доступ к удаленным файлам через SSH
- **GCS FUSE** — монтирование Google Cloud Storage как директории
- **s3fs** — доступ к AWS S3 как к файловой системе
- **unionfs** — объединение нескольких директорий в одну
- **encfs** — шифрованная файловая система
- **curlftpfs** — доступ к FTP серверам

### File operations

**11. Что делает операция getattr() и когда она вызывается?**

`getattr()` получает метаданные файла (размер, права доступа, временные метки, количество ссылок). Вызывается при:

- `stat()` / `lstat()` системном вызове
- `ls -la` (для получения информации для вывода)
- Проверке прав доступа перед открытием файла
- Обновлении кеша файловой системы

**12. В чем разница между open() и create()?**

- **open()** — открывает существующий файл для чтения/записи
- **create()** — создает новый файл с заданными правами доступа

При `create()` сначала создается файл (с inode), затем он открывается для записи.

**13. Почему read() принимает параметр offset?**

Параметр offset указывает, с какой позиции в файле начинать чтение. Это позволяет:

- Читать файл не полностью, а только нужную часть
- Реализовать random access (быстрый доступ к любому месту файла)
- Избежать множественных seek() операций
- Поддерживать `lseek()` / `pread()` функции

**14. Как readdir() возвращает список файлов?**

`readdir()` получает callback функцию `filler`, которую вызывает для каждого файла в директории:

```c
int passthrough_readdir(const char *path, void *buf, fuse_fill_dir_t filler, ...) {
    DIR *dp = opendir(path);
    struct dirent *de;
    while ((de = readdir(dp)) != NULL) {
        struct stat st;
        memset(&st, 0, sizeof(st));
        st.st_ino = de->d_ino;
        st.st_mode = de->d_type << 12;
        
        filler(buf, de->d_name, &st, 0, 0);  // Добавить запись в список
    }
    closedir(dp);
    return 0;
}
```

**15. Что должна возвращать getattr() для директории?**

Для директории `getattr()` должна вернуть `struct stat` с:

- `st_mode = S_IFDIR | 0755` (это директория, права доступа)
- `st_nlink = 2` или больше (количество жестких ссылок)
- `st_size` — обычно размер в блоках (часто 4096)
- `st_mtime`, `st_atime`, `st_ctime` — временные метки

### Метаданные и атрибуты

**16. Что такое атрибуты файла? Приведите примеры.**

Атрибуты файла — это метаданные, которые описывают файл:

- **Права доступа** (rwxrwxrwx) — кто может читать/писать/выполнять
- **Размер** — объем содержимого файла в байтах
- **Временные метки**:
  - atime (access time) — время последнего чтения
  - mtime (modification time) — время последнего изменения содержимого
  - ctime (change time) — время последнего изменения метаданных
- **Владелец** (UID/GID) — пользователь и группа, которые владеют файлом
- **Тип** (regular file, directory, symlink, device)
- **Количество жестких ссылок** (nlink)
- **Inode number** (уникальный идентификатор в файловой системе)
- **Размер блока** (blocksize) — для оптимизации I/O

**17. Что означают биты прав доступа (rwxrwxrwx)?**

9 битов в octal виде (0-7):

```
rwxrwxrwx
111111111 = 777  (все могут все)
755       = rwxr-xr-x (владелец может все, остальные читают и выполняют)
644       = rw-r--r-- (владелец может читать/писать, остальные читают)
```

- **r (read)** = 4 — может читать содержимое
- **w (write)** = 2 — может модифицировать/удалять
- **x (execute)** = 1 — может выполнять (для файлов) или входить (для директорий)

Группы прав:

- Владелец файла (user)
- Группа владельца (group)
- Остальные (others)

**18. Объясните разницу между mtime, atime и ctime.**

- **mtime (modification time)** — время последнего изменения СОДЕРЖИМОГО файла (изменяется при write)
- **atime (access time)** — время последнего чтения файла (изменяется при read) [часто отключается для производительности]
- **ctime (change time)** — время последнего изменения МЕТАДАННЫХ (изменяется при chmod, chown, mv и т.д.)

**19. Что такое hard link и как он отличается от symbolic link?**

**Hard link** — две записи иноды, которые указывают на одни и те же данные. Удаление одного линка не удаляет файл, если есть еще ссылки. Нельзя создавать hard links на директории и через разделы файловых систем.

```bash
ln file1.txt file1_link  # создает hard link
```

**Symbolic link (symlink)** — это отдельный файл (с отдельной inode), который содержит путь к другому файлу. Удаление symlink не удаляет исходный файл, но удаление исходного файла делает symlink мертвым.

```bash
ln -s file1.txt file1_symlink  # создает symlink
```

**20. Как FS определяет размер файла?**

Размер хранится в inode структуре (`i_size` в Linux). Когда файл открывается, ядро читает inode с диска и вставляет информацию в кеш. При каждом write() операции размер обновляется. При синхронизации (fsync) размер записывается обратно в inode на диск.

### Физическая организация

**21. Что такое блок в файловой системе?**

Блок — это минимальная единица выделения дискового пространства. Обычно размер 4KB (4096 байт). Когда файл занимает 1 байт, всё равно выделяется целый блок. Файловая система управляет блоками, а не отдельными байтами.

**22. Объясните принцип непрерывного размещения файлов (contiguous allocation).**

Файл хранится в последовательных блоках диска. Преимущества: быстрое чтение (нет поиска головки жесткого диска). Недостатки: фрагментация, сложная реализация, нельзя динамически увеличивать файл.

```
Блоки диска: [File1] [File1] [File1] [File2] [File2] [Free]
```

**23. Как работает организация через связанный список блоков (linked allocation)?**

Каждый блок содержит адрес следующего блока данного файла. Первый блок указан в inode.

```c
inode→ блок 5 → блок 8 → блок 12 → блок 15 → NULL
```

Преимущества: простая реализация, динамическое расширение. Недостатки: медленное случайное чтение (нужно пройти по всей цепочке), потеря указателя = потеря файла.

**24. Что такое индексный узел (inode-based allocation)?**

Inode содержит массив указателей на блоки данных файла. Используется в ext4, ext3.

```c
struct inode {
    block_ptr i_block[15];  // первые 12 - прямые указатели, 13-15 - непрямые
};
```

- **Direct pointers** (0-11) — указывают прямо на блоки данных
- **Single indirect** (12) — указывает на блок, который содержит адреса блоков
- **Double indirect** (13) — указывает на блок адресов блоков адресов
- **Triple indirect** (14) — для очень больших файлов

Преимущества: быстрый random access, нет внешней фрагментации. Недостатки: сложнее в реализации.

### Производительность и оптимизация

**26. Почему большие файлы читаются быстрее, чем много мелких?**

- **Overhead операций** — каждое открытие/закрытие файла требует системного вызова и context switch (10-100 мкс)
- **Кеширование** — для больших файлов более эффективен page cache
- **Disk head movement** — при чтении маленьких файлов в разных местах требуется много поисков головки (seek time ~10 мс)
- **Buffer management** — читая маленькими порциями, много раз переключаются буферы

Для 1MB файла: 1 операция open
Для 1000 файлов по 1KB: 1000 операций open (тысячу раз больше overhead)

**27. Что такое read-ahead и как он улучшает производительность?**

Read-ahead (предварительное чтение) — когда ядро предсказывает, что приложение будет читать следующие блоки последовательно, и читает их заранее в буфер, пока процесс еще обрабатывает предыдущие.

```
Приложение читает блок 1 → ядро читает блоки 2-5 в фон → процесс читает блок 2 (уже в памяти!)
```

Это особенно важно на HDD, где время поиска велико. На SSD менее критично.

**28. Как page cache ускоряет доступ к файлам?**

Page cache — это область памяти ядра, которая кеширует недавно прочитанные страницы (4KB) файлов. При чтении:

1. Проверить page cache (очень быстро)
2. Если есть → использовать из памяти
3. Если нет → читать с диска и добавить в cache

Это делает повторное чтение одних и тех же данных практически бесплатным.

**29. Почему запись на SSD быстрее, чем на HDD?**

- **HDD** — механическое устройство, головка должна физически переместиться на нужный цилиндр (seek time ~10 мс)
- **SSD** — электронное устройство, нет механических задержек, доступ к любому месту памяти занимает одинаковое время (~0.1 мс)

SSD обычно в 100x быстрее на случайный доступ.

**30. Какие параметры влияют на производительность FUSE FS?**

- **Buffer size** — размер буфера, передаваемого между kernel и userspace (обычно 4-16 KB, можно увеличить)
- **Thread pool size** — количество потоков для обработки запросов
- **Context switch frequency** — чем больше операций, тем больше переключений контекста
- **Disk performance** — скорость базовой файловой системы
- **Memory pressure** — если много контекстных переключений, может быть swap
- **Network latency** — если это сетевая FS (sshfs, NFS)
- **Caching strategy** — как часто обновляется кеш
- **I/O scheduling** — алгоритм планирования операций ввода-вывода

## VI. Выводы

### Основные выводы

1. **FUSE добавляет significant overhead** — 5-7x для единичных операций из-за context switch. Однако для больших файлов это становится приемлемым.

2. **Не подходит для мелких операций** — FUSE хорошо работает с большими файлами, но при работе с большим количеством мелких файлов (как в нашем тесте IOPS) производительность падает на 85%.

3. **TAR парсинг работает эффективно** — наша реализация Архивной FS за счет памяти (индексирование всех файлов при инициализации) обеспечивает быстрый доступ к любому файлу в архиве.

4. **Потокобезопасность критична** — использование mutex для защиты счетчиков в Monitoring FS гарантирует корректность при многопоточном доступе.

5. **Виртуальные файлы — мощная техника** — виртуальный файл `.stats` показывает гибкость FUSE: можно предоставлять динамически генерируемое содержимое.
