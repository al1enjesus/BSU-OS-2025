## цель работы

## задача 1 - гонка данных + устранение при помощи mutex и atomic

для демонстрации гонки данных был написан скрипт `thread_race.c`, который выполняет задачу увелечения счётчика, разбивая задачу на несколько потоков. поддерживается три режима:

- `unsync` - потоки между друг другом не разговаривают (без синхронизации)
- `mutex` - потоки синхронизированы при помощи мьютексов (только один поток может одновременно увеличивать значение счётчика, остальные ждут своей очереди)
- `atomic` - потоки не общаются между друг другом, однако используют специальную структуру данных, которая гарантирует, что изменение значения счётчика не будет прервано ещё каким-то изменением из другого потока (т.е. всё выполняется как "единое целое").
  
запустить программу можно используя команду `make run_race_<MODE>`. итак, для всех трёх подходов рассмотрим корректность результатов и скорость работы:

| метод    | кол-во потоков | итерации | ожидание (`expected`) | реальность (`actual`) | время работы (мс) | `ожидание` == `реальность`? |
| -------- | -------------- | -------- | --------------------- | --------------------- | ----------------- | --------------------------- |
| `unsync` | 4              | 1000000  | 4000000               | 830254                | 32                | **нет**                     |
| `mutex`  | 4              | 1000000  | 4000000               | 4000000               | 132               | да                          |
| `atomic` | 4              | 1000000  | 4000000               | 4000000               | 31                | да                          |

получается, что если потоки не синхронизировать, то они будут читать значение счётчика в разное время и задавать новое значение, которое *они* думают считается верным, из-за чего результат даже близко не совпал с ожидаемым значением.

mutex и atomic посчитали результат правильно, однако синхронизация через мьютексы оказалась медленнее, т.к. идея мьютексов заключается в том, что **только один поток** может менять значение счётчика, т.е. остальные потоки по сути ничего не делают и ждут своей очереди, теряя драгоценное время. в свою очередь атомики оптимизированы на уровне архитектуры процессора и потоки не теряют время ожидая других.

**вывод:** если необходимо разделить задачу между потоками, следует использовать либо мьютексы, либо атомики для синхронизации данных. если структура довольно проста (как с счётчиком), то можно использовать мьютекс, где простота написания + внедрения перевешивает потраченное время. иначе, если в приоритете работа программы, следует использовать атомики.

## задача 2 - producer-consumer (семафоры)

producer-consumer - набор проблем, описанных нидерландским учёным Эдсгер Вибе Дейкстра начиная с 1965г. в очень упрощённом понимании, в них описывается проблема синхронизации процесса "производителя" (producer) с процессом "потребителем" (consumer), когда они работают на **одном общем** массиве данных.

мною приведено решение при помощи семафоров - одного из возможных примитивов для синхронизации потоков. в основе семафора лежит обычный счётчик, у которого есть две **атомарные** (atomic) операции: увлечение и уменьшение на единицу, при этом уменьшение на единицу, когда семафор равен нулю, "блокирует" операции до увелечения значения обратно.

> почему атомики крутые описано в первом задании.

в файле `prodcons.c` приведено решение той же задачи увеличения счётчика, однако используя семафоры и фиксированную кольцевую очередь. запустить программу можно при помощи команды `make run_prodcons`:

```
somerandomprog@vbox:~/$ time make run_prodcons
./prodcons -P 2 -C 2 -N 100000 -B 64
[prodcons] P=2 C=2 N=100000 B=64 produced=100000 consumed=100000 sum=152499950000

real	0m0,462s
user	0m0,019s
sys	0m0,355s
```

таким образом, мы устранили гонку данных, и связали потоки при помощи семафоров. производительность зависит от числа потоков, и соотношения производителей-потребителей, однако это не влияет на стабильность алгоритма.

# задача 3 - где видны потоки

воспользуемся программой из задачи 1 со следующими параметрами:

`./thread_race 4 100000000000 mutex` - это вычисляется довольно долго, поэтому мы можем посмотреть какие потоки создаёт программа.

PID программы - `5176`. посмотрим на потоки...

- `ps -L -p 5176 -o pid,tid,psr,pcpu,stat,comm | head -n 20 | cat`:

```
    PID     TID PSR %CPU STAT COMMAND
   5176    5176   0  0.0 Sl+  thread_race
   5176    5177   1 37.8 Rl+  thread_race
   5176    5178   1 41.6 Rl+  thread_race
   5176    5179   0 35.8 Rl+  thread_race
   5176    5180   1 33.1 Rl+  thread_race
```

мы видим 5 потоков, где один из них - это поток самой программы, а остальные 4 - "дочерние" потоки, созданные процессом. основной поток (у которого pid == tid) спит, ожидая завершения дочерних потоков, поэтому процесс он не кушает, а вот потоки, отвечающие за вычисление счётчика, кушают где-то 1/3 ядра процессора.

- `cat /proc/5176/status | grep Threads`:

```
Threads:	5
```

всё верно. почему потоков 5, а не 4, описано выше.

- `ls -l /proc/5176/task | head -n 10 | cat`

```
итого 0
dr-xr-xr-x 7 somerandomprog somerandomprog 0 окт  5 16:32 5176
dr-xr-xr-x 7 somerandomprog somerandomprog 0 окт  5 16:32 5177
dr-xr-xr-x 7 somerandomprog somerandomprog 0 окт  5 16:32 5178
dr-xr-xr-x 7 somerandomprog somerandomprog 0 окт  5 16:32 5179
dr-xr-xr-x 7 somerandomprog somerandomprog 0 окт  5 16:32 5180
```

сверху "итого 0" обозначает суммарный размер файлов в папке, который равен нулю, т.к. в файлах ничего не хранится и вообще это виртуальная файловая система :)

## вопросы

- **чем поток отличается от процесса? где увидеть поток в /proc и ps?**

    > процесс - независимая среда выполнения с собственным кусочком памяти и ресурсами. поток - часть процесса, и если потоков несколько, то они делят один и тот же кусочек памяти (процесса). потоки можно увидеть в виртуальной директории `/proc/<PID>/task`, например через `ls -l /proc/<PID>/task`. также потоки можно посмотреть при помощи команды `ps -T -p <PID>`, которая покажет все TID, принадлежащие процессу.

- **что такое race condition и почему volatile не решает проблему корректности?**

    > **race condition** - ситуация, когда результат выполнения программы непредсказуем из-за порядка выполнения операций внутри потоков. например, для увеличения счётчика на единицу необходимо прочитать текущее значение счётчика, а только потом записать новое значение; если потоки будут читать значение общего счётчика в разное время, то результат будет неверным. 

    > `volatile` - ключевое слово в языке C, обозначающее, что переменная может быть изменена извне потоков или процесса в целом, однако это не обеспечивает атомарность операций над переменной, т.е. она всё равно уязвима к гонке данных.

- **когда выбирать mutex/condvar, когда semaphore, когда атомики?**
  
    > **атомики** - когда важна скорость, но объём данных невелик (т.е. для всяких счётчиков, флагов, т.д.)

    > **мьютекс** - когда важен *исключительный доступ* (т.е. доступ есть только у одного потока) к большому объёму данных (например, базе данных, где чтение или запись сразу от нескольких потоков может её повредить).

    > **семафор** - когда необходимо ограничить кол-во потоков, имеющих доступ к ресурсу (т.е. это по сути мьютекст, но неограниченный только до одного потока).

- **почему синхронизация замедляет выполнение и как уменьшать contention?**

    > каждый поток хочет выполнять работу. на примере мьютексов:  потоки "соревнуется" за право выполнять какую-то работу, вызывая задержки на уровне ядра, т.к. оно отвечает за очередь потоков и переключение контекстов. также, когда поток заблокирован, он не выполняет полезную работу, ожидая, пока другие потоки завершат свою работу (если объём синхронизируемых данных невелик, то это решается атомиками).

- **что такое ложное совместное использование (false sharing) и как его избежать?**
  
    > **false sharing** - проблема производительности, когда потоки, работающие на разных ядрах, обращаются к **разным** переменным, находящимся на **одной** кэш-линии. когда один поток меняет что-то на кэш-линии, она становится недействительной для другого ядра, из-за чего ему приходится заново загрузить его из оперативной памяти, что очень медленно. таким образом, потоки "мешают" друг-другу работать.

    > проблема решается выравниванием и локализацией данных (изолированием и организацией данных так, чтобы кэш-линии не пересекались), а также использованием структур, оптимизированных для многопоточности (например, те же атомиков или семафор).
