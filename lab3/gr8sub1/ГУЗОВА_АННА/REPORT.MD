## Задания

### 1) Гонка данных и устранение (mutex vs atomic)

**Описание.**  
N потоков суммарно выполняют M инкрементов общего счётчика. Нужно **сравнить** два корректных способа синхронизации:
- `pthread_mutex_t`
- атомики (`stdatomic.h`, `atomic_fetch_add_explicit(..., memory_order_relaxed)`).

**Шаги/решение.**
- Реализована программа `thread_race.c`, поддерживающая режимы: `unsync|mutex|atomic`.
- Тайминг берётся по `CLOCK_MONOTONIC`.
- Для каждого запуска печатаются: `expected`, `actual`, `time_ms`.

**Команда для сборки и запуска:**
```bash
make thread_race
./thread_race 4 1000000 mutex
```

**Результат **  

| N потоков | M на поток | Режим  | expected           | actual              | Время, ms |
|-----------|------------|--------|--------------------|---------------------|-----------|
| 1         | 1,000,000  | mutex  | 1,000,000          | 1,000,000           | 60        |
| 2         | 1,000,000  | mutex  | 2,000,000          | 2,000,000           | 260       |
| 4         | 1,000,000  | mutex  | 4,000,000          | 4,000,000           | 512       |
| 8         | 1,000,000  | mutex  | 8,000,000          | 8,000,000           | 883       |

**Команда для сборки и запуска:**
```bash
make thread_race
./thread_race 4 1000000 atomic
```

**Результат **  

| N потоков | M на поток | Режим  | expected           | actual              | Время, ms |
|-----------|------------|--------|--------------------|---------------------|-----------|
| 1         | 1,000,000  | atomic | 1,000,000          | 1,000,000           | 40        |
| 2         | 1,000,000  | atomic | 2,000,000          | 2,000,000           | 47        |
| 4         | 1,000,000  | atomic | 4,000,000          | 4,000,000           | 158       |
| 8         | 1,000,000  | atomic | 8,000,000          | 8,000,000           | 245       |

**Команда для сборки и запуска:**
```bash
make thread_race
./thread_race 4 1000000 unsync
```

**Результат **  

| N потоков | M на поток | Режим  | expected           | actual              | Время, ms |
|-----------|------------|--------|--------------------|---------------------|-----------|
| 1         | 1,000,000  | atomic | 1,000,000          | 1,000,000           | 0         |
| 2         | 1,000,000  | atomic | 2,000,000          | 2,000,000           | 2         |
| 4         | 1,000,000  | atomic | 4,000,000          | 4,000,000           | 9         |
| 8         | 1,000,000  | atomic | 8,000,000          | 8,000,000           | 12        |

**Вывод.**
- Оба способа дают корректный результат (совпадает `actual` и `expected`).
- В данных условиях **атомики быстрее мьютексов**, т.к. `fetch_add` не входит в ядро и не вызывает блокировок на уровне планировщика; однако при очень высокой конкуренции и узких критических секциях картина может меняться.
- `unsync` демонстрирует еще бюольшую скорость, однако обычно образует потери.

### 2) Producer–Consumer (bounded buffer, **семафоры**)

**Описание.**  
Нужно реализовать фиксированную кольцевую очередь. Несколько производителей генерируют элементы, несколько потребителей их извлекают. Синхронизация — **POSIX семафоры**:
- `sem_t` для свободных слотов (**empty**) и занятых слотов (**full**),
- плюс `pthread_mutex_t` на критическую секцию доступа к кольцу.

Корректное завершение: после окончания производителей добавляем **`C` «ядовитых пилюль» (sentinel)** в очередь, чтобы каждый потребитель гарантированно вышел без busy‑wait.

**Шаги/решение.**
- Реализация в `prodcons.c`.
- Опции через `getopt`: `-P` (producers), `-C` (consumers), `-N` (items_total), `-B` (buffer).
- Значения элементов кодируются как положительные ints (заведомо не равные `INT_MIN`), а `INT_MIN` используется как **sentinel** для остановки потребителей.
- Корректность: сверяем `produced_total == N` и `consumed_total == N`; также агрегируем сумму значений.

**Команда для сборки и запуска:**
```bash
make prodcons
./prodcons -P 2 -C 2 -N 100000 -B 64
```

**Результат (пример):**
```
[prodcons] P=2 C=2 N=100000 B=64 produced=100000 consumed=100000 sum=152499950000
```

**Вывод.**
- Семафорная схема `empty/full` + мьютекс на структуру очереди даёт корректность без busy‑wait.
- «Пилюли» упрощают корректное завершение, не заставляя потребителей висеть на `sem_wait(full)` после исчерпания данных.
- По производительности семафоры сопоставимы с `mutex+condvar`; точные цифры зависят от размера буфера, числа потоков и поведения планировщика.

**Использование ИИ.**
Помощь при написании prodcons.c. Объяснение результатов

### 3) Где видны потоки

**Описание.**  
Показать потоки запущенной программы в системе и прокомментировать.

**Шаги/решение.**
1. Запускаем, например, `./thread_race 8 1000000 mutex &` и берём его `PID=$!`.
2. Смотрим LWP/TID через `ps` и `/proc`:

```bash
./thread_race 8 50000000 mutex & pid=$! && sleep 0.1 && ps -L -p "$pid" -o pid,tid,psr,pcpu,stat,comm && echo "Threads:" && cat /proc/"$pid"/status | grep Threads
```

**Результат:**
```
[1] 4619
    PID     TID PSR %CPU STAT COMMAND
   4619    4619   0  0.0 Sl   thread_race
   4619    4621   0 42.8 Rl   thread_race
   4619    4622   0 25.0 Sl   thread_race
   4619    4623   0 28.5 Rl   thread_race
   4619    4624   1 25.0 Sl   thread_race
   4619    4625   0 42.8 Sl   thread_race
   4619    4626   0 42.8 Rl   thread_race
   4619    4627   0 28.5 Sl   thread_race
   4619    4628   0 21.4 Sl   thread_race
Threads:
Threads: 9
```

**Вывод.**
- В `ps -L` видны **TID** (идентификаторы потоков).
- В `/proc/<PID>/status` поле `Threads` показывает их количество.

## Ответы на вопросы

1) **Чем поток отличается от процесса? Где увидеть поток в `/proc` и `ps`?**  
Процессы имеют собственное адресное пространство; потоки одного процесса разделяют адресное пространство и большинство ресурсов, но имеют собственные регистры и **TID**. Видно через `ps -L` (колонка TID/LWP), а также в `/proc/<PID>/task/<TID>/` и поле `Threads` в `/proc/<PID>/status`.

2) **Что такое race condition и почему `volatile` не решает проблему корректности?**  
Гонка данных — зависит от недетерминированного межплетения операций. `volatile` лишь запрещает некоторые оптимизации компилятора; он **не** делает операции атомарными и **не** упорядочивает доступы между потоками.

3) **Когда выбирать `mutex/condvar`, когда `semaphore`, когда атомики?**  
- `mutex/condvar` — защищённые критические секции, ожидание условий (очереди, пулы).  
- `semaphore` — счётчики ресурсов/слотов (bounded buffer, лимит соединений).  
- атомики — простые счётчики/флаги, lock‑free структуры, где нужна высокая производительность и достаточно атомарных примитивов.

4) **Почему синхронизация замедляет выполнение и как уменьшать contention?**  
Есть накладные расходы на вход/выход из критических секций и ожидание. Снижаем contention: уменьшать время в критической секции, увеличивать буферы, шардировать данные, использовать lock‑free/атомики, выравнивать структуры (борьба с false sharing).

5) **Что такое ложное совместное использование (false sharing) и как его избежать?**  
Разные потоки пишут в разные переменные, но попадающие в один cache‑line ⇒ лишняя инвалидизация кэша. Борьба: выравнивать и «распадить» поля (alignas(64)), хранить счётчики по одному на линию, разделять горячие поля.
