# Отчёт по лабораторной работе

## Задание 1: Демонстрация гонки данных и методов её устранения

### Цель
Целью работы является демонстрация проблемы гонки данных при параллельном доступе к общей переменной и исследование способов её устранения. Реализована многопоточная программа, в которой N потоков суммарно выполняют M инкрементов общего счётчика. Предусмотрены три режима работы:
- **Без синхронизации (unsync)** — для демонстрации некорректного результата.
- **С использованием мьютекса (mutex)** — для корректного результата с блокировкой.
- **С использованием атомарных операций (atomic)** — для корректного результата без блокировок.

### Описание реализации
Программа принимает три аргумента: количество потоков (N), общее число инкрементов (M) и режим синхронизации. Каждый поток выполняет M/N инкрементов. Время выполнения измеряется с помощью `clock_gettime(CLOCK_MONOTONIC)`.

- **Режим unsync**: Используется обычный `counter++`, что приводит к гонке данных.
- **Режим mutex**: Используются `pthread_mutex_lock` и `pthread_mutex_unlock` для защиты доступа к счётчику.
- **Режим atomic**: Используется `atomic_fetch_add` из `stdatomic.h`.

## Задание 2: Модель «производитель–потребитель»

### Цель работы
Реализовать многопоточную модель взаимодействия «производитель–потребитель» на языке C с использованием POSIX Threads. Основная задача — обеспечить безопасное помещение данных в общий буфер несколькими потоками-производителями и их извлечение потоками-потребителями, гарантируя отсутствие гонок данных и корректное завершение работы всех потоков.

### Реализация
В качестве общей структуры данных используется кольцевой буфер `ring_buffer_t`, содержащий:
- Массив элементов.
- Индексы головы и хвоста.
- Счётчик текущего количества элементов.
- Мьютекс и две условные переменные.

**Производители** используют функцию `rb_push`, которая помещает элемент в буфер и при необходимости ждёт освобождения места. **Потребители** используют функцию `rb_pop`, которая извлекает элемент и при необходимости ждёт появления данных. Когда последний производитель завершает работу, он вызывает `rb_producer_done`, уменьшая счётчик активных производителей и пробуждая всех ожидающих потребителей.

Каждый поток-производитель получает количество элементов для генерации и кладёт их в буфер. Каждый поток-потребитель извлекает данные до тех пор, пока буфер не опустеет и все производители не завершат работу. В конце программа подсчитывает общее количество произведённых и потреблённых элементов, а также контрольную сумму.

### Запуск программы
Программа принимает параметры командной строки:
- `-P` — количество производителей.
- `-C` — количество потребителей.
- `-N` — общее количество элементов.
- `-B` — размер буфера.

**Пример запуска**:
```bash
gcc -pthread -o prodcons prodcons.c
./prodcons -P 2 -C 2 -N 100000 -B 64
```

Также доступен скрипт `benchmark_prodcons.sh`, который выполняет серию тестов с разными параметрами и сохраняет результаты в файл `prodcons_result.txt`.

### Результаты
Пример вывода:
```bash
./prodcons -P 2 -C 2 -N 100000 -B 64
Result: P=2 C=2 N=100000 B=64 produced=100000 consumed=100000 sum=5000050000
```
Количество произведённых элементов совпадает с количеством потреблённых, а контрольная сумма подтверждает целостность данных. Аналогичные результаты наблюдаются при запуске с другими параметрами через скрипт.

### Выводы
Программа корректно реализует модель «производитель–потребитель» с использованием POSIX Threads. Синхронизация через мьютексы и условные переменные обеспечивает безопасный доступ к буферу и предотвращает гонки данных. Проверка статистики подтверждает правильность работы: количество произведённых элементов совпадает с количеством потреблённых. Решение масштабируется по числу потоков и размеру буфера.

## Ответы на вопросы

1. **Чем поток отличается от процесса? Где увидеть поток в /proc и ps?**
   - **Поток** — единица выполнения внутри процесса, разделяющая память и ресурсы с другими потоками.
   - **Процесс** — контейнер для потоков с собственным адресным пространством и ресурсами.
   - В `/proc/[PID]/task/` каждая подпапка соответствует потоку (TID).
   - В `ps -L` ключ `-L` отображает потоки процесса.

2. **Что такое race condition и почему volatile не решает проблему корректности?**
   - **Race condition** — ошибка при одновременном доступе к общим данным без должной синхронизации.
   - `volatile` лишь запрещает кэширование переменной, но не обеспечивает атомарность или порядок операций.
   - Для корректности нужны примитивы синхронизации: мьютексы, атомарные операции, барьеры памяти.

3. **Когда выбирать mutex/condvar, semaphore, атомики?**
   - **Mutex** — для защиты критических секций с эксклюзивным доступом.
   - **Condvar** — для ожидания событий (например, "пока очередь не пуста").
   - **Semaphore** — для подсчёта ресурсов, допускает несколько потоков одновременно.
   - **Atomic** — для простых операций без блокировок (например, счётчик).

4. **Почему синхронизация замедляет выполнение и как уменьшать contention?**
   - Синхронизация требует блокировок, что вызывает ожидание и переключение контекста.
   - **Contention** — конкуренция потоков за один ресурс.
   - Уменьшение: использовать атомарные операции, минимизировать область блокировки, применять локальные данные, использовать lock-free структуры.

5. **Что такое ложное совместное использование (false sharing) и как его избежать?**
   - **False sharing** — когда потоки используют разные переменные в одном cache line, вызывая лишние инвалидации кэша.
   - Избежание: выравнивание данных (`alignas(64)`), размещение переменных в разных cache line, использование padding.
