## Ответы на вопросы
###1. Чем поток отличается от процесса? Где увидеть поток в /proc и ps?
Отличия потока от процесса:

Потоки разделяют адресное пространство, файловые дескрипторы и другие ресурсы процесса. Процессы изолированы друг от друга. Создание потока быстрее создания процесса. Потоки имеют общие глобальные переменные, процессы - нет.

Где увидеть потоки:

В ps -L -p <PID>: колонка TID показывает ID потока, разные TID с одинаковым PID
В /proc/<PID>/task: отдельные папки для каждого потока
В /proc/<PID>/status | grep Threads: общее количество потоков

###2. Что такое race condition и почему volatile не решает проблему корректности?
**Race condition** (состояние гонки) возникает, когда несколько потоков одновременно обращаются к общим данным, и хотя бы один из них выполняет запись. Результат выполнения становится непредсказуемым и зависит от порядка выполнения потоков.

Почему **volatile** не решает проблему:

volatile гарантирует только чтение из основной памяти, а не из кэша процессора
volatile не обеспечивает атомарность операций (например, инкремент состоит из чтения-изменения-записи)
volatile не предотвращает переупорядочивание операций компилятором и процессором

###3. Когда выбирать mutex/condvar, когда semaphore, когда атомики?
**Mutex/Condvar**:

Сложные условия ожидания (например, ожидание изменения состояния). Несколько условий синхронизации. Producer-Consumer с сложной логикой ожидания.

**Semaphore**:

Управление доступом к ресурсам с ограниченной ёмкостью. Producer-Consumer с фиксированным буфером. Ограничение количества одновременных операций.

**Atomic операции**:

Простые операции над отдельными переменными (инкремент, декремент, CAS). Высокопроизводительные сценарии с минимальной contention. Реализация lock-free алгоритмов.

###4. Почему синхронизация замедляет выполнение и как уменьшать contention?
Причины замедления:

Блокировки вызывают переключения контекста
Потоки ожидают освобождения ресурсов
Contention (конкуренция) при высокой нагрузке
False sharing (ложное разделение) кэш-линий

Способы уменьшения contention:

Использовать lock-free алгоритмы где возможно
Уменьшать время удержания блокировок
Использовать read-write locks для read-heavy workload
Разделять данные между потоками (thread-local storage)
Правильно выравнивать данные для избежания false sharing

###5. Что такое ложное совместное использование (false sharing) и как его избежать?
False sharing возникает, когда разные процессоры модифицируют разные переменные, расположенные в одной кэш-линии. При изменении одной переменной вся кэш-линия помечается как невалидная, вызывая ненужные обновления кэша.

Как избежать:

Выравнивание данных до размера кэш-линии (обычно 64 байта)
Использование alignas(CACHE_LINE_SIZE) в C++
Размещение часто изменяемых данных отдельно друг от друга
Использование padding между переменными, доступными разным потокам
