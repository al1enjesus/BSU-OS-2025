## B) Producer-Consumer (bounded buffer, семафоры)

### Реализация
Использованы POSIX семафоры для синхронизации доступа к ограниченному буферу:

- `sem_t empty` - счётчик свободных мест в буфере (инициализируется размером буфера)
- `sem_t full` - счётчик занятых мест в буфере (инициализируется 0)  
- `pthread_mutex_t mutex` - защита критической секции при операциях с буфером

### Алгоритм работы

#### Производитель (Producer):
```c
sem_wait(&empty);        // Ждём свободное место
pthread_mutex_lock(&mutex);

// Добавляем элемент в буфер
buffer[in] = item;
in = (in + 1) % size;

pthread_mutex_unlock(&mutex);
sem_post(&full);         // Увеличиваем счётчик занятых мест
```
### Потребитель (Consumer):
```c
sem_wait(&full);         // Ждём доступные элементы
pthread_mutex_lock(&mutex);

// Извлекаем элемент из буфера
item = buffer[out];
out = (out + 1) % size;

pthread_mutex_unlock(&mutex);
sem_post(&empty);        // Увеличиваем счётчик свободных мест
```

## Ответы на вопросы
1. Чем поток отличается от процесса? Где увидеть поток в /proc и ps?
Различия:
- Процесс - отдельная программа со своей памятью, файлами, сетью
- Поток - часть процесса, делит с ним память, но имеет свой стек и регистры
Где увидеть:
```bash
# Все потоки процесса
ps -L -p <PID> -o pid,tid,psr,pcpu,stat,comm

# В /proc - каждый поток в отдельной папке
ls /proc/<PID>/task/
cat /proc/<PID>/status | grep Threads
```
2. Что такое race condition и почему volatile не решает проблему?
- Race Condition (Гонка данных) - когда несколько потоков одновременно читают/пишут в одну переменную и результат зависит от порядка выполнения.
- Почему volatile не помогает:
      1.volatile только гарантирует чтение из памяти (а не из кэша процессора)
      2. Не делает операции атомарными
      3. Не предотвращает interleaving (перемешивание операций)
3. Когда выбирать mutex/condvar, когда semaphore, когда атомики?
    - Атомики - для простых операций над одним значением.
    - Мьютекс + Condvar - для сложной синхронизации с условиями.
    - Семафоры - для управления доступом к ресурсам:
    - Почему синхронизация замедляет выполнение и как уменьшать contention?
  Почему медленно:
      - Блокировки - потоки ждут друг друга
      - Переключения контекста - ОС переключает потоки
      - Инвалидация кэшей - разные ядра обновляют кэши
  Как уменьшить:
      - Блокируй на МИНИМАЛЬНОЕ время
      - Используй разные замки для разных данных
      - Копируй данные и работай локально
      - Дели работу между потоками без пересечений
5. Что такое ложное совместное использование (false sharing) и как его избежать?
  - False Sharing - когда несвязанные данные лежат в одной кэш-линии, и изменение одного процессора заставляет другие обновлять кэш.
  - Способы избежания:
    - Выравнивание данных (alignas(64))
    - Разделение часто изменяемых данных
    - Локальные копии в каждом потоке
