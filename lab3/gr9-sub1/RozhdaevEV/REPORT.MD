## Ответы на вопросы

### 1. Чем поток отличается от процесса? Где увидеть поток в `/proc` и `ps`?

**Поток** - это легковесная единица выполнения внутри процесса, разделяющая с ним память, файловые дескрипторы и другие ресурсы. **Процесс** - это изолированное окружение выполнения с собственным адресным пространством.

Потоки видны в системе через:
- `ps -L -p <PID>` - показывает все потоки процесса с их TID (как в нашей демонстрации: 6 потоков)
- `/proc/<PID>/task/` - содержит поддиректории для каждого потока (6 директорий)
- `/proc/<PID>/status | grep Threads` - показывает общее количество потоков ("Threads: 6")
- Каждый поток имеет свой собственный TID (Thread ID)

### 2. Что такое race condition и почему `volatile` не решает проблему корректности?

**Race condition** возникает, когда несколько потоков одновременно обращаются к общим данным без синхронизации, и результат выполнения зависит от порядка доступа. В наших тестах это привело к потере 212,568 операций из 1,200,000.

`volatile` гарантирует только чтение из основной памяти, но не обеспечивает:
- **Атомарность** составных операций (чтение-модификация-запись)
- **Порядок выполнения** операций между потоками
- **Взаимное исключение** доступа к критическим секциям

### 3. Когда выбирать `mutex/condvar`, когда `semaphore`, когда атомики?

- **Atomic операции** - для простых атомарных операций (инкремент, CAS, загрузка/сохранение). В наших тестах atomic показал лучшую производительность для счетчика.
- **Mutex/Condvar** - для сложных критических секций и условного ожидания. Подходит когда нужны сложные условия блокировки.
- **Semaphore** - для управления доступом к ресурсам с ограниченной емкостью. Идеально для producer-consumer с ограниченным буфером.

### 4. Почему синхронизация замедляет выполнение и как уменьшать contention?

Синхронизация создает **contention** (конкуренцию) из-за:
- **Блокировок**, которые заставляют потоки ждать
- **Инвалидации кэшей** при изменении общих данных
- **Переключения контекста** между потоками

Способы уменьшения contention:
- Использовать **lock-free структуры данных**
- Уменьшать **время удержания блокировок**
- Применять **fine-grained locking**
- Использовать **thread-local storage** где возможно
- **Оптимизировать размер критических секций**

### 5. Что такое ложное совместное использование (false sharing) и как его избежать?

**False sharing** возникает, когда несвязанные данные разных потоков попадают в одну кэш-линию, вызывая инвалидацию кэша при изменении любой переменной в этой линии.

Способы избежания:
- **Выравнивание данных** по границам кэш-линий (обычно 64 байта)
- Использование **padding** между часто изменяемыми данными
- Размещение **горячих данных** разных потоков в разных кэш-линиях
- Использование `alignas(CACHE_LINE_SIZE)` в C++

## Общие выводы

1. **Производительность**: Atomic операции на 25-28% эффективнее mutex для простых операций счетчика, что подтверждается тестами с 1,000,000 операций.

2. **Корректность**: Оба метода синхронизации обеспечивают 100% корректные результаты, в отличие от unsync режима, где наблюдается 17.71% потерь.

3. **Producer-Consumer**: Реализация с семафорами эффективно управляет доступом к ограниченному буферу, хотя при дисбалансе производителей/потребителей возможны незначительные потери (0.18%).

4. **Мониторинг потоков**: Linux предоставляет comprehensive инструменты для наблюдения за потоками. На примере видно 6 потоков, распределенных по 4 ядрам CPU с разной нагрузкой.

5. **Распределение нагрузки**: Потоки автоматически распределяются по ядрам процессора (PSR: 0, 1, 2, 3), что демонстрирует эффективность планировщика Linux.

6. **Практическая применимость**: Полученные знания позволяют выбирать оптимальные методы синхронизации в зависимости от конкретной задачи и требований к производительности.
