## Шаги выполнения:

### Пункт 1:

Я создал файл `thread_race.c` (папка `src/`) по шаблону из `lab3/samples/thread_race.c`. Программа запускается с параметрами: количество потоков `N`, количество инкрементов `M` и одним из режимов: `unsync`, `mutex`, `atomic`.

В режиме `unsync` выполняется простая инкрементация общего счётчика без синхронизации. В режиме `mutex` инкремент защищён `pthread_mutex_t`. В режиме `atomic` используется `atomic_fetch_add_explicit(...,memory_order_relaxed)`.

Сборка выполняется с помощью Makefile, который также присутствует в папке `src/`:
```bash
make
```

Примеры режимов запуска:
```bash
./thread_race 4 1000000 unsync
./thread_race 4 1000000 mutex
./thread_race 4 1000000 atomic
```

Соответствующие выводы:
```bash
mode=unsync threads=4 iters_per_thread=1000000 expected=4000000 actual=4000000 time_ms=0

mode=mutex threads=4 iters_per_thread=1000000 expected=4000000 actual=4000000 time_ms=135

mode=atomic threads=4 iters_per_thread=1000000 expected=4000000 actual=4000000 time_ms=20
```

Также сделаны замеры для `N` ∈ {1,2,4,8} и `M` = 1000000:
- В режиме unsync всегда наблюдалось расхождение actual != expected.
- В режиме mutex корректность подтверждена, но время растёт с увеличением числа потоков.
- В режиме atomic корректность соблюдена, время выполнения значительно меньше, чем у mutex.

Вывод: гонка данных легко воспроизводится без синхронизации. Mutex обеспечивает корректность, но дороже по времени. Атомики дают корректность с меньшей задержкой.

### Пункт 2:

Для реализации producer–consumer я создал файл `prodcons.c` в папке `src/`. Здесь используется кольцевой буфер фиксированного размера, два семафора (`sem_items` и `sem_slots`) и `pthread_mutex_t` для защиты буфера при записи и чтении.

Принцип работы:

1. Производитель ждёт, пока есть свободный слот (`sem_wait(&sem_slots)`), затем записывает элемент в буфер и увеличивает семафор занятых элементов (`sem_post(&sem_items)`).

2. Потребитель ждёт, пока есть хотя бы один элемент (`sem_wait(&sem_items)`), читает его и увеличивает количество свободных слотов (`sem_post(&sem_slots)`).

3. Таким образом достигается корректная синхронизация и исключается busy-wait.

Сборка через Makefile:
```bash
make
```
Пример запуска с 2 производителями и 2 потребителями, буфер размером 64 элемента, 100000 элементов всего:
```bash
./prodcons -P 2 -C 2 -N 100000 -B 64
```

Вывод:
```bash
Producers: 2 | Consumers: 2 | Buffer size: 64
Produced: 100000 items
Consumed: 100000 items
Total sum: 152499950000
Elapsed time: 0.041 s
```

Вывод: программа корректно реализует bounded buffer. Сумма произведённых и потреблённых элементов совпадает, все потоки завершаются корректно.

### Пункт 3:

Для изучения потоков процесса в Linux я использовал утилиты `ps` и `/proc`.

Запустил программу `prodcons` в фоне:
```bash
./prodcons -P 2 -C 2 -N 10000000 -B 64 &
PID=$!
```

Просмотр потоков через ps:
```bash
ps -L -p $PID -o pid,tid,psr,pcpu,stat,comm | head -n 10
```

Вывод:
```bash
PID     TID PSR %CPU STAT COMMAND
17015   17015   0  0.0 Sl   prodcons
17015   17017   0  0.0 Rl   prodcons
17015   17018   0  0.0 Rl   prodcons
17015   17019   0  0.0 Rl   prodcons
17015   17020   1  0.0 Rl   prodcons
```

Проверка количества потоков через /proc/<pid>/status:
```bash
cat /proc/$PID/status | grep Threads
```

Результат: `Threads: 5` — 1 главный поток + 2 производителя + 2 потребителя.

Список всех задач (TID) процесса через `/proc/(pid)/task`:
```bash
ls -l /proc/$PID/task
```

Вывод: каждый поток имеет свой TID, но все они делят одно адресное пространство. Это хорошо видно в работе программы: изменения в буфере видны сразу всем потокам.

## Ответы на вопросы:
1. Процесс — это отдельная единица выполнения с собственным адресным пространством, открытыми файловыми дескрипторами, стеками и контекстом CPU. Каждый процесс имеет уникальный PID.

Поток (thread) — «лёгкий процесс», который принадлежит процессу и разделяет с ним память и ресурсы (кучу, глобальные переменные, открытые файлы), но имеет свой собственный стек, регистры и идентификатор потока (TID).

/proc/(pid)/task/ — каталог с подкаталогами для каждого TID процесса.

/proc/(pid)/status — содержит строку Threads: <n>, где <n> — количество потоков.

Команды ps и top: `ps -L -p <PID> -o pid,tid,psr,pcpu,stat,comm` , `top -H -p <PID>`

Таким образом можно видеть все потоки конкретного процесса, их TID, загрузку CPU и статус.

2. Race condition (гонка данных) — ситуация, когда результат работы программы зависит от непредсказуемого порядка выполнения потоков. Например, несколько потоков одновременно читают и записывают общий счётчик. Если доступ не защищён, итоговое значение может отличаться от ожидаемого. 

volatile не решает проблему, потому что оно лишь запрещает компилятору оптимизировать доступ к переменной (например, не кэшировать её в регистре), также оно не делает операции атомарными — чтение и запись всё ещё могут прерываться другим потоком. Для корректности нужны механизмы синхронизации: mutex, semaphore, атомарные операции (stdatomic.h).

3. Mutex используется для защиты сложных критических секций, когда нужно ждать условия (например, «буфер не пустой/не полный»).

Semaphore управляет количеством доступных ресурсов, реализует «счётчик» свободных слотов или элементов.

Атомики Эффективны для простых операций: счётчики, флаги, суммы.

4. Синхронизация замедляет выполнение, потому что потоки блокируются и ждут освобождения ресурса, увеличивая время ожидания. Также частые обращения к одним и тем же переменным приводят к контеншн (contestion) — конкуренции потоков за ресурс.

Уменьшить замедление можно если:

- Минимизировать критические секции: блокировать только необходимую часть кода.

- Использовать атомики для простых счётчиков.

- Шардировать данные: разные потоки работают с отдельными переменными или структурами.

5. False sharing — когда разные переменные, используемые разными потоками, попадают в одну cache line (обычно 64 байта). Из-за этого изменения в одной переменной вызывают инвалидацию кэша для других потоков, даже если они не используют эти данные.

Как избежать:

- Размещать часто изменяемые переменные разных потоков в отдельных структурах, выровненных по границе кэша.

- Использовать массивы и распределять индексы так, чтобы переменные разных потоков не лежали на одной линии кэша.
