## Задание A: Гонка данных и устранение (mutex vs atomic)

#### Цель
Продемонстрировать проблему гонки данных при многопоточном инкременте счетчика и сравнить эффективность двух методов синхронизации: мьютексов (`pthread_mutex_t`) и атомарных операций (`stdatomic.h`).

#### Решение
1. **Реализация программы**: Создана программа `thread_race.c`, которая:
   - Принимает параметры: количество потоков, итераций на поток и режим синхронизации
   - Создает указанное количество потоков для параллельного инкремента общего счетчика
   - Поддерживает два режима синхронизации: `mutex` и `atomic`

2. **Измерение производительности**: 
   - Используется `clock_gettime(CLOCK_MONOTONIC)` для точного измерения времени выполнения
   - Сравнивается ожидаемое значение счетчика с фактическим
   - Проводятся тесты для разного количества потоков (2, 4, 8)

#### Ключевые выводы
1. **Корректность**: Оба метода обеспечивают корректный результат - фактическое значение счетчика всегда равно ожидаемому
2. **Производительность**: Атомарные операции значительно быстрее мьютексов:
   - Для 2 потоков: atomic в ~1.8 раза быстрее
   - Для 4 потоков: atomic в ~1.4 раза быстрее  
   - Для 8 потоков: atomic в ~1.8 раза быстрее
1. **Масштабируемость**: С увеличением количества потоков время выполнения растет для обоих методов, но атомарные операции демонстрируют лучшую масштабируемость

#### Как проверяли
```bash
# Компиляция и запуск тестов
make race
./bin/thread_race 2 10000000 mutex
./bin/thread_race 4 10000000 mutex  
./bin/thread_race 8 10000000 mutex
./bin/thread_race 2 10000000 atomic
./bin/thread_race 4 10000000 atomic
./bin/thread_race 8 10000000 atomic
```

**Результаты:**

| Потоки | Режим  | Ожидаемое | Фактическое | Время(мс) |
| ------ | ------ | --------- | ----------- | --------- |
| 2      | mutex  | 20000000  | 20000000    | 716       |
| 4      | mutex  | 40000000  | 40000000    | 1527      |
| 8      | mutex  | 80000000  | 80000000    | 3457      |
| 2      | atomic | 20000000  | 20000000    | 381       |
| 4      | atomic | 40000000  | 40000000    | 1074      |
| 8      | atomic | 80000000  | 80000000    | 1921      |

Оба метода обеспечивают корректность, но атомарные операции показывают существенное преимущество в производительности за счет более легковесной реализации на аппаратном уровне.
## Задание B: Producer-Consumer (bounded buffer, семафоры)

#### Цель
Реализовать задачу producer-consumer с использованием bounded buffer (кольцевой очереди) и синхронизации на основе POSIX семафоров. Обеспечить корректную работу при параллельном доступе нескольких производителей и потребителей, включая полную проверку целостности данных через вычисление ожидаемой суммы.

#### Шаги/Решение
1. **Структура данных**: Реализована кольцевая очередь (`ring_buffer_t`) с фиксированной емкостью, содержащая:
   - Массив данных и индексы head/tail
   - Два семафора: `free_slots` (свободные места) и `used_slots` (занятые места)
   - Мьютекс для защиты критических секций при модификации структуры
   - Счетчик активных производителей

2. **Синхронизация**:
   - **Producer**: Ожидает свободного места через `sem_wait(&free_slots)`, добавляет элемент, сигнализирует о новом элементе через `sem_post(&used_slots)`
   - **Consumer**: Ожидает доступных элементов через `sem_timedwait(&used_slots)` с таймаутом, извлекает элемент, освобождает место через `sem_post(&free_slots)`
   - **Корректное завершение**: При завершении производителей уменьшается счетчик `producers_active`, что позволяет потребителям корректно завершиться

3. **Проверка корректности**: 
   - Сравнивается общее количество произведенных и потребленных элементов
   - Вычисляется фактическая сумма потребленных значений
   - Вычисляется ожидаемая сумма по математической формуле для проверки целостности данных

#### Ключевые выводы
1. **Полная корректность данных**: Программа обеспечивает не только сохранность количества элементов, но и полную целостность данных - фактическая сумма всегда совпадает с ожидаемой
2. **Математическая верификация**: Добавлена строгая математическая проверка через вычисление ожидаемой суммы, что исключает любые искажения данных
3. **Эффективная синхронизация**: Использование семафоров позволяет эффективно управлять доступом к буферу без busy-wait
4. **Надежное завершение**: Механизм с `producers_active` и таймаутами гарантирует корректное завершение всех потоков при различных конфигурациях

#### Как проверяли
```bash
# Компиляция и запуск различных конфигураций
make prodcons
./bin/prodcons -P 2 -C 2 -N 100000 -B 64
./bin/prodcons -P 4 -C 4 -N 200000 -B 32
./bin/prodcons -P 1 -C 3 -N 50000 -B 16
```

**Результаты выполнения:**

**Тест 1:**
```
[prodcons] P=2 C=2 N=100000 B=64 produced=100000 consumed=100000 sum=152499950000
[prodcons] Excepted sum = 152499950000
```

**Тест 2:**
```
[prodcons] P=4 C=4 N=200000 B=32 produced=200000 consumed=200000 sum=504999900000
[prodcons] Excepted sum = 504999900000
```

**Тест 3:**
```
[prodcons] P=1 C=3 N=50000 B=16 produced=50000 consumed=50000 sum=51249975000
[prodcons] Excepted sum = 51249975000
```

**Анализ результатов:**
- Во всех тестах `produced = consumed = N` - все элементы успешно обработаны
- Фактическая сумма `sum` в точности равна ожидаемой `Excepted sum` во всех случаях
- Программа корректно работает с разными соотношениями производителей/потребителей (2/2, 4/4, 1/3)
- Различные размеры буфера (64, 32, 16) не влияют на целостность данных
## Задание C: Где видны потоки

#### Цель
Продемонстрировать видимость потоков в системе Linux во время выполнения многопоточной программы, используя различные системные утилиты и интерфейсы `/proc`.

#### Шаги/Решение
1. **Запуск длительной операции**: Запущена программа producer-consumer с большим количеством элементов (20 миллионов) для обеспечения достаточного времени наблюдения за потоками
2. **Использование команды `ps -L`**: Показана информация о всех потоках процесса с отображением PID, TID, процессора, загрузки CPU и состояния
3. **Анализ `/proc/<PID>/status`**: Получено общее количество потоков в процессе
4. **Просмотр директории `/proc/<PID>/task`**: Показаны отдельные директории для каждого потока (TID)

#### Ключевые выводы
1. **Структура потоков**: В процессе присутствует 5 потоков:
   - Главный поток (PID = TID = 10852) в состоянии `Sl` (sleeping, multi-threaded)
   - 4 рабочих потока (10853-10856) в состояниях `Rl` (running, multi-threaded) и `Sl`

2. **Распределение по CPU**: Потоки распределены по разным процессорным ядрам (PSR: 2, 1, 7, 3), что демонстрирует реальную параллельную работу

3. **Загрузка CPU**: Рабочие потоки показывают высокую загрузку (74.6%-94.5%), в то время как главный поток практически не нагружен (0.0%) - типичная картина для producer-consumer паттерна

4. **Состояния потоков**: 
   - `Rl` - потоки активно выполняются (producer/consumer рабочие потоки)
   - `Sl` - поток ожидает (главный поток ожидает завершения через `pthread_join`)

5. **Интерфейс `/proc`**: Каждый поток имеет свою директорию в `/proc/<PID>/task/` с собственным TID, что подтверждает их независимое представление в системе

#### Как проверяли
```bash
# Запуск программы в фоне с большим объемом работы
make prodcons
./bin/prodcons -P 2 -C 2 -N 20000000 -B 64 & PID=$!

# Просмотр информации о потоках во время выполнения
echo "[PID] $PID"
ps -L -p "$PID" -o pid,tid,psr,pcpu,stat,comm | head -n 20 | cat
cat /proc/"$PID"/status | grep Threads
ls -l /proc/"$PID"/task | head -n 10 | cat
wait "$PID"
```

**Анализ результатов:**
- **5 потоков** соответствуют: 1 главный + 2 producer + 2 consumer

- **Распределение по ядрам** (PSR: 1, 2, 3, 5, 7) показывает реальную параллельную работу
- **Высокая загрузка рабочих потоков** (до 94.5%) свидетельствует об эффективном использовании CPU
- **Директории `/proc/10852/task/`** содержат поддиректории для каждого TID, что подтверждает независимое представление потоков в ядре

Система Linux рассматривает потоки как "легковесные процессы" (LWP), что подтверждается наличием отдельных записей в планировщике и файловой системе `/proc`.
## Вопросы для отчёта
**1. Чем поток отличается от процесса? Где увидеть поток в `/proc` и `ps`?**
Поток разделяет память и ресурсы процесса, но имеет свой стек. Потоки видны в `ps -L`, `/proc/PID/task/`, `/proc/PID/status` (Threads).

**2. Что такое race condition и почему `volatile` не решает проблему корректности?**
Race condition - гонка данных при параллельном доступе. volatile не решает проблему, так как не гарантирует атомарность операций и не предотвращает переупорядочивание.

**3. Когда выбирать `mutex/condvar`, когда `semaphore`, когда атомики?**
mutex/condvar - для сложной логики ожидания, semaphore - для ограничения доступа к ресурсам, атомики - для простых операций над переменными.

**4. Почему синхронизация замедляет выполнение и как уменьшать contention?**
Замедление из-за блокировок и переключения контекста. Снижать contention можно уменьшив время блокировки.

**5. Что такое ложное совместное использование (false sharing) и как его избежать?**
Разные переменные в одной кэш-линии вызывают инвалидацию кэша. Избегать: выравнивание данных, разделение часто изменяемых переменных.
