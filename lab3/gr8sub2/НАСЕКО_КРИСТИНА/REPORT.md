# Лабораторная 3 — Потоки, синхронизация и гонки данных
Практика по многопоточности в Linux: увидим гонки данных, устраним их примитивами синхронизации, реализуем bounded buffer (producer–consumer) и посмотрим, где видны потоки в `/proc` и утилитах.

## Цели
- Понять модель потоков (TID, Threads) и где их смотреть в системе.
- На практике воспроизвести race condition и корректно её устранить.
- Освоить базовые примитивы: `pthread_mutex_t`, `pthread_cond_t` и/или POSIX `sem_t`.
- Сопоставить корректность и производительность при разной синхронизации.

Ubuntu 24.04.3 на VirtualBox.

Варинат для лабораторной работы - 2.

## Задания

### 1) Гонка данных и устранение (mutex vs atomic)
Цель: демострация гонки данных (инкремент счетчика) и сравнить два конкретных способа устранения гонки данных - сравнить их корректность и производительность.

Шаги/решения:
    - До конца реализовать код в файле thread_race.c
    - Увидеть гонку данных при параллельном инкрименте.
    - Сравнить и выполнить два конкретных способа устранения гонки данных.
    
Код:
    Код на С представлен в файле thread_race.c, сборка и запуск файла с помощью Makefile, конкретные параметры запуска thread_race.c представлены ниже:

Команда:
~~~
    ./thread_race 8 10000000 unsync
~~~
  
Результат:
~~~
    mode=unsync threads=8 iters_per_thread=10000000 expected=80000000 actual=10000000 time_ms=6387
~~~

Команда:
~~~
    ./thread_race 8 10000000 mutex
~~~
  
Результат:
~~~
    mode=mutex threads=8 iters_per_thread=10000000 expected=80000000 actual=80000000 time_ms=4897
~~~

Команда:
~~~
    ./thread_race 8 10000000 atomic
~~~
  
Результат:
~~~
    mode=atomic threads=8 iters_per_thread=10000000 expected=80000000 actual=80000000 time_ms=1177
~~~

Выводы:
  Без синхронизации результат многопточного инкремента отличается от ожидаемого (expected > actual).
  Оба подхода: `mutex` и `atomic` - показали верный результат, т.е. expected равняется actual, однако для одинаковых входных данных `atomic` работает быстрее `mutex`.
    
Использование ИИ:
    Помощь в понимании кода на С в файле thread_race.c и проверка правильности полной реализации кода для данного задания. Замедление работы кода при выборе его выполнения без синхронизации (без искусственной задержки не было видно гонки данных на моем устройстве - т.е. expected равнялось actual).

## Ответы на вопросы
1. Процесс – это экземпляр выполняемой программы со своим пространством памяти и ресурсами, а поток – это минимальная единица выполнения внутри процесса, которая делит ресурсы и память с другими потоками одного процесса, но имеет собственные стеки и регистры. Увидеть поток можно: в ps - с помощью ключа -L (ps -L -p <PID>), в /proc - в каталогах /proc/<PID>/task/.
2. Race condition - возникает, когда несколько потоков одновременно обращаются к общим данным (например одновременно увеличивают счетчик - инкермент теряет обновление). Volatile отменяет некоторые оптимизации компилятора (например, кэширование в регистре) и указывает, что значение переменной может быть изменино извне, но он не обеспечивает атомарности операций или барьеров памяти.
3. mutex:основной инструмент защиты критических секций (участки кода, где происходит несколько операций с общими данными).
   condvar (условные переменные): используется вместе с mutex, когда потоку необходимо ждать выполнения некоторого условия. 
   semaphore: удобно для счетчиков ресурсов; более общий механизм, чем mutex, но не заменяет его. 
   атомики: используются для простых операций над одиночными переменными (короткие атомарные операции, например, декремент или инкремент).
4. Замедление происходит из-за накладных расходов (вызов функций синхронизации), блокировок и конкуренции. Способы уменьшения конкуренции: уменьшить размер критических секций, при возможности использовать более легкие примитивы (атомики), уменьшить частоту синхронизации.
5. Ложное совместное использование (false sharing) – это снижение производительности в многопоточных программах, когда несколько потоков работают с разными переменными, расположенными в одной кеш-линии процессора. Как избежать false sharing: сделать так, чтобы переменные, активно используемые разными потоками, гарантированно попадали в разные кэш-линии.
