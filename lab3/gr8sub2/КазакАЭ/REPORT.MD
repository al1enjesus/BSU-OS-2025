## 1. Цель работы

1) Воспроизвести гонку данных на инкременте общего счётчика.  
2) Устранить гонку двумя способами: через `pthread_mutex_t` и через C11 атомики (`stdatomic.h`, `memory_order_relaxed`).  
3) Реализовать bounded buffer (producer–consumer) на `pthread_mutex_t` + `pthread_cond_t` без busy-wait и с корректным завершением потребителей.  
4) Показать, где видны потоки: `ps -L`, `/proc/<PID>/status`, `/proc/<PID>/task`.

## 5. Часть A — Гонка данных и устранение

### 5.1. Описание реализации

- `thread_race`: создаётся `N` потоков; суммарно выполняется ровно `M_total` инкрементов. Распределение равномерное, остаток от деления раздаётся первым потокам.  
- Режимы:
  - `unsync` — инкремент без синхронизации;
  - `mutex` — инкремент в критической секции под `pthread_mutex_t`;
  - `atomic` — `atomic_fetch_add_explicit(..., memory_order_relaxed)`.
- Тайминг: `CLOCK_MONOTONIC`. Формат строки вывода:
  ```
  mode=... N=... M_total=... expected=... actual=... elapsed_ms=...
  ```

### 5.2. Методика эксперимента

- Фиксированный объём работы: `M_total = 8 000 000` для `N ∈ {1,2,4,8}`.  
- Для каждого случая выполнено по три запуска; в таблице указаны средние значения.

### 5.5. Интерпретация

- `unsync`: инкремент не атомарен; параллельные потоки перезаписывают значение, поэтому `actual < expected`.  
- `mutex`: корректность достигается за счёт эксклюзивного доступа; ухудшение времени при росте `N` связано с контеншном и когерентностью кеша.  
- `atomic`: атомарная операция без блокировок; быстрее mutex, но сериализация на одной кеш-строке счётчика сохраняется.

## 6. Часть B — Producer–Consumer (mutex + condvar)

### 6.1. Инварианты и протокол

- Кольцевой буфер ёмкости `B` с полями `head`, `tail`, `count`, `buf`.  
- Один `mutex` защищает все поля буфера.  
- Две условные переменные:  
  - `not_full` — производители ждут при `count == cap`;  
  - `not_empty` — потребители ждут при `count == 0`.  
- Завершение: после `join` всех производителей главный поток ставит `producers_done = true` под `mutex` и выполняет `pthread_cond_broadcast(&not_empty)`. Потребитель выходит, когда `count == 0 && producers_done == true`. Busy-wait отсутствует.  
- Проверка корректности: `consumed_count == N_total` и `sum == N_total*(N_total+1)/2`.

### 6.2. Команды и результаты

Команды:
```bash

./bin/prodcons -P 4 -C 4 -N 500000  -B 256

```

## 8. Ответы на контрольные вопросы

1) **Поток vs процесс; где увидеть поток**. Процесс имеет собственное адресное пространство; потоки разделяют адресное пространство процесса и его ресурсы. Потоки видны как подкаталоги `/proc/<PID>/task/<TID>`, их число — поле `Threads` в `/proc/<PID>/status`. В `ps` — опция `-L`.  
2) **Race condition и `volatile`**. Race condition — зависимость результата от недетерминированного межпоточного расписания при совместном доступе без синхронизации. `volatile` не делает операции атомарными и не задаёт межпоточный порядок, следовательно проблему корректности не решает.  
3) **Когда `mutex/condvar`, когда `semaphore`, когда атомики**. `mutex/condvar` — для составных критических секций и ожидания условий; `semaphore` — для счётчиков ресурсов и ограничения параллелизма (в т.ч. межпроцессно); атомики — для коротких операций над скалярами без ожиданий.  
4) **Почему синхронизация замедляет и как уменьшать contention**. Причины: блокировки, переключения контекста, когерентность кеша. Снижение: минимизация критических секций, батчинг, sharding/striping, локальные структуры на поток, разумный выбор размера буфера, устранение false sharing.  
5) **False sharing**. Независимые данные разных потоков попали в одну кеш-строку → лишние инвалидации. Избежать: паддинг/выравнивание под размер кеш-строки, разнос «горячих» полей, per-thread хранение данных.
