## 1. Цель работы

1) Воспроизвести **гонку данных** на инкременте общего счётчика.  
2) Корректно устранить гонку двумя способами:  
   - `pthread_mutex_t` (блокировка);  
   - C11 атомики (`stdatomic.h`, `memory_order_relaxed`).  
3) Реализовать **bounded buffer** (producer–consumer) на `pthread_mutex_t` + `pthread_cond_t`: `not_full`/`not_empty`, **без busy-wait**, корректное завершение.  
4) Показать, где видны **потоки**: `ps -L`, `/proc/<PID>/status`, `/proc/<PID>/task`.

## 5. Часть A — Гонка данных и устранение

### 5.1. Описание реализации

- Утилита `thread_race` создаёт `N` потоков и **строго равномерно** распределяет `M_total` инкрементов: каждому по `M_total / N`, остаток (`M_total % N`) раздаётся первым потокам.  
- Режимы:
  - `unsync` — намеренная гонка: `counter++` без синхронизации; ожидаем `actual < expected`.  
  - `mutex` — один `pthread_mutex_t` защищает инкремент.  
  - `atomic` — `atomic_fetch_add_explicit(..., memory_order_relaxed)`; корректно, обычно быстрее мьютекса.  
- Замер времени: `CLOCK_MONOTONIC`, на выход **одна строка**:
  ```
  mode=... N=... M_total=... expected=... actual=... elapsed_ms=...
  ```

### 5.2. Методика эксперимента

- Для сравнимости производительности зафиксирован объём работы: **`M_total = 8 000 000`** при `N ∈ {1,2,4,8}`.  
- Каждую конфигурацию запускал **3 раза**, в таблице — среднее.

## 6. Часть B — Producer–Consumer (mutex + condvar)

### 6.1. Инварианты и протокол

- **Кольцевой буфер** ёмкости `B`: поля `head`, `tail`, `count`, массив `buf`.  
- Один `mutex` защищает все поля буфера.  
- Две условные переменные:  
  - `not_full` — производители ждут при `count == cap`;  
  - `not_empty` — потребители ждут при `count == 0`.  
- Производители генерируют **точно** числа из диапазона `1..N_total` **без перекрытия** между потоками (распределение диапазона по P).  
- **Корректное завершение:** после `join` всех производителей главный поток делает:
  1) `producers_done = true` под `mutex`;  
  2) `pthread_cond_broadcast(&not_empty)` — разбудить всех потребителей;  
  3) Потребитель завершает цикл, когда `count == 0 && producers_done == true`.  
- **Busy-wait отсутствует** (только `pthread_cond_wait`).

### 6.2. Проверка корректности

- `consumed_count == N_total`  
- `sum == N_total*(N_total+1)/2`

### 6.3. Серии и результаты (среднее по 3 запускам)

Команды:

## 8. Анализ и интерпретация

1) **Гонка данных (`unsync`)**: `counter++` состоит из чтения → увеличения → записи; при параллельном доступе операции переписывают друг друга → `actual < expected`.  
2) **`mutex`**: корректен за счёт эксклюзивности критической секции. Ухудшение времени при росте `N` — следствие очереди на замок и когерентности кеша.  
3) **`atomic`**: одна атомарная RMW-операция без парковки потоков → лучше, чем mutex; но сериализация по одной кеш-строке остаётся, идеальной масштабируемости нет.  
4) **Producer–Consumer**: правильный протокол ожиданий (`cond_wait`) и оповещений (`signal`/`broadcast`) обеспечивает отсутствие busy-wait и зависаний.  
5) **Снижение контеншна**: укорочение/редкость критических секций, локальные буферы и батчинг, sharding/striping, разумный выбор `B`, избегание false sharing (паддинг/разнос горячих полей).

## 9. Ответы на вопросы (из ТЗ)

1) **Поток vs процесс; где увидеть поток в `/proc` и `ps`?**  
   Процесс — отдельное адресное пространство и ресурсы; потоки делят адресное пространство процесса. Потоки видны в `/proc/<PID>/task/<TID>` и по суммарному числу `Threads:` в `/proc/<PID>/status`. В `ps`: `ps -L -p <PID>`/`ps -eL`.

2) **Что такое race condition и почему `volatile` не решает корректность?**  
   Race condition — результат зависит от недетерминированного расписания при совместном доступе без синхронизации. `volatile` не делает операции атомарными и не задаёт межпоточный порядок (happens-before); он лишь ограничивает оптимизации компилятора в границах одного потока.

3) **Когда выбирать `mutex/condvar`, когда `semaphore`, когда атомики?**  
   - `mutex/condvar`: составные критические секции, ожидание условий, координация sleep/wakeup.  
   - `semaphore`: счётчики ресурсов/слотов, ограничение параллелизма, IPC/межпроцессные сценарии.  
   - **атомики**: короткие операции на скалярах без ожиданий; когда не нужна сигнализация условий.

4) **Почему синхронизация замедляет и как уменьшать contention?**  
   Блокировки и сериализация, переключения контекста, протокол когерентности кеша. Снижать: укорачивать критические секции, батчить операции, sharding/striping, RW-замки по месту, атомики, увеличение `B` до разумного уровня, устранение false sharing.

5) **Что такое ложное совместное использование (false sharing) и как его избежать?**  
   Независимые данные разных потоков лежат в одной кеш-строке → лишние инвалидации и падение производительности. Избежать: паддинг/выравнивание до размера кеш-строки, разделение структур (SoA), per-thread данные.
