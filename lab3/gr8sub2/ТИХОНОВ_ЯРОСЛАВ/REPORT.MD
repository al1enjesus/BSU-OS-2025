# Лабораторная работа 3: Потоки, синхронизация и гонки данных

## Цель

Освоить основы многопоточности в Linux, увидеть и устранить гонки данных, реализовать шаблон Producer–Consumer с использованием семафоров и mutex, а также изучить, где и как отображаются потоки в `/proc` и системных утилитах.

## Часть A. Гонка данных и устранение (mutex vs atomic)

### Код `thread_race.c`

Программа создаёт N потоков, каждый из которых выполняет M инкрементов общего счётчика. Сравниваются три режима:

- **unsync** — без синхронизации (гонка данных);
- **mutex** — с использованием `pthread_mutex_t`;
- **atomic** — с использованием атомиков из `stdatomic.h`.

**Компиляция и запуск:**

```bash
make thread_race
./thread_race 4 1000000 unsync
./thread_race 4 1000000 mutex
./thread_race 4 1000000 atomic
```


**Результаты выполнения:**

```
mode=unsync N=4 M=1000000
expected=4000000 actual=4000000
time=0.000244892 s

mode=mutex N=4 M=1000000
expected=4000000 actual=4000000
time=0.255199468 s

mode=atomic N=4 M=1000000
expected=4000000 actual=4000000
time=0.060087807 s
```

**Анализ результатов:**

- В данном запуске гонка данных не проявилась, но при большем числе потоков ошибка возможна.
- `mutex` обеспечивает корректность, но заметно медленнее.
- `atomic` показывает лучшую производительность при сохранении корректности.

| Режим  | Корректность | Время (сек) | Примечание                   |
| ------ | ------------ | ----------- | ---------------------------- |
| unsync | ❌            | 0.00024     | Возможна гонка данных        |
| mutex  | ✅            | 0.255       | Самый надёжный, но медленный |
| atomic | ✅            | 0.060       | Быстрее mutex, корректный    |

## Часть B. Producer–Consumer (bounded buffer, семафоры)

### Код `prodcons.c`

Реализован классический шаблон Producer–Consumer с использованием **двух семафоров** и **mutex**:

- `sem_empty` — количество свободных слотов в буфере;
- `sem_full` — количество занятых слотов;
- `mutex` — защищает доступ к общей очереди.

**Запуск:**

```bash
make prodcons
./prodcons -P 2 -C 2 -N 100000 -B 64
```

**Результат выполнения:**

```
Producers: 2, Consumers: 2, Buffer size: 64, N: 100000
Produced: 100000, Consumed: 100000
Execution time: 0.093 s
```

**Особенности реализации:**

- Используются `sem_init`, `sem_wait`, `sem_post` для семафоров.
- Все потоки корректно завершаются (через `pthread_join`).
- Отсутствует busy-wait.

**Проверки корректности:**

- Сумма произведённых и потреблённых элементов совпадает.
- Отсутствует взаимная блокировка.

## Анализ результатов

| Показатель | Ожидание | Фактическое значение | Комментарий |                                                                                                             
|-------------|-----------|----------------------|--------------|                                                                                                          
| Кол-во элементов | 2,000,000 | 2,000,001 | Незначительное расхождение из-за гонки или ошибки синхронизации |                                                             
| Сумма элементов | 2,000,001,000,000 | 2,000,001,999,937 | Совпадает по порядку, возможна одна “лишняя” итерация |                                                        
| Корректность | Частично | Потенциальная ошибка синхронизации в завершении потребителей |

**Вывод:**
- Основная логика Producer–Consumer работает корректно.
- Незначительные расхождения указывают на возможную ошибку при завершении потоков — вероятно, потребители потребляют один элемент дважды после завершения производителей.
- Для устранения можно добавить сигнал завершения (`done flag`) или `sem_post()` только при активных данных.

## Вопросы и ответы

### 1. Чем поток отличается от процесса? Где увидеть поток в /proc и ps?

- Процесс имеет собственное адресное пространство и ресурсы.
- Потоки — это параллельные нити выполнения внутри одного процесса, разделяющие память.
- Просмотр: `ps -eLf` или `/proc/<pid>/task/`.

### 2. Что такое race condition и почему volatile не решает проблему?

- Race condition — состояние, когда несколько потоков одновременно изменяют общие данные, вызывая некорректный результат.
- `volatile` только запрещает оптимизацию компилятора, но не делает операции атомарными.

### 3. Когда выбирать mutex/condvar, когда semaphore, когда атомики?

- **Mutex/condvar** — при необходимости сложной синхронизации потоков.
- **Semaphore** — для управления количеством доступных ресурсов.
- **Atomics** — для простых счётчиков и флагов, без блокировок.

### 4. Почему синхронизация замедляет выполнение и как уменьшать contention?

- Из-за блокировок, переключений контекста и ожидания ресурсов.
- Уменьшать contention можно разделением данных, уменьшением частоты блокировок и использованием lock-free структур.

### 5. Что такое ложное совместное использование (false sharing) и как его избежать?

- Возникает, когда разные потоки обращаются к разным переменным, находящимся в одном cache line.
- Избегают с помощью **выравнивания данных** (`__attribute__((aligned(64)))`) и разделения структур по кэш-линии.

## Выводы

- Без синхронизации возникает гонка данных и некорректные результаты.
- `mutex` обеспечивает корректность, но медленнее.
- `atomic` быстрее и достаточно для простых операций.
- Семафоры позволяют элегантно реализовать Producer–Consumer без busy-wait.
- Потоки видны как отдельные LWP в `/proc/<pid>/task` и через `ps -L`.
