# Задание A — Гонка данных и устранение

## Постановка задачи

Создать многопоточную программу, в которой несколько потоков инкрементируют общий счётчик.  
Реализовать три версии:

1. Без синхронизации — продемонстрировать **гонку данных**.  
2. С использованием **мьютекса** (`pthread_mutex_t`).  
3. С использованием **атомиков** (`stdatomic.h`).  

Цель — сравнить корректность и производительность трёх подходов.

---

## Реализация (`thread_race.c`)

Каждый поток выполняет фиксированное число итераций, увеличивая общий счётчик.  
При отсутствии синхронизации несколько потоков обращаются к одной переменной одновременно, что приводит к потере инкрементов.

### 1. Без синхронизации (демонстрация гонки)

```c
for (long long i = 0; i < a->iterations_per_thread; i++) {
    shared_counter_unsync++;
}
```

### 2. С мьютексом

```c
for (long long i = 0; i < a->iterations_per_thread; i++) {
    pthread_mutex_lock(&counter_mutex);
    shared_counter_mutex++;
    pthread_mutex_unlock(&counter_mutex);
}
```

### 3. С атомиками

```c
for (long long i = 0; i < a->iterations_per_thread; i++) {
    atomic_fetch_add_explicit(&shared_counter_atomic, 1, memory_order_relaxed);
}
```

- Использование **мьютекса** (`pthread_mutex_t`) гарантирует корректность, так как только один поток может изменить значение в момент времени. Однако из-за частых блокировок выполнение становится медленнее.  
- При применении **атомиков** (`stdatomic.h`) операции выполняются атомарно на уровне процессора, что устраняет гонку и при этом минимизирует накладные расходы по сравнению с мьютексом.

# Задание B — Модель «Производитель–Потребитель» (bounded buffer)

## Постановка задачи

Реализовать взаимодействие нескольких производителей и потребителей через общий буфер фиксированной длины.  
Синхронизация выполняется с помощью **POSIX семафоров (`sem_t`)** и **мьютекса (`pthread_mutex_t`)**.  

---

## Логика работы

1. **Производитель (Producer)**:
   - ждёт свободное место в буфере (`sem_wait(&sem_empty)`);  
   - помещает элемент, обновляет `tail`;  
   - разблокирует буфер и сигнализирует о новом элементе (`sem_post(&sem_full)`).  

2. **Потребитель (Consumer)**:
   - ждёт появления элемента (`sem_wait(&sem_full)`);  
   - извлекает элемент, обновляет `head`;  
   - сообщает о появлении свободного слота (`sem_post(&sem_empty)`).  

3. Для защиты структуры буфера используется **мьютекс**, чтобы избежать одновременной записи и чтения.  

---

## Основные фрагменты кода (`prodcons.c`)

```c
sem_t sem_empty, sem_full;
pthread_mutex_t buffer_mutex;

void* producer_thread(void* arg) {
    for (int i = 0; i < n; i++) {
        sem_wait(&sem_empty);
        pthread_mutex_lock(&buffer_mutex);
        buffer[tail] = i;
        tail = (tail + 1) % capacity;
        pthread_mutex_unlock(&buffer_mutex);
        sem_post(&sem_full);
    }
    return NULL;
}

void* consumer_thread(void* arg) {
    for (;;) {
        sem_wait(&sem_full);
        pthread_mutex_lock(&buffer_mutex);
        int value = buffer[head];
        head = (head + 1) % capacity;
        pthread_mutex_unlock(&buffer_mutex);
        sem_post(&sem_empty);
    }
}
```

## Пояснения к решению

- Семафоры `sem_empty` и `sem_full` контролируют количество свободных и занятых ячеек буфера.  
- Мьютекс `buffer_mutex` защищает операции записи и чтения.  
- Ожидание реализовано через `sem_wait()` — потоки блокируются без активного ожидания (busy-wait).  
- Размер буфера (`-B`) влияет на производительность:  
  маленький буфер вызывает частые блокировки, слишком большой — перерасход памяти.

- Количество произведённых и потреблённых элементов совпадает.  
- Гонок данных и взаимных блокировок не возникает.

# Контрольные вопросы

**1. Чем поток отличается от процесса?**  
Процессы имеют отдельное адресное пространство, а потоки его разделяют. Потоки совместно используют память и файловые дескрипторы, что повышает эффективность, но требует синхронизации.

**2. Что такое race condition и почему `volatile` не помогает?**  
Race condition — это ситуация, когда несколько потоков одновременно обращаются к одной переменной без синхронизации.  
`volatile` предотвращает оптимизацию доступа, но не делает операции атомарными.

**3. Когда использовать `mutex`, `semaphore`, `atomic`?**  
- `mutex` — защита критических секций и структур данных;  
- `semaphore` — ограничение числа потоков, получающих доступ к ресурсу;  
- `atomic` — быстрые атомарные операции для счётчиков и флагов.

**4. Почему синхронизация снижает производительность?**  
Блокировки вызывают переключения контекста и ожидание, снижая степень параллелизма.

**5. Что такое ложное совместное использование (false sharing)?**  
Разные потоки изменяют данные в одной кэш-линии, вызывая постоянную инвалидацию кэша.  
Решение: разнести данные (например, с помощью `alignas(64)`).
