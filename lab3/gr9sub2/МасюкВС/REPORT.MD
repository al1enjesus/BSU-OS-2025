## Цель работы
Изучить основы многопоточности в Linux: воспроизвести и устранить гонки данных с помощью мьютексов и атомарных операций, реализовать задачу «производитель–потребитель» на основе семафоров и рассмотреть, как потоки отображаются в системе и в файловой структуре /proc.

## A) Гонка данных и синхронизация

### Методика эксперимента
Создано приложение, в котором N потоков выполняют M инкрементов общего счётчика.
Реализованы три режима:
1. unsync — без синхронизации (демонстрация ошибки);
2. mutex — использование pthread_mutex_t для защиты счётчика;
3. atomic — применение атомарных операций из stdatomic.h.

| 4 | 1M | mutex  | 0.233 | 4000000 | 4000000 | Корректно |

### Выводы по части A
Без синхронизации наблюдается расхождение между ожидаемым и фактическим значением счётчика, что подтверждает наличие гонки данных.
Использование мьютекса гарантирует корректность, но замедляет выполнение из-за блокировок.
Атомарные операции обеспечивают правильный результат с меньшими накладными расходами и лучшей масштабируемостью.

## B) Producer–Consumer (ограниченный буфер, семафоры)

### Принцип работы
Реализован кольцевой буфер фиксированного размера.
Синхронизация потоков выполнена через три объекта:
- sem_t empty — количество свободных ячеек буфера;
- sem_t full — число занятых ячеек;
- pthread_mutex_t mutex — защита критической секции при доступе к буферу.

### Логика работы потоков

Производитель (Producer):
```c
sem_wait(&empty);
pthread_mutex_lock(&mutex);
buffer[in] = item;
in = (in + 1) % size;
pthread_mutex_unlock(&mutex);
sem_post(&full);
```

Потребитель (Consumer):
```c
sem_wait(&full);
pthread_mutex_lock(&mutex);
item = buffer[out];
out = (out + 1) % size;
pthread_mutex_unlock(&mutex);
sem_post(&empty);
```

### Результаты тестов

Тест 1
```bash
./prodcons -P 2 -C 2 -N 100000 -B 64
```
Результат: произведено и потреблено 200000 элементов, суммы совпадают.
Время выполнения: около 0.177 с — корректная работа.

Тест 2 (буфер 5 элементов)
```bash
./prodcons -P 2 -C 2 -N 50000 -B 5
```
Время выполнения: около 0.795 с — программа работает корректно, но медленнее из-за ожидания освобождения буфера.

Тест 3 (3 производителя, 1 потребитель)
```bash
./prodcons -P 3 -C 1 -N 30000 -B 20
```
Результат: произведено и потреблено 90000 элементов.
Время выполнения: около 0.445 с — корректное завершение без потерь.

Тест 4 (1 производитель, 3 потребителя)
```bash
./prodcons -P 1 -C 3 -N 30000 -B 20
```
Результат: произведено 30000 элементов, распределено между тремя потребителями.
Время выполнения: около 0.134 с — корректная работа, ускорение за счёт параллельного потребления.

## C) Потоки в системе

### Проверка видимости потоков
Запуск процесса в фоне:
```bash
./prodcons -P 2 -C 2 -N 10000 -B 10 &
```
PID = 8887

Команды анализа:
```bash
ps -L -p 8887 -o pid,tid,psr,pcpu,stat,comm
cat /proc/8887/status | grep Threads
ls -l /proc/8887/task
```

Результаты:
- ps -L показывает 5 потоков (TID 8887–8891);
- /proc/8887/status содержит Threads: 5;
- /proc/8887/task/ — каталог с поддиректориями по каждому потоку.

### Выводы
Потоки отображаются как отдельные задачи (task) в /proc/<PID>/task/.
Планировщик Linux распределяет их по ядрам автоматически.
Утилиты ps, top, htop позволяют наблюдать потоки наряду с процессами.

## Ответы на контрольные вопросы

1. Чем поток отличается от процесса?
Процесс — независимая программа со своей памятью. Потоки — часть процесса, использующая общее адресное пространство, но имеющая собственные стеки и идентификаторы (TID).

2. Что такое race condition и почему volatile не спасает?
Race condition — ситуация, когда результат вычислений зависит от порядка исполнения потоков.
volatile не делает операции атомарными, а лишь запрещает кэширование значения, поэтому не предотвращает гонки.

3. Когда использовать mutex, semaphore и atomic?
mutex — для защиты общих структур данных;
semaphore — для учёта количества ресурсов;
atomic — для простых счётчиков и флагов.

4. Почему синхронизация снижает производительность и как уменьшить contention?
Блокировки вызывают ожидание и переключения контекста.
Минимизировать contention можно разделением данных, использованием нескольких замков и сокращением времени удержания блокировки.

5. Что такое ложное совместное использование (false sharing)?
Когда независимые данные находятся в одной кэш-линии и изменение одного значения вызывает синхронизацию кэша на всех ядрах.
Решается выравниванием данных (например, alignas(64)) или разнесением структур.
