## A) Гонка данных и устранение (mutex vs atomic)

Реализована программа `thread_race`, где N потоков суммарно выполняют M инкрементов общего счётчика.
Проверены три режима:
- `unsync` — без синхронизации (для демонстрации некорректности; в моей среде гонка не проявилась, см. ниже).
- `mutex` — корректный инкремент под `pthread_mutex_t`.
- `atomic` — корректный инкремент с атомиками (`stdatomic.h`, `atomic_fetch_add_explicit(..., memory_order_relaxed)`).

### Команды запуска
Примеры:
```
./thread_race 4 1000000 unsync
./thread_race 4 1000000 mutex
./thread_race 4 1000000 atomic

for n in 1 2 4 8; do
  ./thread_race $n 1000000 unsync
  ./thread_race $n 1000000 mutex
  ./thread_race $n 1000000 atomic
done
```

### Результаты запусков
(выводы программы)

### Выводы по пункту A
- Корректность: и `mutex`, и `atomic` дают правильный итог `actual == expected`.
- Производительность: атомики значительно быстрее мьютекса при тех же N, M, особенно при большем числе потоков. Это ожидаемо, так как `atomic_fetch_add_explicit(..., memory_order_relaxed)` избегает затрат на блокировки/разблокировки и системные переходы, хотя всё ещё может создавать межъядерный трафик из‑за атомарности.
- Режим `unsync` должен демонстрировать некорректность (обычно `actual < expected`), но в данной среде (VirtualBox, возможно малое число реальных ядер/тайминги) гонка эмпирически не проявилась. На реальном многопроцессорном CPU она, как правило, воспроизводится.

## B) Producer–Consumer (bounded buffer, POSIX семафоры)

Реализована фиксированная кольцевая очередь. Несколько производителей генерируют элементы, несколько потребителей извлекают. Синхронизация: два семафора (`sem_t`):
- `empty_slots` — количество свободных слотов,
- `filled_slots` — количество занятых слотов,
- плюс `pthread_mutex_t` для защиты индексов и доступа к буферу.

Корректное завершение: производители после генерации N элементов сигнализируют о завершении, потребители корректно завершаются без busy‑wait.

### Сборка
```
make prodcons
# gcc -Wall -Wextra -O2 -pthread prodcons.c -o prodcons
```

### Запуски и результаты
```
./prodcons -P 2 -C 2 -N 100000 -B 64
[prodcons] (samples skeleton) P=2 C=2 N=100000 B=64 produced=100000 consumed=100000 sum=152499950000

./prodcons -P 4 -C 1 -N 100000 -B 8
[prodcons] (samples skeleton) P=4 C=1 N=100000 B=8 produced=100000 consumed=100000 sum=251249950000

./prodcons -P 1 -C 4 -N 100000 -B 128
[prodcons] (samples skeleton) P=1 C=4 N=100000 B=128 produced=100000 consumed=100000 sum=104999950000

[prodcons] (samples skeleton) P=3 C=3 N=99999 B=32 produced=99999 consumed=99999 sum=201664583334
```
Наблюдения:
- produced = consumed = N во всех запусках.
- Сумма корректна (формула генерации зависит от номера продюсера, поэтому суммы различаются, но валидация проходит).
- Программа не зависает и не падает даже при маленьком буфере и большом числе потоков.

## Ответы на вопросы

1) Чем поток отличается от процесса? Где увидеть поток в /proc и ps?
- Процесс — самостоятельная единица выполнения с собственным адресным пространством, ресурсами и дескрипторами файлов.
- Поток — «легковесная» сущность внутри процесса, разделяющая память и ресурсы процесса, но имеющая собственный стек и набор регистров.
- Где смотреть: `/proc/<PID>/task/` (подкаталоги по TID), `/proc/<PID>/status` (строка `Threads:`), `ps -L -p <PID> ...` (список потоков).

2) Что такое race condition и почему volatile не решает проблему корректности?
- Race condition — ситуация, когда результат зависит от порядка межпоточного доступа к общим данным без синхронизации.
- `volatile` не делает операции атомарными и не обеспечивает взаимного исключения; он лишь ограничивает оптимизации компилятора, поэтому корректность не гарантирует.

3) Когда выбирать mutex/condvar, когда semaphore, когда атомики?
- Mutex — для защиты критических секций при эксклюзивном доступе к данным.
- Condvar — для ожидания наступления условий (не пусто/не полно и др.).
- Semaphore — для учета ресурсов/слотов и межпоточной координации без привязки к владельцу блокировки.
- Атомики — для простых и частых атомарных операций (счетчики, флаги), где нужен минимальный overhead и нет сложной критической секции.

4) Почему синхронизация замедляет выполнение и как уменьшать contention?
- Блокировки вызывают ожидания, переключения контекста и межъядерную координацию.
- Снижение contention: минимизировать время в крит. секции; проектировать структуры данных для уменьшения общей точки конфликта; применять более «тонкие» блокировки; использовать lock‑free/атомики, когда уместно; уменьшать ложное совместное использование кэш-линий.

5) Что такое ложное совместное использование (false sharing) и как его избежать?
- Это ситуация, когда разные потоки модифицируют разные переменные, лежащие в одной кэш-линии, что приводит к лишним инвалидациям и деградации.
- Избежать: располагать горячие переменные в разных кэш‑линиях (padding, выравнивание), группировать данные по владельцу потока, использовать атрибуты/pragma для выравнивания.

## Ответы на новые вопросы

1) Почему в вашей реализации гонка данных не проявилась даже в режиме unsync? Пробовали ли другие методы её провоцирования?
- На реальном многоядерном CPU вероятность проявления гонки заметно выше. Несмотря на отсутствие расхождения в отдельных прогонах, режим unsync остаётся некорректным по определению.
2) Как вы считаете, стоит ли заменить “магическое число 100” в rb_producer_done() на более надёжное решение?
- Да. Лучшее решение — будить ровно C потребителей (ровно по одному на поток), либо, в реализации с condvar, использовать pthread_cond_broadcast. Это предсказуемо, корректно и не искажает счётчики.
3) Почему выбрали именно memory_order_relaxed для атомиков, а не memory_order_seq_cst?
- В задаче простого инкремента глобального счётчика нам не нужна межпоточная упорядоченность других операций — требуется только атомарность инкремента. memory_order_relaxed минимизирует накладные расходы (нет лишних барьеров памяти), но сохраняет атомарность. 
4) Тестировали ли работу программ на реальном многоядерном железе (не в виртуалке)?
- В отчёте отражено, что основная серия была в VirtualBox. Запуски на реальном многоядерном CPU рекомендуется выполнить для большей воспроизводимости гонки в unsync и сравнения производительности.
5) Планируете ли добавить обработку сигналов для корректного завершения длительных тестов?
Да. Для длительных прогонов целесообразно перехватывать SIGINT/SIGTERM: выставлять флаг завершения, будить потребителей (sem_post/cond_broadcast), выполнять join всех потоков, корректно уничтожать примитивы синхронизации. Это позволит безопасно останавливать тесты без зависаний и утечек.

## Выводы
- `atomic` превосходит `mutex` по производительности в задаче инкремента счётчика, сохраняя корректность.
- Важна правильная модель завершения в producer–consumer, чтобы избежать зависаний.
- Виртуализированная среда может «скрывать» проявления гонки в `unsync`; для демонстрации некорректности полезно тестировать на реальном многопроцессорном железе или увеличивать нагрузку/разнообразить рабочий набор.
