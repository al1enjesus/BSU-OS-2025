# Лабораторная 3 — Потоки, синхронизация и гонки данных

### Цель
Продемонстрировать гонку при одновременном доступе нескольких потоков к разделяемой переменной без синхронизации и показать, как её можно устранить с помощью мьютекса.


## Вариант 1

## Часть A: Гонка данных и устранение (инкремент счётчика)

Использована программа `thread_race.c`, в которой:
- `N` потоков выполняют по `M` инкрементов глобального счётчика.
- Поддерживаются три режима:
  - `unsync` — без синхронизации (для демонстрации гонки),
  - `mutex` — с защитой через `pthread_mutex_t`,
  - `atomic` — через атомические операции (опционально).

Т.к. я использую Arch Linux и GCC 13+ счётчик в режиме `unsync` объявлен как `volatile`, чтобы запретить агрессивную оптимизацию цикла.

### Результаты замеров
Проведены эксперименты при общем числе инкрементов = 4 000 000 (ожидаемое значение). Использованы разные числа потоков.

| Потоков (N) | Режим     | Итераций на поток | Expected | Actual   | Время (мс) |
|-------------|-----------|-------------------|----------|----------|------------|
| 1           | unsync    | 4000000           | 4000000  | 4000000  | 5          |
| 2           | unsync    | 2000000           | 4000000  | 2845621  | 3          |
| 4           | unsync    | 1000000           | 4000000  | 1270730  | 3          |
| 8           | unsync    | 500000            | 4000000  | 982341   | 4          |
| 4           | mutex     | 1000000           | 4000000  | 4000000  | 61         |

окружение: Arch Linux, CPU — 8 ядер.

### Выводы
- В режиме без синхронизации (unsync) наблюдается сильная гонка данных: с ростом числа потоков доля потерянных инкрементов увеличивается (при 8 потоках потеряно более 75% операций).
- При одном потоке (N=1) гонки нет, так как отсутствует конкурентный доступ.
- Использование mutex полностью устраняет гонку: результат всегда точный.
- Однако синхронизация замедляет выполнение (примерно в 20 раз медленнее в данном эксперименте) из-за конкуренции за блокировку (contention).

Это подтверждает, что незащищённый доступ к разделяемым данным в многопоточной среде приводит к неопределённому поведению, и для обеспечения корректности обязательно требуется синхронизация.
-ИИ использовались для решения проблемм с arch и командами.

## Часть B: Producer–Consumer (bounded buffer, mutex+condvar)

### Цель
Реализовать фиксированную кольцевую очередь использованием кольцевого буфера фиксированного размера и синхронизации через мьютекс и условные переменные.

### Реализация
Дописана программа `prodcons.c`, в которой:
- Кольцевой буфер реализован на основе массива с индексами `head`, `tail` и счётчиком заполненности `count`.
- Синхронизация выполнена с помощью:
  - `pthread_mutex_t` — для защиты критической секции,
  - `pthread_cond_t not_full` — производители ожидают, пока в буфере появится место,
  - `pthread_cond_t not_empty` — потребители ожидают, пока в буфере появятся данные.
- Завершение потоков:
  - После завершения работы каждый производитель уменьшает счётчик активных производителей.
  - Когда все производители завершили работу (`producers_active == 0`), вызывается `pthread_cond_broadcast(&not_empty)`, чтобы разбудить всех ожидающих потребителей.
  - Потребители завершают работу, если буфер пуст и новых элементов больше не будет.

### Результаты
Программа запущена с параметрами: 2 производителя, 2 потребителя, 100 000 элементов, размер буфера — 64.

Вывод программы:
```
[prodcons] P=2 C=2 N=100000 B=64 produced=100000 consumed=100000 sum=152499950000
```


Результат правильный:
- Количество произведённых и потреблённых элементов совпадает (`100000 == 100000`),
- Сумма значений равна ожидаемой (рассчитана как сумма двух арифметических прогрессий),
- Программа завершается мгновенно, без зависаний.


### Вывод
Реализация корректно решает задачу:
- Обеспечена thread-safe работа с разделяемым буфером,
- Потоки эффективно ожидают нужных условий без излишней нагрузки на CPU,
- Завершение всех потоков происходит корректно и безопасно.  
ИИ использовались для тестирования и исправления ошибок.

## Вывод

В ходе выполнения лабораторной работы были достигнуты все поставленные цели:

- Успешно воспроизведена гонка данных (race condition) при несинхронизированном доступе к разделяемому счётчику. Показано, что без синхронизации результат работы многопоточной программы недетерминирован и некорректен.
- Продемонстрировал, что использование мьютекса (`pthread_mutex_t`) полностью устраняет гонку и гарантирует корректность результата, хотя и снижает производительность из-за contention.
- Реализована задача с использованием ограниченного буфера, мьютекса и условных переменных. Программа корректно завершает работу всех потоков без зависаний и потерь данных.
- Показано, как потоки отображаются в операционной системе Linux: через утилиту `ps -L`, файл `/proc/<PID>/status` и каталог `/proc/<PID>/task`. Подтверждено, что потоки в Linux — это легковесные задачи внутри одного процесса, имеющие общий PID, но уникальные TID.

Работа позволила на практике убедиться в важности синхронизации в многопоточных программах, освоить базовые примитивы (`pthread_mutex_t`, `pthread_cond_t`) и понять, как операционная система управляет потоками на низком уровне.

# ОТВЕТЫ НА ВОПРОСЫ
1.Чем поток отличается от процесса? Где увидеть поток в /proc и ps?
```
 Процесс имеет собственное адресное пространство и ресурсы, 
 а потоки разделяют память и файлы внутри одного процесса, 
 отличаясь своими идентификаторами потоков (TID); 
 потоки видны как подкаталоги в /proc/<PID>/task с 
 именами=TID и в выводе ps с режимом потоков, где у всех строк общий PID и разные TID.
```
2. Что такое race condition и почему volatile не решает проблему корректности?
```
 Race condition — это зависимость результата от порядка межпоточных доступов 
 к общим данным, вызывающая потерю обновлений и нарушение инвариантов; 
 volatile лишь ограничивает оптимизации компилятора, но не делает операции
 атомарными, не вводит взаимного исключения и не упорядочивает доступы между 
 потоками, поэтому гонка остаётся.
```
3. Когда выбирать mutex/condvar, когда semaphore, когда атомики?
```
 Mutex+condvar нужны для критических секций и ожидания логических условий 
 (например, буфер пуст/полон) с блокирующим сном; семафоры удобны как счётчики 
 ресурсов (empty/full) и для простых схем синхронизации потоков/процессов; атомики 
 подходят для простых счётчиков и флагов без длинных критических секций и без 
 необходимости блокирующего ожидания.
 ```
4. Почему синхронизация замедляет выполнение и как уменьшать contention?
```
Синхронизация замедляет из‑за конкуренции за блокировки, парковки/пробуждения, 
барьеров памяти и затрат на когерентность кеша; contention снижают сокращением 
времени в критической секции, шардированием данных (несколько независимых замков), 
батчингом операций, использованием атомик/lock‑free там, где возможно, и 
уменьшением частоты сигнализаций/пробуждений.
```
5.Что такое ложное совместное использование (false sharing) и как его избежать?
```
False sharing — когда разные потоки часто обновляют разные переменные на одной 
кеш‑линии, вызывая постоянную инвалидацию и падение производительности; избегают 
разнесением «горячих» данных по разным кеш‑линиям (выравнивание/padding), 
использованием per‑thread структур с последующей агрегацией и осмысленной 
группировкой полей по паттернам доступа.
```
