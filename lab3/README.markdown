## Шаги выполнения

### A) Гонка данных и устранение (mutex vs atomic)
Реализована программа `thread_race.py`, которая демонстрирует гонку данных в режиме `unsync` и устраняет её в режимах `mutex` и `atomic`. Программа принимает параметры: количество потоков (`threads`), количество итераций на поток (`iters`) и режим выполнения (`unsync`, `mutex`, `atomic`). Важное замечание: в режиме `unsync` и `mutex` счетчиком является элемент в списке. Это обусловлено тем, что при выполнении операции вроде counter += 1 для переменной типа int Python создаёт новый объект int с новым значением, а старая переменная перестаёт ссылаться на предыдущее значение. Это означает, что в многопоточной среде потоки могут работать с разными копиями значения, что может скрыть гонку данных или усложнить её воспроизведение. А при работе со списком все потоки обращаются к одному и тому же элементу в памяти.

- **Режим `unsync`**:
  - В стандартной версии CPython гонка потоков в режиме `unsync` не наблюдается, что очень странно. Ответом на этот вопрос является GIL (Global Interpreter Lock), который блокирует многопоточность в Python, из-за чего операции выполняются последовательно. Например:
    ```
    python3 thread_race.py 8 1000000 unsync
    [thread_race] Запуск с 8 потоками, 1000000 итерациями, режим=unsync
    mode=unsync threads=8 iters_per_thread=1000000 expected=8000000 actual=8000000 time_ms=422
    ```
  - Однако с версии Python 3.13 появилась возможность использовать Free-threaded CPython (без GIL), что и было сделано. В этом случае гонка данных проявляется, так как потоки могут одновременно изменять общий счётчик:
    ```
    python3.13t thread_race.py 8 1000000 unsync
    [thread_race] Запуск с 8 потоками, 1000000 итерациями, режим=unsync
    mode=unsync threads=8 iters_per_thread=1000000 expected=8000000 actual=1728321 time_ms=6347
    ```
    Здесь `actual` (1728321) значительно меньше `expected` (8000000), что демонстрирует гонку данных.

- **Режим `mutex`**: Используется `threading.Lock` для синхронизации доступа к счётчику. Результаты корректны:
  ```
  python3.13t thread_race.py 8 100000 mutex
  [thread_race] Запуск с 8 потоками, 100000 итерациями, режим=mutex
  mode=mutex threads=8 iters_per_thread=100000 expected=800000 actual=800000 time_ms=2029
  ```

- **Режим `atomic`**: 
  - В Python отсутствует встроенный механизм атомарного инкремента, аналогичный `stdatomic.h` в C. Для реализации атомарного инкремента была создана C-библиотека `libatomic.so` с функцией `atomic_increment`, которая использует `atomic_fetch_add_explicit` из `stdatomic.h`. Эта функция компилируется отдельно и вызывается из Python через `ctypes`. Код C-функции:
    ```c
    #include <stdatomic.h>
    int atomic_increment(int *ptr) {
        return atomic_fetch_add_explicit(ptr, 1, memory_order_seq_cst);
    }
    ```
  - Пример запуска:
    ```
    python3.13t thread_race.py 8 100000 atomic
    [thread_race] Запуск с 8 потоками, 100000 итерациями, режим=atomic
    mode=atomic threads=8 iters_per_thread=100000 expected=800000 actual=800000 time_ms=1980
    ```

**Замеры производительности** (N — количество потоков, M — итераций на поток):

| Режим   | N   | M       | Expected | Actual  | Время (ms) |
|---------|-----|---------|----------|---------|------------|
| unsync  | 8   | 1000000 | 8000000  | 1728321 | 6347       |
| unsync  | 16  | 1000000 | 16000000 | 1515366 | 35624      |
| mutex   | 4   | 100000  | 400000   | 400000  | 356        |
| mutex   | 8   | 100000  | 800000   | 800000  | 2029       |
| mutex   | 16  | 100000  | 1600000  | 1600000 | 5666       |
| atomic  | 4   | 100000  | 400000   | 400000  | 350        |
| atomic  | 8   | 100000  | 800000   | 800000  | 1980       |
| atomic  | 16  | 100000  | 1600000  | 1600000 | 5705       |

**Вывод**: 
- В стандартном Python с GIL гонка данных в режиме `unsync` отсутствует из-за последовательного выполнения, вызванного GIL. В Free-threaded CPython (без GIL) гонка данных проявляется, что подтверждает необходимость синхронизации.
- Режимы `mutex` и `atomic` устраняют гонку, обеспечивая корректный результат (`actual == expected`).
- Атомарные операции (`atomic`) работают быстрее, чем `mutex`, благодаря использованию низкоуровневых инструкций процессора через скомпилированную C-функцию, минимизируя накладные расходы на блокировку. Например, для 8 потоков и 100000 итераций `atomic` (1980 ms) быстрее, чем `mutex` (2029 ms).

### B) Producer–Consumer (bounded buffer, семафоры)
Реализована программа `prodcons.py`, использующая модель producer-consumer с кольцевым буфером фиксированного размера. Синхронизация реализована через два семафора (`free_slots` и `used_slots`) и мьютекс (`threading.Lock`) для защиты доступа к буферу.

- **Параметры**: 
  - `-P` — количество производителей.
  - `-C` — количество потребителей.
  - `-N` — общее количество элементов.
  - `-B` — размер буфера.
- **Проверка корректности**: Подсчитывается общее количество произведённых и потреблённых элементов, а также сумма значений для проверки целостности данных.
- **Пример запуска**:
  ```
  python3.14t prodcons.py -P 4 -C 4 -N 1000000 -B 64
  [prodcons] P=4 C=4 N=1000000 B=64 produced=1000000 consumed=1000000 sum=2624999500000 time_ms=9230
  ```
  Корректность подтверждена: `produced == consumed == 1000000`, сумма значений совпадает с ожидаемой.

**Замеры**:

| P | C | N       | B  | Produced | Consumed | Сумма          | Время (ms) |
|---|---|---------|----|----------|----------|----------------|------------|
| 4 | 4 | 1000000 | 64 | 1000000  | 1000000  | 2624999500000  | 9230       |
| 4 | 4 | 1000000 | 64 | 1000000  | 1000000  | 2624999500000  | 9418       |

**Вывод**: 
- Реализация с семафорами обеспечивает корректную синхронизацию: производители и потребители работают без гонок данных, а завершение потоков происходит корректно (без зависаний).
- Использование семафоров упрощает управление количеством свободных и занятых слотов в буфере, избегая busy-wait.
- Производительность зависит от размера буфера и числа потоков, но остаётся стабильной при повторных запусках.

## Ответы на вопросы

1. **Чем поток отличается от процесса? Где увидеть поток в /proc и ps?**
   - **Отличие**: Поток является единицей выполнения внутри процесса, разделяющей его адресное пространство, память и ресурсы, но имеющей собственный стек и регистры. Процесс представляет собой независимую программу с собственным адресным пространством. Потоки создаются и выполняются быстрее, так как не требуют выделения отдельной памяти.
   - **Где увидеть**: Потоки видны в `/proc/<PID>/task` (каждая папка — отдельный поток с TID), в `/proc/<PID>/status` (поле `Threads` показывает общее число потоков), и в выводе `ps -L` (колонка TID показывает идентификаторы потоков).

2. **Что такое race condition и почему volatile не решает проблему корректности?**
   - **Race condition**: Это ситуация, когда результат выполнения программы зависит от порядка выполнения потоков, одновременно изменяющих общие данные. Например, в `unsync` режиме с Free-threaded CPython два потока могут одновременно инкрементировать счётчик, что приводит к потере обновлений.
   - **Почему `volatile` не помогает**: Ключевое слово `volatile` в C/C++ указывает компилятору не оптимизировать доступ к переменной, но не гарантирует атомарность операций. Без синхронизации (например, мьютекса или атомарных операций) несколько потоков могут всё равно конфликтовать при доступе к общей переменной.

3. **Когда выбирать mutex/condvar, когда semaphore, когда атомики?**
   - **Mutex/condvar**: Используются для защиты критических секций (mutex) и синхронизации событий (condvar). Подходят для сложных ситуаций, где нужно управлять доступом к общим ресурсам или ожидать определённые условия (например, producer-consumer с condvar для сигналов `not_full`/`not_empty`).
   - **Semaphore**: Используются для управления количеством доступных ресурсов, таких как свободные или занятые слоты в буфере.
   - **Atomics**: Используются для простых операций (например, инкремент счётчика), когда нужна высокая производительность и нет сложной логики синхронизации.
   
4. **Почему синхронизация замедляет выполнение и как уменьшать contention?**
   - **Почему замедляет**: Синхронизация (мьютексы, семафоры) вводит накладные расходы из-за блокировки потоков, переключения контекста и ожидания освобождения ресурсов. Например, мьютекс заставляет потоки ждать, если другой поток уже удерживает блокировку.
   - **Как уменьшить contention**:
     - Использовать атомарные операции вместо мьютексов для простых операций.
     - Уменьшить размер критической секции, чтобы минимизировать время удержания блокировки.
     - Использовать разделение данных (например, локальные счётчики для каждого потока с последующим суммированием).
     - Применять более лёгкие примитивы, такие как семафоры, для управления ресурсами.

5. **Что такое ложное совместное использование (false sharing) и как его избежать?**
   - **False sharing**: Это ситуация, когда несколько потоков работают с разными переменными, находящимися в одной кэш-линии процессора (обычно 64 байта). Изменение одной переменной приводит к инвалидации кэш-линии, что вызывает ненужную синхронизацию кэша между ядрами.
   - **Как избежать**:
     - Размещать переменные, используемые разными потоками, в разных кэш-линиях.
     - Использовать локальные данные для каждого потока и объединять результаты в конце.
     - Избегать хранения часто изменяемых данных рядом в памяти.

## Выводы
- В стандартном Python с GIL гонка данных в режиме `unsync` отсутствует из-за последовательного выполнения, вызванного GIL. В Free-threaded CPython (без GIL) гонка данных проявляется, что подтверждает необходимость синхронизации.
- Режимы `mutex` и `atomic` устраняют гонку, обеспечивая корректный результат. Атомарные операции, реализованные через C-библиотеку `libatomic.so`, показывают небольшое преимущество в производительности по сравнению с `mutex`.
- Модель producer-consumer с семафорами успешно реализована, обеспечивая корректное завершение потоков и согласованность данных.
- Анализ `/proc` и `ps` позволяет увидеть потоки в системе, их TID, состояние и распределение по ядрам.
- Синхронизация увеличивает время выполнения, но её можно оптимизировать, используя атомарные операции или минимизируя критические секции.
