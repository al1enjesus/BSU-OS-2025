### Лабораторная 5 — модули ядра Linux
### 1. Окружение и безопасность

Работа выполнялась в изолированной среде:

- ОС: Ubuntu (внутри виртуальной машины / аналогичной изолированной среды).
- Установлены пакеты: `build-essential`, `linux-headers-$(uname -r)`, `kmod`.
- Все действия с модулями (`insmod`, `rmmod`, `dmesg`) выполнялись от `root`.

Причины использования VM:

- Код модулей выполняется в kernel space.
- Ошибка может привести к `kernel panic` и падению всей системы.
- Нет стандартной защиты памяти, как в user‑space.

---

#### 2. Цель работы

- Освоить базовые принципы разработки модулей ядра Linux.
- Научиться:
  - загружать и выгружать модули;
  - логировать события через `printk` и анализировать `dmesg`;
  - взаимодействовать с user‑space через `/proc`;
  - использовать параметры модулей;
  - получать системную статистику из ядра.

#### 3. Реализованные модули - Вариант 2

### 3.1. Задание A — Hello World модуль

**Файл:** `hello_module.c`  
**Назначение:** простейший модуль с приветствием, параметром и корректным логированием.

Основные моменты реализации:

- Метаданные:
  - `MODULE_LICENSE("GPL");`
  - `MODULE_AUTHOR("Anya");`
  - `MODULE_DESCRIPTION("Hello World Kernel Module");`
  - `MODULE_VERSION("1.0");`
- Параметр:
  - `message` (тип `charp`), права `0444`.
- При инициализации (`module_init`):
  - Если `message == NULL`, выводится:
    - `Hello from Anya module!`
  - Если `message` задан, выводится:
    - `Hello Module: <message>`
- При выгрузке (`module_exit`):
  - Всегда выводится:
    - `Goodbye from Anya module!`

**Подтверждение по логам:**

- Загрузка без параметра (файлы логов `hello_load_default.log` / `hello_unload.log`):

  - Приветствие:
    - `Hello from Anya module!`
  - При выгрузке:
    - `Goodbye from Anya module!`

- Загрузка с параметром `message="Custom_greeting_from_lab5"` (`hello_load_custom.log`):

  - `Hello Module: Custom_greeting_from_lab5`

### 3.2. Задание B — /proc файл с записью (`/proc/my_config`)

**Файл:** `proc_config.c`  
**Назначение:** реализовать файл `/proc/my_config` с чтением и записью строкового значения.

Основная логика:

- Создаётся файл `/proc/my_config` с правами `0644`.
- Внутренний буфер `config_buf`:
  - Максимальная длина: 256 символов.
  - Значение по умолчанию: `"default"`.
- При чтении:
  - Возвращается текущее значение буфера (однократная выдача за одно чтение).
- При записи:
  - Значение копируется из user‑space с ограничением по длине.
  - Удаляется завершающий `'\n'` от `echo`.
  - Логируется новое значение:
    - `proc_config: new value set: '<значение>'`.
- При выгрузке:
  - `/proc/my_config` удаляется и пишется соответствующее сообщение в лог.

**Фактическое поведение (логи):**

Из `proc_read_default.log`:

- Создание:

  - `proc_config: /proc/my_config created, default='default'`

- После записи нового значения:

  - `proc_config: new value set: 'new value'`

Ожидаемое взаимодействие:

- Первое чтение — `"default"`.
- После записи `"new value"` — чтение возвращает `"new value"`.

### 3.3. Задание C — /proc файл со статистикой системы (`/proc/sys_stats`)

**Файл:** `proc_sys_stats.c`  
**Назначение:** предоставить в `/proc/sys_stats` основную статистику системы.

Основная логика:

- Создаётся файл `/proc/sys_stats` с правами `0444`.
- При чтении:
  - Считается количество процессов с помощью `for_each_process`.
  - Получается информация о памяти через `si_meminfo`.
  - Считается uptime на основе `jiffies` и `jiffies_to_msecs`.
  - Формируется человекочитаемый вывод:

    ```text
    Processes: <N>
    Memory Used: <X> MB
    System Uptime: <T> seconds
    ```

- Данные формируются во временном буфере в kernel‑space (`kmalloc` / `kfree`) и копируются в user‑space через `copy_to_user`.
- При выгрузке:
  - `/proc/sys_stats` удаляется, в лог пишется сообщение о удалении.

**Фактический вывод (из `proc_sys_stats.log`):**

Примеры вызова `cat /proc/sys_stats`:

```text
Processes: 241
Memory Used: 2978 MB
System Uptime: 2285 seconds

Processes: 240
Memory Used: 2981 MB
System Uptime: 2322 seconds

Processes: 240
Memory Used: 2979 MB
System Uptime: 2328 seconds
```

Логи создания и удаления:

```text
proc_sys_stats: /proc/sys_stats created
proc_sys_stats: /proc/sys_stats removed
```

### 4. Ответы на вопросы

#### Базовые понятия

1. **Что такое модуль ядра и зачем он нужен?**  
   Загружаемый в runtime фрагмент кода ядра (драйвер/функциональность), который можно добавить/убрать без перекомпиляции и перезагрузки ядра.

2. **Чем отличается kernel-space от user-space?**  
   - Kernel‑space: привилегированный режим, полный доступ к ресурсам, ошибка → `kernel panic`.  
   - User‑space: ограниченный доступ, падение затрагивает только процесс.

3. **Что произойдёт, если в модуле обратиться к NULL указателю?**  
   Будет обращение к недопустимой памяти → аварийное исключение → почти всегда `kernel panic`.

4. **Почему нельзя использовать printf() в модуле ядра?**  
   В ядре нет стандартной libc; используется `printk`, который пишет в буфер логов ядра.

5. **Что такое kernel panic и как его избежать?**  
   Критическая ошибка в ядре, после которой система останавливается. Избегать — аккуратная работа с указателями, памятью, проверка кодов ошибок, отсутствие небезопасных операций.

#### Жизненный цикл модуля

6. **Какие функции вызываются при insmod и rmmod?**  
   - `insmod` → функция, зарегистрированная `module_init(...)`.  
   - `rmmod` → функция, зарегистрированная `module_exit(...)`.

7. **Что должна делать функция module_exit()?**  
   Освобождать все ресурсы, выделенные в `module_init`: память, `proc`‑записи, устройства и т.д.

8. **Что происходит, если module_init() возвращает ошибку?**  
   Модуль не загружается, `module_exit()` вызван не будет, ответственность за освобождение уже выделенных ресурсов до `return` лежит на `module_init`.

9. **Можно ли выгрузить модуль, если он используется?**  
   Нет, `rmmod` вернёт ошибку «Module is in use», пока есть ссылки/открытые дескрипторы.

#### Логирование и отладка

10. **Чем printk() отличается от printf()?**  
    `printk` пишет в kernel log buffer с уровнями важности, `printf` — в stdout в user‑space.

11. **Какие уровни логирования существуют в ядре?**  
    От `KERN_EMERG` (0) до `KERN_DEBUG` (7), включая `KERN_ERR`, `KERN_WARNING`, `KERN_INFO` и др.

12. **Как посмотреть логи модуля?**  
    `dmesg`, `dmesg | grep <имя_модуля>`, `journalctl -k`.

13. **Что означает "tainted kernel"?**  
    Ядро помечено «испорченным» — например, из‑за проприетарного или некорректно лицензированного модуля; разработчики ядра обычно не поддерживают такие конфигурации.

#### Память

14. **Чем kmalloc() отличается от malloc()?**  
    `kmalloc` — внутренняя функция ядра, выделяет физически непрерывную память в kernel‑space, без поддержки swap; `malloc` — из libc для user‑space.

15. **Что такое флаги GFP и зачем они нужны?**  
    Флаги аллокатора (`GFP_KERNEL`, `GFP_ATOMIC` и др.) описывают контекст и допустимое поведение при выделении (можно ли спать, и т.п.).

16. **Что произойдёт, если не освободить память в module_exit()?**  
    Утечка памяти в ядре — память не будет возвращена до перезагрузки системы.

17. **Почему нельзя использовать user-space указатели напрямую в ядре?**  
    Адреса в user‑space недействительны в контексте ядра и могут быть поддельными → нужно использовать `copy_to_user` / `copy_from_user`, которые проверяют и безопасно копируют данные.

#### Взаимодействие с user-space

18. **Что такое /proc и для чего он используется?**  
    Виртуальная файловая система procfs для предоставления информации ядра/процессов и простого интерфейса взаимодействия.

19. **Что такое /sys (sysfs) и чем отличается от procfs?**  
    Sysfs — иерархия атрибутов устройств/драйверов (один файл — одно значение), больше для конфигурации; `/proc` исторически используется для разнородной информации.

20. **Зачем нужны функции copy_to_user() и copy_from_user()?**  
    Для безопасного копирования данных между kernel‑space и user‑space с проверкой корректности адресов.

21. **Что такое character device и как он работает?**  
    Символьное устройство — интерфейс к драйверу, работающий с потоком байтов через операции `open/read/write/ioctl` над файлом в `/dev`.

#### Параметры и метаданные

22. **Как передать параметры модулю при загрузке?**  
    Через `insmod mymod.ko name=value`, при этом в коде используется `module_param(...)` / `module_param_array(...)`.

23. **Зачем нужен MODULE_LICENSE()?**  
    Указывает лицензию модуля; позволяет ядру корректно отмечать taint‑статус и открывает доступ к некоторым GPL‑только символам.

24. **Что произойдёт, если не указать лицензию?**  
    Ядро пометит модуль как tainted (несовместимая/неизвестная лицензия), и некоторые функции ядра могут быть недоступны.

#### Безопасность

25. **Какие основные правила безопасного кода в ядре?**  
    - Проверять все возвращаемые значения.  
    - Освобождать ресурсы.  
    - Не обращаться к user‑space без `copy_*_user`.  
    - Не использовать стандартную libc, не использовать float.  
    - Избегать бесконечных циклов и долгих блокировок.

26. **Можно ли использовать бесконечный цикл в модуле?**  
    В общем случае нельзя (без выхода/ожидания) — может заблокировать ядро и систему.

27. **Почему в ядре нет FPU операций?**  
    Использование FPU дорого и требует сложного сохранения контекста; ядро в общем случае избегает float и использует целочисленную арифметику/фиксированную точку.

28. **Что делать, если модуль вызвал kernel panic?**  
    Перезагрузить систему (в VM — откатиться к snapshot), проанализировать логи (`dmesg`, журналы) и исправить код, убрав опасные операции.

#### Практические вопросы

29. **Как узнать, какие модули загружены в системе?**  
    `lsmod`, `cat /proc/modules`.

30. **Как получить информацию о модуле (версия, параметры)?**  
    `modinfo mymodule.ko` (или `modinfo mymodule` если установлен), а также через `/sys/module/<имя>/` и `/sys/module/<имя>/parameters/`.

 **Как использовался ИИ при решении лабораторной?**
   Чтобы проанализировать и понять ошибки, которые я допускала при выполнении команд.
