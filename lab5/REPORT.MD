## 3. Краткое описание реализованных модулей

### 3.1. Модуль `hello_module.ko`

**Назначение:**  
Демонстрация базовой структуры модуля ядра и механизма передачи параметров при загрузке.

**Что делает:**

- При загрузке модуля (функция инициализации) в системный журнал выводится строка с приветствием. Текст сообщения задаётся параметром модуля `message`.
- При выгрузке модуля (функция завершения) в журнал выводится прощальное сообщение.
- Параметр `message` объявлен через `module_param` и может задаваться при загрузке через `insmod`.

**Как запускать:**

```bash
cd ~/os/lab5/src

# Загрузка с параметром
sudo insmod hello_module.ko message="Hello_from_VM"

# Проверка загрузки
lsmod | grep hello_module

# Просмотр журнала ядра
sudo dmesg | tail -n 10

# Выгрузка модуля
sudo rmmod hello_module
sudo dmesg | tail -n 10
```

В журнале ядра фиксировались сообщения вида:

```text
lab5: Hello_from_VM
lab5: Goodbye from Artem module!
```

---

### 3.2. Модуль `my_config.ko` и файл `/proc/my_config`

**Назначение:**  
Демонстрация двустороннего обмена строковыми данными между ядром и пространством пользователя через `/proc`.

**Что делает:**

- При загрузке модуля создаётся запись `/proc/my_config` с правами `0666`.
- В модуле хранится строковый буфер фиксированного размера, по умолчанию — значение `"default"`.
- При чтении `/proc/my_config` возвращается текущее значение буфера (строка).
- При записи в `/proc/my_config` новое значение копируется в буфер (с обрезкой по длине), а в `dmesg` выводится сообщение о смене значения.

**Как запускать:**

```bash
cd ~/os/lab5/src

# Загрузка модуля
sudo insmod my_config.ko
lsmod | grep my_config

# Чтение значения по умолчанию
cat /proc/my_config

# Изменение значения
echo "new value from VM" | sudo tee /proc/my_config > /dev/null

# Повторное чтение
cat /proc/my_config

# Логи ядра
sudo dmesg | tail -n 10

# Выгрузка
sudo rmmod my_config
sudo dmesg | tail -n 10
```

### 3.3. Модуль `sys_stats.ko` и файл `/proc/sys_stats`

**Назначение:**  
Вывод краткой системной статистики из ядра в пространство пользователя через `/proc`.

**Что делает:**

- При загрузке модуля создаётся файл `/proc/sys_stats` (только для чтения).
- При чтении файла модуль:
  - подсчитывает количество активных процессов;
  - оценивает объём используемой памяти в МБ;
  - рассчитывает время работы системы (uptime) в секундах.
- Формирует текстовый отчёт из трёх строк:
  - `Processes: <число>`
  - `Memory Used: <MB>`
  - `System Uptime: <секунды>`

**Как запускать:**

```bash
cd ~/os/lab5/src

sudo insmod sys_stats.ko
lsmod | grep sys_stats

cat /proc/sys_stats
cat /proc/sys_stats > sys_stats_output.txt

sudo dmesg | tail -n 10

sudo rmmod sys_stats
sudo dmesg | tail -n 10
```

## 6. Возникшие проблемы и их решения

### 6.1. Ошибка сборки Makefile: `missing separator`

- **Симптом:**

  ```text
  Makefile:7: *** missing separator.  Stop.
  ```

- **Причина:**  
  В строках с командами (`all:` и `clean:`) вместо символа **TAB** были использованы пробелы. Утилита `make` требует, чтобы команды в рецептах начинались строго с TAB.

- **Решение:**  
  Makefile был полностью пересоздан так, чтобы перед `$(MAKE)` использовался символ TAB. После исправления ошибка исчезла, модули успешно собираются.

---

### 6.2. Ошибка доступа к `dmesg`: `Operation not permitted`

- **Симптом:**

  ```bash
  dmesg | tail -n 20
  dmesg: read kernel buffer failed: Operation not permitted
  ```

- **Причина:**  
  В системе включён параметр `kernel.dmesg_restrict`, который запрещает непривилегированным пользователям читать буфер ядра.

- **Решение:**  
  Для просмотра журнала используется команда с `sudo`:

  ```bash
  sudo dmesg | tail -n 20
  ```

---

### 6.3. Неверная передача параметров модулю `hello_module`

- **Симптом:**

  В журнале появлялись строки:

  ```text
  hello_module: unknown parameter 'from' ignored
  hello_module: unknown parameter 'VM!' ignored
  lab5: Hello
  ```

- **Причина:**  
  Модуль загружался командой:

  ```bash
  sudo insmod hello_module.ko message=Hello from VM!
  ```

  Shell разбивал это на три аргумента: `message=Hello`, `from`, `VM!`. Ядро воспринимало `from` и `VM!` как несуществующие параметры модуля и игнорировало их.

- **Решение:**  

  Использовать кавычки, чтобы значение параметра воспринималось как одно целое:

  ```bash
  sudo insmod hello_module.ko message="Hello_from_VM"
  ```

## 8. Ответы на теоретические вопросы

### Логирование и отладка: базовые понятия

**1. Что такое модуль ядра и зачем он нужен?**  
Модуль ядра — это загружаемый в уже работающее ядро объектный файл, который расширяет его функциональность (драйверы устройств, файловые системы, сетевые протоколы и т.п.) без пересборки и перезагрузки ядра.

**2. Чем отличается kernel-space от user-space?**  
Kernel-space — привилегированное пространство, где выполняется код ядра с полным доступом к памяти и устройствам.  
User-space — пространство пользовательских процессов с ограниченными правами; доступ к ядру осуществляется только через системные вызовы, ошибки обычно «убивают» только процесс, а не всю систему.

**3. Что произойдёт, если в модуле обратиться к NULL указателю?**  
В привилегированном режиме это приведёт к исключению (page fault) в ядре, что может вызвать сообщение `Oops` или `kernel panic` и сделать систему нестабильной или полностью неработоспособной.

**4. Почему нельзя использовать `printf()` в модуле ядра?**  
`printf()` — часть пользовательской библиотеки `libc`, завязанной на stdout процесса. В ядре нет ни `libc`, ни процессов в привычном смысле. Для вывода сообщений используется специальная функция `printk()`, пишущая в буфер логов ядра.

**5. Что такое `kernel panic` и как его избежать?**  
`Kernel panic` — критическая ошибка ядра, при которой оно считает продолжение работы опасным и останавливает систему.  
Избежать помогают: проверка указателей и кодов возврата, аккуратная работа с памятью и синхронизацией, запрет использования недопустимых контекстов (сон в прерывании и т.п.), тестирование модулей в VM.

### Жизненный цикл модуля

**6. Какие функции вызываются при `insmod` и `rmmod`?**  
При `insmod` ядро вызывает функцию, зарегистрированную через `module_init()`.  
При `rmmod` — функцию, зарегистрированную через `module_exit()`.

**7. Что должна делать функция `module_exit()`?**  
Освобождать все ресурсы, захваченные модулем: память, таймеры, потоки, записи в `/proc` и `/sys`, зарегистрированные устройства и т.п., чтобы после выгрузки система была в «чистом» состоянии.

**8. Что происходит, если `module_init()` возвращает ошибку?**  
Загрузка модуля считается неуспешной: модуль не появится в списке `lsmod`, а `module_exit()` вызван не будет. Всё, что было выделено до возврата ошибки, модуль должен очистить самостоятельно внутри `init`-функции.

**9. Можно ли выгрузить модуль, если он используется?**  
В нормальном режиме — нет. У модуля есть счётчик ссылок (usage count); если он не ноль, `rmmod` откажет с ошибкой «module in use». Форсированная выгрузка потенциально приводит к краху системы.

**10. Чем `printk()` отличается от `printf()`?**  
`printf()` — функция user-space, пишет в stdout процесса.  
`printk()` — функция ядра, пишет в кольцевой буфер логов ядра, поддерживает уровни важности сообщений и доступна только в kernel-space.

**11. Какие уровни логирования существуют в ядре?**  
Основные уровни (префиксы для `printk`):
- `KERN_EMERG` — система неработоспособна;
- `KERN_ALERT` — критическая ситуация;
- `KERN_CRIT` — критические ошибки;
- `KERN_ERR` — ошибки;
- `KERN_WARNING` — предупреждения;
- `KERN_NOTICE` — важная нормальная информация;
- `KERN_INFO` — информационные сообщения;
- `KERN_DEBUG` — отладочная информация.

**12. Как посмотреть логи модуля?**  
Через:
- `dmesg` / `sudo dmesg | grep <имя_модуля>`;
- `journalctl -k` (в системах с systemd);
- просмотр логов `/var/log/kern.log` или `/var/log/syslog` (зависит от дистрибутива).

**13. Что означает «tainted kernel»?**  
Это признак, что ядро работает в «запятнанном» состоянии: были загружены проприетарные или внешние (out-of-tree) модули, произошёл `Oops`, включены нестандартные настройки и т.п. Это важно при анализе багов: разработчики видят, что система не «чистая».

---

### Память

**14. Чем `kmalloc()` отличается от `malloc()`?**  
`malloc()` — пользовательская функция из `libc`, выделяет память в адресном пространстве процесса.  
`kmalloc()` — функция ядра, выделяет память в kernel-space, учитывает флаги GFP и требования к контексту (можно ли спать, откуда брать память, нужен ли непрерывный блок и т.д.).

**15. Что такое флаги GFP и зачем они нужны?**  
Флаги GFP (`GFP_KERNEL`, `GFP_ATOMIC`, `GFP_NOWAIT` и др.) описывают условия выделения памяти: можно ли блокироваться, из какой зоны памяти выделять, каков приоритет.  
Например, `GFP_KERNEL` — обычные выделения, допускающие сон; `GFP_ATOMIC` используется в атомарном контексте (прерывания, spinlock), где спать нельзя.

**16. Что произойдёт, если не освободить память в `module_exit()`?**  
Память останется выделенной до перезагрузки системы — это утечка памяти в ядре. При многократной загрузке/выгрузке модуля утечки могут накопиться и привести к нехватке RAM и нестабильности системы.

**17. Почему нельзя использовать user-space указатели напрямую в ядре?**  
Потому что адресное пространство пользователя и ядра различаются, указатель может быть невалидным или не иметь нужных прав доступа. Прямое разыменование пользовательского указателя в ядре может вызвать page fault и крах системы. Для обмена данными используются `copy_to_user()` и `copy_from_user()`.

### Взаимодействие с user-space

**18. Что такое `/proc` и для чего он используется?**  
`/proc` — виртуальная (псевдо-) файловая система, формируемая ядром в памяти. Предоставляет информацию о процессах и состоянии системы (например, `/proc/meminfo`, `/proc/cpuinfo`, `/proc/<pid>`) и может использоваться для настройки параметров. В лабораторной работе через неё реализованы `/proc/my_config` и `/proc/sys_stats`.

**19. Что такое `/sys` (sysfs) и чем он отличается от procfs?**  
`/sys` (sysfs) — виртуальная файловая система, отражающая структуру объектов ядра: устройства, драйверы, шины, kobject’ы. Она более строго структурирована и в основном используется для представления и настройки устройств.  
`/proc` — больше про процессы и состояние ядра, `/sys` — про структуру и атрибуты объектов ядра и оборудования.

**20. Зачем нужны функции `copy_to_user()` и `copy_from_user()`?**  
Они обеспечивают безопасное копирование данных между kernel-space и user-space:
- `copy_to_user()` копирует данные из ядра в пользовательскую память;
- `copy_from_user()` — из пользовательской памяти в ядро.  
Обе функции проверяют доступность адресов и защищают ядро от падения из-за неверных указателей.

**21. Что такое character device и как он работает?**  
Символьное устройство (character device) — устройство, к которому обращаются как к потоку байтов (например, `/dev/tty`, `/dev/null`).  
Драйвер символьного устройства регистрирует набор операций (`file_operations`: `open`, `read`, `write`, `release`, `ioctl` и т.д.), а ядро через VFS вызывает эти функции при обращении к соответствующему файловому дескриптору.

### Параметры и метаданные

**22. Как передать параметры модулю при загрузке?**  
Параметры задаются при `insmod`/`modprobe` как `имя=значение`, а в коде объявляются через макросы `module_param()` и т.п. Например:

```bash
sudo insmod hello_module.ko message="Hello_from_VM"
```

**23. Зачем нужен `MODULE_LICENSE()`?**  
Определяет лицензию модуля (например, `"GPL"`). От неё зависит:
- будет ли ядро считать модуль GPL-совместимым;
- будет ли доступ к символам, экспортированным как `EXPORT_SYMBOL_GPL`;
- будет ли ядро помечено как tainted из-за проприетарного модуля.

**24. Что произойдёт, если не указать лицензию?**  
Ядро воспримет модуль как проприетарный: в логах появится предупреждение, ядро будет помечено как tainted, а модулю могут быть недоступны GPL-символы.

### Безопасность

**25. Какие основные правила безопасного кода в ядре?**  

- Проверять указатели и коды возврата всех системных вызовов/функций ядра.
- Не доверять данным из user-space, всегда валидировать их.
- Не использовать большие буферы на стеке.
- Корректно использовать механизмы синхронизации (mutex, spinlock и т.п.).
- Освобождать все ресурсы при ошибках и в `module_exit()`.
- Избегать busy-wait и бесконечных циклов без сна/планирования.
- Тестировать модуль сначала в виртуальной машине.

**26. Можно ли использовать бесконечный цикл в модуле?**  
Безусловный бесконечный цикл без вызовов `schedule()`/`msleep()` и т.п. недопустим — он может «повесить» систему. Допустимо использовать циклы, которые либо ограничены по времени, либо периодически отдают управление планировщику.

**27. Почему в ядре нет FPU операций?**  
Использование FPU требует сохранения и восстановления дополнительного состояния, что дорого и усложняет контекст переключения. Во многих контекстах ядра использование FPU запрещено или нежелательно. Поэтому вычисления с плавающей точкой в ядре либо не используются, либо применяются только через специальные механизмы.

**28. Что делать, если модуль вызвал `kernel panic`?**  

- Перезагрузить систему (часто это единственный вариант восстановления).
- Изучить логи (`dmesg`, `journalctl -k`) и stack trace.
- Воспроизвести проблему в виртуальной машине.
- Добавить `printk()` и поэтапную отладку, чтобы локализовать ошибочный участок.
- По возможности минимизировать воздействие модуля на «живые» системы.

### Практические вопросы

**29. Как узнать, какие модули загружены в системе?**  

```bash
lsmod
# или
cat /proc/modules
```

**30. Как получить информацию о модуле (версия, параметры)?**  

```bash
modinfo module.ko
# или по имени, если модуль установлен в системе:
modinfo <module_name>
```

Команда `modinfo` показывает имя, версию, автора, лицензию, описание и список параметров модуля.
