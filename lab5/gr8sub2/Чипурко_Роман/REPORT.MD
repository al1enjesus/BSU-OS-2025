# Лабораторная работа 5

## Цели: 

Реализовать и изучить простые модули ядра Linux:
- создать Hello-World модуль с параметром message;

## Среда выполнения:

- Работа выполнялась в VM

## Шаги выполнения: 

### Задание А:

Реализованный код и вспомогательные файлы находятся в `src/`:
- `src/hello_module.c` — исходный код модуля (см. краткое содержание ниже).
- `src/Makefile` — Makefile для сборки модуля.

Реализация (`hello_module.c`):

 1. Используется `printk(KERN_INFO ...)` для вывода при загрузке и выгрузке модуля.

 2. Параметр `message` объявлен через `module_param(message, charp, 0444)`; описание через `MODULE_PARM_DESC`.

 3. Стандартные метаданные: `MODULE_LICENSE("GPL")`, `MODULE_AUTHOR("Чипурко Роман")`, `MODULE_DESCRIPTION(...)`, `MODULE_VERSION("1.0")`.

Логика: при init печатается message (или дефолт), при exit печатается сообщение о выгрузке с последним message.

#### Запуск

1. Перед запуском я решил выполнить очисту dmesg:

```bash
sudo dmesg -C
```
2. Затем выполнил загрузку модуля (без параметра):

```bash
sudo insmod hello_module.ko
```
3. Проверил, что модуль загрузился:

```bash
lsmod | grep hello
```

Вывод:

```bash
hello_module           12288  0
```

4. Просмотрим последние сообщения ядра (в этом окружении я использовал `journalctl`):

```bash
sudo journalctl -k | tail -20
```

Вывод можно увидеть в `screenshots/dmesg_after_insmod_1`

5. Выполнил выгрузку модуля:

```bash
sudo rmmod hello_module
sudo journalctl -k | tail -20
```

Вывод можно увидеть в `screenshots/dmesg_after_insmod_2`

6. И выполним загрузку с параметром:

```bash
sudo modprobe hello_module message="Hello from Ivan Ivanov module!"
sudo journalctl -k | tail -10
```

Вывод можно увидеть в `screenshots/dmesg_after_insmod_3`

Примичание: здесь я использовал `modprobe`, потому что в отличие от `insmod` он корректно обрабатывает параметры модуля, содержащие пробелы. Команда `insmod` передаёт параметры ядру "как есть", и строка вида `message="Hello from Ivan Ivanov"` разбивается на несколько отдельных токенов, что приводит к ошибкам вида `unknown parameter`. `modprobe` же использует конфигурацию модулей из `/lib/modules/$(uname -r)/` и умеет правильно передавать строковые параметры, включая параметры с пробелами, благодаря чему модуль получает значение аргумента полностью и без искажений.

### Задание B:

Реализован модуль ядра, создающий файл /proc/my_config. По умолчанию содержит строку "default", поддерживает запись строк (максимум 256 байт), чтение возвращает текущее значение, файл создаётся с правами 0666.

#### Запуск

1. Перед запуском я решил выполнить очисту dmesg:
```bash
sudo dmesg -C
```

2. Загрузка модуля `/proc/my_config`

```bash
sudo insmod proc_my_config.ko
```

Файл `/proc/my_config` создаётся сразу же при инициализации.

3. Проверка, что файл появился

```bash
ls -l /proc/my_config
```

Ожидаемые права: **-rw-rw-rw-**, владелец — root.

4. Чтение значения по умолчанию

```bash
cat /proc/my_config
```

Вывод:
```bash
default
```

5. Запись нового значения в `/proc/my_config`

```bash
echo "some text" > /proc/my_config
```

В моем случае файл доступен без sudo, т.к. права 0666.

6. Проверка, что значение изменилось

```bash
cat /proc/my_config
```

Вывод:
```bash
some text
```

7. Просмотр сообщений ядра

Чтобы убедиться, что модуль создал файл корректно:

```bash
sudo journalctl -k | tail -5
```

В выводе должно быть:
```bash
/proc/my_config created with default="default"
```

Что и видно на скриншоте `screenshots/proc_my_config_1`

8. Выгрузка модуля

Когда тестирование завершено:

```bash
sudo rmmod proc_my_config
sudo journalctl -k | tail -5
```

В выводе появится сообщение:

```bash
/proc/my_config removed
```

Что и видно на скриншоте `screenshots/proc_my_config_2`

### Вывод

Представленные выше выводы, а также скриншоты тестов, подтверждают корректную работу: файл создан с правами 0666, значение по умолчанию — default, запись нового значения срабатывает, чтение возвращает ожидаемое значение. В логе ядра присутствует сообщение о создании `/proc/my_config` и об успешном удалении.

### Задание C:

Создан /proc-файл `/proc/sys_stats`, который при чтении выводит: количество запущенных процессов, используемую память (приблизительно, в MB), время работы системы (uptime) в секундах.

#### Запуск

1. Загрузка модуля:
```bash
sudo insmod sys_stats.ko
```

2. Проверка наличия /proc-файла:

```bash
ls -l /proc/sys_stats
```

Вывод:
```bash
-r--r--r-- 1 root root 0 ноя 24 21:26 /proc/sys_stats
```

3. Чтение статистики:

```bash
cat /proc/sys_stats
```

Вывод:
```bash
Processes: 274
Memory Used: 3506 MB
System Uptime: 40541 seconds
```

4. Проверка логов ядра:

```bash
sudo journalctl -k | tail -10
```

Скриншот предоставлен в `screenshots/sys_stats_1`

5. Выгрузка модуля: 

```bash
sudo rmmod sys_stats
sudo journalctl -k | tail -10
```

Скриншот предоставлен в `screenshots/sys_stats_2`

### Вывод

- Processes: 274 — подсчёт получен через `for_each_process()`; для больших систем обход процесса O(N), но для лабораторной это приемлемо.
- Memory Used: 3506 MB — приближённая оценка: делаем `(totalram - freeram - bufferram) * PAGE_SIZE` и переводим в MB. Такой метод даёт грубую оценку используемой оперативной памяти.
- System Uptime: 40541 seconds — получено через `jiffies_to_msecs(jiffies) / 1000`. Значение — целые секунды с момента загрузки.
- В логах видно сообщение о создании `/proc/sys_stats` — это подтверждение успешного init модуля.

### Выводы по лабораторной работе

- Реализованы и успешно протестированы требуемые модули (`Hello`, `/proc/my_config`, `/proc/sys_stats`).
- Продемонстрировано взаимодействие `kernel-space` <-> `user-space` через `printk`, `/proc`, `proc_create`, `copy_to_user/copy_from_user` и `seq_file`.
- Показана осторожность работы с ресурсами: выделение/освобождение памяти (`kmalloc/kfree`), регистрация/удаление `proc entries`.
- Не произошло kernel panic — все тесты выполнены в VM и корректно завершились.

## Ответы на вопросы: 

1. Модуль ядра — компилируемый объект, который может динамически загружаться/выгружаться в ядро. Позволяет добавлять драйверы и функциональность без перекомпиляции всего ядра и без перезагрузки системы.

2. Kernel-space — привилегированное пространство, где выполняется ядро и модули, с полным доступом к памяти и оборудованию. User-space — непривилегированное пространство процессов с ограничениями по доступу; ошибки в user-space не рушат всю систему.

3. Разыменование NULL в kernel-space обычно вызывает oops и может привести к kernel panic; по меньшей мере вызовет аварийную ошибку ядра и нестабильность системы.

4. printf() — функция user-space libc; в kernel-space её нет. Для логирования используется printk() и прочие kernel API.

5. Kernel panic — фатальная ошибка ядра, приводящая к остановке или перезагрузке. Избежать можно: проверять указатели, проверять возвращаемые значения, не выполнять FPU операции, избегать бесконечных блокирующих циклов, тестировать в VM.

6. При insmod вызывается функция, зарегистрированная через module_init() (init). При rmmod — функция, зарегистрированная через module_exit() (exit).

7. Освобождать все ресурсы: удалять proc/sysfs entries, освобождать память (kfree), удалять cdev, deregister major/minor, удалять созданные устройства/классы.

8. Модуль не загружается, module_exit() не вызывается автоматически — нужно вручную освободить ресурсы, выделенные до ошибки внутри init.

9. Нет — rmmod выдаст ошибку Module ... is in use. Нужно закрыть все файловые дескрипторы и процессы, использующие модуль.

10. printk() выводит в kernel log buffer и имеет уровни логирования (KERN_INFO, KERN_ERR и т. д.), не зависит от libc и работает в ядре.

11. KERN_EMERG, KERN_ALERT, KERN_CRIT, KERN_ERR, KERN_WARNING, KERN_NOTICE, KERN_INFO, KERN_DEBUG.

12. dmesg | tail или journalctl -k (systemd). Для живого просмотра dmesg -w или journalctl -k -f.

13. Ядро отмечено (tainted), если загружены непривилегированные или проприетарные модули, или произошли определённые ошибки — это пометка о потенциально некорректном состоянии ядра.

14. kmalloc() — kernel allocator, работает в kernel-space с флагами GFP_*; malloc() — user-space libc. kmalloc() может требовать особых флагов (GFP_ATOMIC/GFP_KERNEL).

15. GFP (Get Free Pages) указывают поведение аллокатора: может ли спать, допустимо ли ожидание IO, использоваться ли в прерываниях (GFP_ATOMIC), и т.д.

16. Утечка памяти в ядре — память не вернётся до перезагрузки; возможно накопление утечек и деградация системы.

17. Указатели user-space не валидны в контексте ядра; нужно использовать copy_from_user/copy_to_user, потому что пользовательская память может быть не доступна или свапирована.

18. Procfs — виртуальная файловая система для экспорта информации о системе/процессах из ядра в user-space. Удобна для мониторинга и управления.

19. Sysfs — интерфейс для атрибутов устройств и их иерархии, ориентирован на конфигурацию и представление устройства/драйвера. /proc — более общее представление состояния системы.

20. Для безопасного копирования данных между kernel-space и user-space, с проверкой доступа и корректностью адресов.

21. Character device — устройство, доступное как поток байтов (файловый интерфейс /dev/...). Драйвер реализует open, read, write, release, и регистрируется с major/minor через alloc_chrdev_region, cdev_add.

22. Через insmod module.ko param=value или modprobe modulename param=value. Параметры объявляются через module_param.

23. Указывает лицензию модуля; если не указать GPL-подобную, ядро пометит модуль tainted и ограничит доступ к некоторым символам.

24. Ядро пометит модуль как tainted и возможно откажет в предоставлении некоторых API; это лог безопасности.

25. Проверять возвращаемые значения, освобождать ресурсы, не разыменовывать user-пointers напрямую, не блокировать долго в контексте с высокой приоритетностью, избегать FPU и неиспользуемых указателей.

26. Нет, бесконечный блокирующий цикл в kernel-space приведёт к зависанию/kernel panic; в реальном коде используют worker-queues, tasklets, timers.

27. Поскольку ядро не сохраняет/восстанавливает FPU-контекст по умолчанию, использование FPU в ядре может нарушить контекст процесса; поэтому FPU операции запрещены.

28. Перезагрузить VM, восстановить snapshot, проанализировать dmesg/логи, исправить код, тестировать по шагам. Всегда работать в изолированной VM.

29. lsmod или cat /proc/modules.

30. modinfo module.ko или ls /sys/module/<module>/parameters и cat /sys/module/<module>/parameters/<param>.
