### Реализация
Программа `memory_info.c` демонстрирует:
- Выделение памяти разных типов (стек, heap, mmap)
- Чтение метрик из `/proc/[PID]/status`
- Анализ карты памяти из `/proc/[PID]/maps`
- Расчёт PSS и USS

## Задание B: Memory Mapping vs Read/Write

### Цель
Сравнить производительность традиционного I/O (read/write) и memory-mapped I/O (mmap) для работы с большими файлами.

### Методика тестирования
- Создан тестовый файл размером 50MB
- Каждый метод запускался последовательно
- Замерялось время выполнения, пропускная способность и количество page faults

### Результаты выполнения

#### Производительность (файл 50MB):

| Метод | Время (сек) | Пропускная способность | Minor Faults | Major Faults |
|-------|-------------|------------------------|--------------|--------------|
| **read()** | 0.033 | 1497.85 MB/s | 17 | 0 |
| **mmap()** | 0.030 | 1659.22 MB/s | 800 | 0 |
| **mmap()+madvise** | 0.031 | 1634.47 MB/s | 800 | 0 |

#### Сравнение методов:

| Критерий | read() | mmap() |
|----------|--------|--------|
| **Скорость** | 0.033 сек | **0.030 сек** (на 9% быстрее) |
| **Пропускная способность** | 1497 MB/s | **1659 MB/s** |
| **Page Faults** | **17** | 800 |
| **Использование памяти** | Контролируемое | Весь файл отображается |
| **Сложность** | Проще | Сложнее |

#### Ключевые наблюдения:
- **Checksums совпадают**: 6684672000 - все методы корректно прочитали данные
- **mmap() быстрее**: На 0.003 секунды для файла 50MB
- **mmap вызывает больше faults**: 800 vs 17 из-за ленивой загрузки страниц
- **madvise незначительно помогает**: Улучшение минимально для последовательного доступа

### Выводы по Заданию B  
1. **mmap() эффективнее для больших файлов**: Отсутствие копирования данных между буферами даёт прирост производительности
2. **Ленивая загрузка страниц**: mmap вызывает значительно больше minor faults, так как страницы загружаются по требованию
3. **read() предсказуемее**: Меньшее количество faults и контролируемое использование памяти
4. **madvise(MADV_SEQUENTIAL)**: Даёт незначительное улучшение для последовательного доступа
5. **Выбор метода зависит от сценария**: 
   - **mmap** для больших файлов и случайного доступа
   - **read** для маленьких файлов и потоковой обработки

## Задание C: Page Faults в реальном времени

### Цель
Исследовать поведение page faults при различных паттернах доступа к памяти.

### Демонстрации
Программа `page_faults_demo.c` включает 7 демонстраций:
1. Выделение без доступа
2. Последовательный доступ 
3. Заполнение всей памяти
4. Случайный доступ
5. Повторное чтение
6. Сравнение calloc vs malloc
7. mmap vs malloc

### Результаты выполнения

#### Демонстрация 1: Выделение без доступа
Allocated 100 MB
Minor faults: +3
**Вывод**: `malloc()` почти не вызывает faults - память выделяется виртуально.

#### Демонстрация 2: Последовательный доступ
Minor faults: +25,599
Expected: 25,600 (100MB / 4KB)
**Вывод**: Каждая страница вызывает ровно 1 minor fault при первом обращении.

#### Демонстрация 3: Полное заполнение
Minor faults: +0 (после memset)
**Вывод**: Память уже выделена, новых faults нет.

#### Демонстрация 4: Случайный доступ
10,000 обращений → +8,272 faults
Уникальных страниц: ~6,232
**Вывод**: Случайный доступ затрагивает меньше страниц, но менее эффективен.

#### Демонстрация 5: Повторное чтение
Первое обращение: +12,800 faults
Второе чтение: +0 faults
**Вывод**: Повторный доступ к тем же страницам не вызывает faults.

#### Демонстрация 6: calloc vs malloc
calloc + read: +1 fault
calloc + write: +12,799 faults
**Вывод**: `calloc` использует zero-page optimization (CoW).

#### Демонстрация 7: mmap vs malloc
malloc 100MB: +25,600 faults
mmap 100MB: +25,600 faults
**Вывод**: Поведение аналогично для больших блоков.

#### Итоговая статистика:
- **Всего minor faults**: 110,690
- **Major faults**: 0
- **Общий объём памяти**: ~450 MB

### Выводы по Заданию C
1. **Demand Paging**: Страницы выделяются физически только при первом обращении
2. **Zero-page Optimization**: `calloc` использует общую zero-страницу до записи
3. **Copy-on-Write**: При записи в calloc-память происходят CoW faults
4. **Эффективность доступа**: Последовательный доступ оптимальнее случайного
5. **Повторное использование**: Страницы остаются в памяти после освобождения (кеширование)
6. **mmap ≈ malloc**: Для anonymous mappings поведение аналогично

## Ответы на вопросы

### 1. Виртуальная память

**Что такое виртуальная память и зачем она нужна?**
Виртуальная память - это абстракция, которая предоставляет каждому процессу собственное изолированное адресное пространство. Нужна для изоляции процессов, упрощения программирования, эффективного использования RAM и поддержки shared memory.

**Чем отличаются VSZ, RSS, PSS, USS? Какая метрика наиболее точно показывает потребление памяти процессом?**
- **VSZ**: Весь виртуальный размер (выделенная память)
- **RSS**: Резидентный размер (в физической памяти), но дублирует shared
- **PSS**: Пропорциональный размер (делит shared память) - наиболее точный
- **USS**: Уникальный размер (только приватные страницы)

**Что такое страница, кадр, таблица страниц?**
- **Страница**: Единица виртуальной памяти (обычно 4KB)
- **Кадр**: Единица физической памяти того же размера
- **Таблица страниц**: Структура, отображающая виртуальные страницы на физические кадры

**Как работает MMU и TLB? Что происходит при промахе TLB?**
- **MMU**: Аппаратный блок для трансляции адресов
- **TLB**: Кеш трансляций адресов
- **При промахе TLB**: Нужно обращаться к таблице страниц в памяти, что медленнее

**Что такое Copy-on-Write и где он применяется?**
Механизм, при котором страницы копируются только при записи. Применяется в fork(), mmap(MAP_PRIVATE), calloc().

### 2. Page Faults

**Чем отличается minor page fault от major page fault?**
- **Minor**: Страница есть в RAM, но не в таблице страниц (быстро)
- **Major**: Страницы нет в RAM, нужно загружать с диска (медленно)

**Почему при первом обращении к malloc()-памяти происходит page fault?**
Потому что malloc() выделяет только виртуальную память. Физические страницы выделяются по требованию (demand paging) при первом обращении.

**Как уменьшить количество page faults?**
- Использовать последовательный доступ
- Предварительное чтение (prefetching)
- Адекватный размер RAM
- Оптимальные алгоритмы замены страниц

**Что такое demand paging и page replacement?**
- **Demand paging**: Страницы загружаются только при обращении
- **Page replacement**: Алгоритмы вытеснения страниц при нехватке памяти (LRU, Clock и др.)

### 3. Memory Mapping

**Чем mmap() отличается от read()/write()? Когда mmap эффективнее?**
- **mmap()**: Файл отображается в память, доступ как к массиву
- **read()/write()**: Данные копируются через буферы
- **mmap эффективнее** для больших файлов и случайного доступа

**Что такое MAP_PRIVATE и MAP_SHARED? В чём разница?**
- **MAP_PRIVATE**: Изменения видны только процессу (Copy-on-Write)
- **MAP_SHARED**: Изменения видны всем процессам и записываются в файл

**Что произойдёт, если обратиться к памяти за пределами отображённого файла?**
Произойдёт ошибка SIGSEGV или SIGBUS, в зависимости от ситуации.

**Как работает page cache и зачем он нужен?**
Page cache - кеш страниц в RAM для ускорения доступа к файлам. Хранит недавно использованные данные файлов.

### 4. Файловый I/O

**Зачем нужна буферизация? Какие уровни буферизации существуют?**
Для уменьшения количества системных вызовов и оптимизации доступа к диску. Уровни: user-space (stdio), kernel (page cache), disk controller.

**Почему маленький размер буфера замедляет I/O?**
Увеличивает количество системных вызовов и накладные расходы на переключение контекста.

**Что такое O_DIRECT и O_SYNC? Когда их использовать?**
- **O_DIRECT**: Обходит page cache (для СУБД)
- **O_SYNC**: Синхронная запись (для критичных данных)

**Чем отличается fwrite() от write()?**
- **fwrite()**: Библиотечная функция с буферизацией
- **write()**: Системный вызов, пишет в page cache

### 5. Файловая система

**Что такое inode и что в нём хранится?**
Inode - структура с метаданными файла: тип, права, размер, временные метки, указатели на данные. Не хранит имя файла.

**Почему имя файла не хранится в inode?**
Потому что одно имя файла может иметь несколько жёстких ссылок (разные имена для одного inode).

**Чем жёсткая ссылка отличается от символьной?**
- **Жёсткая**: Другое имя для того же inode
- **Символьная**: Файл с путём к оригиналу (новый inode)

**Как в ext4 хранятся большие файлы (indirect pointers)?**
Используются прямые, косвенные, двойные косвенные и тройные косвенные указатели на блоки данных.

### 6. Дисковое планирование

**Зачем нужны I/O schedulers?**
Для оптимизации порядка операций ввода-вывода и уменьшения времени поиска на диске.

**Чем отличаются FCFS, SSTF, SCAN?**
- **FCFS**: В порядке поступления (неэффективно)
- **SSTF**: Ближайший запрос сначала (риск starvation)
- **SCAN**: "Лифт" - в одном направлении, потом обратно

**Какие I/O schedulers используются в современном Linux?**
mq-deadline, bfq, kyber, none (для SSD)

**Почему для SSD планирование менее критично, чем для HDD?**
Потому что у SSD нет механических частей и время доступа ко всем ячейкам одинаково.

### 7. Производительность

**Что такое фрагментация памяти? Внутренняя vs внешняя.**
- **Внутренняя**: Неиспользуемое пространство внутри выделенных блоков
- **Внешняя**: Свободная память разбита на маленькие несмежные фрагменты

**Как swap влияет на производительность?**
Замедляет систему из-за дисковых операций. При активном использовании swap возникает "thrashing".

**Что такое thrashing и как его избежать?**
Система тратит больше времени на подкачку страниц, чем на полезную работу. Избежать: увеличить RAM, оптимизировать working set.

**Почему последовательный доступ к памяти быстрее случайного?**
Из-за prefetching, кеширования и локализации ссылок.

**Что такое cache-friendly код?**
Код с последовательным доступом к данным, хорошей локальностью и предсказуемыми паттернами доступа.
