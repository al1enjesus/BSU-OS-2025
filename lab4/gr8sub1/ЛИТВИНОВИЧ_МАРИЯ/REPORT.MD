##  Метрики до и после выделения памяти

### VSZ и RSS

- VSZ (Virtual Size) — виртуальный размер адресного пространства  
- RSS (Resident Set Size) — реально загруженные страницы в RAM  

| Метрика | Значение |
|--------|----------|
| VSZ до | ~120–160 MB |
| VSZ после | +1–2 MB (heap + mmap) |
| RSS до | ~3–6 MB |
| RSS после | вырос примерно на 1 MB |

---

##  Ответы на вопросы

### Почему VSZ намного больше RSS?

Потому что VSZ отражает *всё адресное пространство процесса*:  
— код, данные, стек  
— сегменты mmap  
— разделяемые библиотеки  
— потенциально зарезервированные, но не загруженные страницы

RSS — это только то, что реально находится в RAM.

### Где находятся разные типы памяти в адресном пространстве?

По выводу /proc/self/maps:

| Тип памяти | Пример адресов | Область |
|------------|----------------|---------|
| Стек | 7ffe... | верх адресного пространства |
| Heap | 55ab..-55ac.. | после bss/data |
| mmap anonymous | 7f22..-7f23.. | в области mmap |
| libc, ld | 7f3c... | ниже mmap |

### Как изменился RSS при выделении 1 MB через malloc vs mmap?

- malloc (heap) → система выделяет память, но страницы появляются только при первом доступе (page fault).  
  RSS растёт постепенно.

- mmap anonymous  
  → аналогично, страницы появляются по требованию.

Обычно mmap чуть более «ленивый» — RSS растёт немного медленнее.

# ЗАДАНИЕ B — Memory Mapping vs Read/Write

##  Суть задания

Два способа чтения файла 100 MB:

1. read() — системные вызовы  
2. mmap() — отображение файла в память  

Обе функции считают сумму всех байтов файла.
### Почему mmap быстрее?

- ядро само подкачивает страницы файла в память  
- меньше переключений контекста  
- нет копирования данных из kernel-space в user-space  
- последовательные page faults приводят к считыванию чанков файла

### Почему у read() больше page faults?

Потому что при read():
- ядру нужно сперва загрузить данные в page cache  
- потом скопировать в буфер пользователя  
- происходит много обращений к ядру

mmap делает это автоматически на основании page faults.

# ЗАДАНИЕ C — Page Faults в реальном времени

##  Что было сделано

Написана программа pagefaults.c, которая:

- выделяет массив 100 MB  
- делает последовательный и случайный доступ  
- выводит ru_minflt и ru_majflt до и после  
 
### Почему при последовательном доступе больше page faults?

Потому что память выделяется лениво — физические страницы появляются только при первом обращении.

При массиве 100 MB → примерно 25000 страниц → столько же minor faults.

### Почему major faults почти не появляются?

Потому что данные:

- анонимные (malloc)  
- не требуют загрузки с диска  
- подкачиваются только из свободных страниц RAM

Major faults появляются только при обращении к отсутствующим данным на диске.

### Что происходит при повторном запуске?

Minor faults будут почти такие же.  
Major faults — снова 0.  

Кэш не играет роли, потому что это не mmap-файл, а malloc-память.
