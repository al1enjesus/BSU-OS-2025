## Теория

### 1. Виртуальная память: основные понятия

#### 1.1 Терминология

**Виртуальная память (Virtual Memory)** — абстракция, позволяющая каждому процессу иметь собственное изолированное адресное пространство, независимое от физической памяти.

**Основные термины:**

- **Виртуальный адрес (Virtual Address)** — адрес, который использует процесс в своих инструкциях. Процесс "думает", что у него есть вся память от 0 до максимального адреса.

- **Физический адрес (Physical Address)** — реальный адрес в оперативной памяти (RAM).

- **Виртуальное адресное пространство (Virtual Address Space)** — диапазон всех возможных виртуальных адресов для процесса. В 64-битных системах Linux это обычно 128 TB (47 бит для пользовательского пространства).

- **Страница (Page)** — единица виртуальной памяти фиксированного размера (обычно 4 KB). Виртуальная память делится на страницы.

- **Кадр (Frame / Page Frame)** — единица физической памяти того же размера, что и страница. Физическая память делится на кадры.

- **Сегмент (Segment)** — непрерывная область памяти с определёнными свойствами (код, данные, стек и т.д.).

#### 1.2 Зачем нужна виртуальная память?

1. **Изоляция процессов** — каждый процесс видит только свою память, не может случайно затереть память другого процесса.

2. **Упрощение программирования** — программист работает с простым линейным адресным пространством, не задумываясь о физическом размещении.

3. **Эффективное использование RAM** — в памяти находятся только активно используемые страницы, остальное на диске (swap).

4. **Разделяемая память** — несколько процессов могут использовать одни и те же физические страницы (например, код библиотек).

5. **Copy-on-Write (COW)** — после `fork()` родитель и ребёнок изначально используют одни страницы, копирование происходит только при записи.

#### 1.3 Трансляция адресов

```
Виртуальный адрес (процесс)
         ↓
    [MMU + TLB]  ← аппаратная трансляция
         ↓
Физический адрес (RAM)
```

**MMU (Memory Management Unit)** — аппаратный блок процессора, который переводит виртуальные адреса в физические используя таблицу страниц.

**Таблица страниц (Page Table)** — структура данных ядра, хранящая соответствие: виртуальная страница → физический кадр + флаги.

**TLB (Translation Lookaside Buffer)** — аппаратный кеш последних трансляций адресов. Значительно ускоряет доступ к памяти (без TLB каждое обращение к памяти требовало бы нескольких дополнительных обращений для чтения таблицы страниц).

### 2. Метрики памяти процесса

Когда мы говорим "процесс занимает X памяти", важно понимать, **какую именно** память мы измеряем.

#### 2.1 VSZ / VIRT (Virtual Size)

**VSZ (Virtual Memory Size)** — полный размер виртуального адресного пространства процесса.

**Включает:**
- Код программы (text)
- Данные (data, bss)
- Стек и кучу (heap)
- Разделяемые библиотеки
- Memory-mapped файлы
- Неиспользуемые зарезервированные области

**Важно:** VSZ **не означает**, что процесс реально использует столько RAM! Это лишь размер виртуального пространства.

**Пример:** Процесс может иметь VSZ = 2 GB, но реально использовать только 10 MB физической памяти.

#### 2.2 RSS (Resident Set Size)

**RSS (Resident Set Size)** — размер физической памяти (RAM), которую процесс **реально занимает** в данный момент.

**Включает:**
- Анонимные страницы (heap, stack)
- Файловые страницы (memory-mapped файлы, загруженный код)
- Разделяемые библиотеки (полностью, даже если используются другими процессами)

**Не включает:**
- Страницы, вытесненные в swap
- Страницы, которые ещё не были затронуты (allocated but not accessed)

**Проблема RSS:** Если считать RSS для всех процессов, можно получить сумму больше, чем есть RAM, потому что разделяемая память считается несколько раз.

#### 2.3 PSS (Proportional Set Size)

**PSS (Proportional Set Size)** — более точная метрика, которая делит разделяемую память пропорционально между процессами.

**Формула:**
```
PSS = (private pages) + (shared pages / number of processes sharing)
```

**Пример:**
- Библиотека libc.so занимает 2 MB
- Используется 10 процессами
- Каждый процесс добавляет к своему PSS: 2 MB / 10 = 200 KB

**PSS** — лучшая метрика для понимания реального вклада процесса в потребление памяти системы.

#### 2.4 USS (Unique Set Size)

**USS (Unique Set Size)** — память, используемая **только** этим процессом (приватные страницы).

**Важно:** USS показывает, сколько памяти освободится, если завершить этот процесс.

#### 2.5 Сравнение метрик

```
┌─────────────────────────────────────┐
│  VSZ (Virtual Size) = 500 MB        │  ← Виртуальное пространство
└─────────────────────────────────────┘
         ↓ (только часть в RAM)
┌─────────────────────────────────────┐
│  RSS (Resident) = 100 MB            │  ← В физической памяти
│  ├─ Shared libs: 60 MB (shared)     │
│  ├─ Heap: 30 MB (private)           │
│  └─ Stack: 10 MB (private)          │
└─────────────────────────────────────┘
         ↓
┌─────────────────────────────────────┐
│  PSS = 30 + 10 + (60/N) ≈ 46 MB     │  ← Пропорциональная доля
└─────────────────────────────────────┘
         ↓
┌─────────────────────────────────────┐
│  USS = 30 + 10 = 40 MB              │  ← Только уникальная память
└─────────────────────────────────────┘
```

### 3. Страничные ошибки (Page Faults)

**Page Fault** — исключение, возникающее когда процесс обращается к виртуальной странице, которой нет в физической памяти.

#### 3.1 Minor Page Fault (мягкая ошибка страницы)

Происходит когда:
- Страница есть в RAM, но не отмечена как присутствующая в таблице страниц процесса
- Типичный случай: первое обращение к новой странице после `malloc()`
- Или: обращение к разделяемой странице, которая уже в памяти (но процесс к ней ещё не обращался)

**Разрешение:** Ядро просто обновляет таблицу страниц, указывая на существующий кадр. **Дисковый I/O не нужен.**

**Время:** Микросекунды (очень быстро).

#### 3.2 Major Page Fault (жёсткая ошибка страницы)

Происходит когда:
- Страницы нет в RAM, нужно загружать с диска
- Типичные случаи:
  - Первая загрузка кода программы
  - Обращение к memory-mapped файлу
  - Загрузка страницы из swap

**Разрешение:** Ядро должно:
1. Найти свободный кадр (или вытеснить существующий)
2. Загрузить данные с диска
3. Обновить таблицу страниц
4. Возобновить выполнение процесса

**Время:** Миллисекунды (в 1000+ раз медленнее minor fault из-за дискового I/O).

#### 3.3 Пример: Жизненный цикл страницы

```c
char *ptr = malloc(1024 * 1024);  // Выделили 1 MB
// На этом этапе: память виртуальная, физических кадров нет

ptr[0] = 'A';  // Первое обращение → Minor Page Fault
               // Ядро выделяет физический кадр, обнуляет его

ptr[4096] = 'B';  // Вторая страница → Minor Page Fault
                  // (страницы по 4 KB, это новая страница)

// Если система под нагрузкой, страницы могут быть вытеснены в swap
// ...время спустя...

char x = ptr[0];  // Если страница в swap → Major Page Fault
                  // Ядро загружает страницу с диска обратно в RAM
```

#### 3.4 Где смотреть Page Faults

```bash
# Общая статистика процесса
cat /proc/[PID]/stat | awk '{print "Minor faults: " $10 "\nMajor faults: " $12}'

# Детальная информация
ps -o pid,comm,min_flt,maj_flt -p [PID]

# В реальном времени
watch -n 1 'ps -o pid,comm,min_flt,maj_flt -p [PID]'
```

### 4. Memory Mapping (mmap)

**mmap()** — системный вызов, отображающий файл или устройство в виртуальное адресное пространство процесса.

#### 4.1 Зачем нужен mmap?

**Традиционный подход (read/write):**
```c
int fd = open("file.dat", O_RDONLY);
char buf[4096];
read(fd, buf, 4096);  // Копирование: диск → kernel buffer → user buffer
// Работаем с buf
close(fd);
```

**С помощью mmap:**
```c
int fd = open("file.dat", O_RDONLY);
char *ptr = mmap(NULL, 4096, PROT_READ, MAP_PRIVATE, fd, 0);
// ptr указывает прямо на содержимое файла, копирования нет!
// Работаем с ptr как с обычным массивом
munmap(ptr, 4096);
close(fd);
```

#### 4.2 Преимущества mmap

1. **Нет лишнего копирования** — данные читаются напрямую из page cache ядра.

2. **Ленивая загрузка** — страницы загружаются по требованию (page fault), а не сразу все.

3. **Эффективная память** — если несколько процессов открывают один файл через mmap, они используют одни физические страницы.

4. **Простота работы с большими файлами** — можно работать с файлом как с массивом, не заботясь об `lseek()`.

5. **Автоматический page cache** — ОС сама решает, когда выгружать/загружать страницы.

#### 4.3 Недостатки mmap

1. **Ошибки доступа** — если файл короче, чем отображённая область, обращение к "пустой" части вызовет `SIGBUS`.

2. **Сложность с ростом файла** — нужно делать `munmap()` и `mmap()` заново.

3. **Не подходит для всех задач** — для маленьких файлов или последовательного чтения `read()` может быть проще.

#### 4.4 Типы mmap

**MAP_PRIVATE** — изменения видны только текущему процессу, не записываются в файл (Copy-on-Write).

**MAP_SHARED** — изменения видны всем процессам, отображающим этот файл, записываются обратно в файл.

**MAP_ANONYMOUS** — не связано с файлом, используется для выделения памяти (альтернатива `malloc` для больших блоков).

#### 4.5 Пример: чтение большого файла

```c
#include <sys/mman.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <stdio.h>
#include <unistd.h>

int main() {
    int fd = open("largefile.bin", O_RDONLY);
    struct stat sb;
    fstat(fd, &sb);  // Узнаём размер файла

    // Отображаем весь файл в память
    char *data = mmap(NULL, sb.st_size, PROT_READ, MAP_PRIVATE, fd, 0);

    // Работаем с data как с обычным массивом
    printf("First byte: %c\n", data[0]);
    printf("Last byte: %c\n", data[sb.st_size - 1]);

    // Освобождаем
    munmap(data, sb.st_size);
    close(fd);
    return 0;
}
```

### 5. Буферизация ввода-вывода

#### 5.1 Уровни буферизации

```
Application
    ↓ fprintf(), fwrite()
[User-space buffer (stdio)]  ← Буфер библиотеки C (обычно 8 KB)
    ↓ fflush() / автоматически при заполнении
System Call (write())
    ↓
[Kernel buffer (page cache)]  ← Кеш страниц ядра
    ↓ fsync() / периодически
Disk Controller
    ↓
[Disk cache]  ← Кеш на уровне диска
    ↓
Physical Disk
```

#### 5.2 Stdio буферизация (FILE*)

**Три режима:**

1. **Fully buffered** — данные пишутся на диск только когда буфер заполнен или при `fflush()`. Используется для файлов.

2. **Line buffered** — данные пишутся при встрече `\n`. Используется для терминалов (stdout).

3. **Unbuffered** — данные пишутся немедленно. Используется для stderr.

**Пример:**
```c
FILE *f = fopen("output.txt", "w");
fprintf(f, "Hello");  // Данные в буфере
fprintf(f, "World");  // Всё ещё в буфере
fflush(f);            // Теперь записано в ядро
fclose(f);            // fclose() автоматически делает fflush()
```

#### 5.3 Kernel Page Cache

**Page Cache** — кеш страниц в оперативной памяти, используемый ядром для ускорения дискового I/O.

**Принцип работы:**
- При чтении файла данные сначала загружаются в page cache
- Повторные чтения берутся из кеша (без обращения к диску)
- При записи данные сначала попадают в page cache (dirty pages)
- Периодически или при `fsync()` dirty pages сбрасываются на диск

**Посмотреть page cache:**
```bash
free -h
#               total        used        free      shared  buff/cache   available
# Mem:           15Gi       2.3Gi       8.1Gi       467Mi       5.2Gi        12Gi
#                                                                ↑
#                                                          Page cache
```

#### 5.4 Прямой I/O (O_DIRECT)

Иногда нужно обойти page cache:
```c
int fd = open("file.dat", O_RDWR | O_DIRECT);
// Чтение/запись идут напрямую с диска, минуя кеш ядра
```

**Когда использовать:**
- Базы данных (у них свой кеш)
- Потоковое видео (данные не будут читаться повторно)

**Недостатки:**
- Требует выравнивания буферов (обычно 512 байт или 4 KB)
- Медленнее для маленьких случайных операций

### 6. Структура виртуальной памяти процесса

Типичная карта памяти процесса в Linux (64-bit):

```
Высокие адреса (0x7fff...)
┌─────────────────────────────────┐
│ Kernel Space                    │ ← Недоступно процессу
├─────────────────────────────────┤
│ Stack (растёт вниз ↓)           │ ← Стек функций, локальные переменные
│         ↓                       │
│                                 │
│ [неиспользуемое пространство]   │
│                                 │
│         ↑                       │
│ Heap (растёт вверх ↑)           │ ← malloc(), new
├─────────────────────────────────┤
│ BSS (неинициализированные)      │ ← static int x;
├─────────────────────────────────┤
│ Data (инициализированные)       │ ← static int x = 5;
├─────────────────────────────────┤
│ Text (код программы)            │ ← Исполняемый код, Read-Only
├─────────────────────────────────┤
│ Shared Libraries                │ ← libc.so, libpthread.so и т.д.
└─────────────────────────────────┘
Низкие адреса (0x0000...)
```

**Посмотреть карту памяти:**
```bash
cat /proc/[PID]/maps
```

**Пример вывода:**
```
00400000-00401000 r-xp 00000000 08:01 12345  /usr/bin/myapp     ← Text (код)
00600000-00601000 r--p 00000000 08:01 12345  /usr/bin/myapp     ← Data (read-only)
00601000-00602000 rw-p 00001000 08:01 12345  /usr/bin/myapp     ← Data (read-write)
00602000-00623000 rw-p 00000000 00:00 0      [heap]             ← Heap
7f1234567000-7f1234568000 rw-p 00000000 00:00 0                 ← Anonymous mapping
7f1234568000-7f123470a000 r-xp 00000000 08:01 54321  /lib/libc.so.6  ← Shared lib
7ffc12345000-7ffc12366000 rw-p 00000000 00:00 0      [stack]    ← Stack
```

**Флаги:**
- `r` = read (чтение разрешено)
- `w` = write (запись разрешена)
- `x` = execute (выполнение разрешено)
- `p` = private (Copy-on-Write)
- `s` = shared

### 7. Файловая система: inode и структуры данных

#### 7.1 Inode (индексный узел)

**Inode** — структура данных файловой системы, содержащая метаданные о файле.

**Что хранится в inode:**
- Тип файла (обычный файл, директория, символьная ссылка и т.д.)
- Права доступа (rwxr-xr-x)
- Владелец (UID) и группа (GID)
- Размер файла в байтах
- Временные метки:
  - `atime` — время последнего доступа (access)
  - `mtime` — время последней модификации содержимого (modify)
  - `ctime` — время последнего изменения метаданных (change)
- Количество жёстких ссылок
- Указатели на блоки данных (прямые, косвенные, двойные косвенные)

**Что НЕ хранится в inode:**
- Имя файла! (имя хранится в директории)

**Посмотреть inode:**
```bash
ls -li file.txt
# 1234567 -rw-r--r-- 1 user group 1024 Jan 15 10:30 file.txt
# ↑
# Номер inode

stat file.txt
# Подробная информация: размер, inode, время доступа и т.д.
```

#### 7.2 Директория

**Директория** — специальный файл, содержащий таблицу: имя файла → номер inode.

**Пример (упрощённо):**
```
Директория /home/user/:
┌──────────────┬───────────┐
│ Имя файла    │ Inode     │
├──────────────┼───────────┤
│ .            │ 1000      │  ← Текущая директория
│ ..           │ 500       │  ← Родительская директория
│ file.txt     │ 1234567   │
│ script.sh    │ 1234568   │
│ docs/        │ 1234569   │  ← Поддиректория (это тоже inode)
└──────────────┴───────────┘
```

**Жёсткая ссылка (hard link):**
```bash
ln file.txt file_copy.txt
```
Создаётся новая запись в директории, указывающая на **тот же inode**. Оба имени равноправны.

**Символьная ссылка (soft link / symlink):**
```bash
ln -s file.txt file_link.txt
```
Создаётся новый файл (новый inode), содержащий путь к оригиналу.

#### 7.3 Размещение файлов на диске

**Прямые указатели (direct pointers):**
Inode содержит 12-15 прямых указателей на блоки данных. Каждый блок обычно 4 KB.

**Косвенные указатели (indirect pointers):**
Для больших файлов используются:
- **Indirect** — указатель на блок, содержащий указатели на данные
- **Double Indirect** — указатель на блок указателей на блоки указателей...
- **Triple Indirect** — ещё один уровень

```
Inode
├─ Direct [0] ──→ Data Block
├─ Direct [1] ──→ Data Block
├─ ...
├─ Direct [11] ──→ Data Block
├─ Indirect ──→ [Block of pointers] ──→ Data Blocks
├─ Double Indirect ──→ [Block] ──→ [Blocks] ──→ Data Blocks
└─ Triple Indirect ──→ [Block] ──→ [Blocks] ──→ [Blocks] ──→ Data Blocks
```

Это позволяет эффективно хранить как маленькие файлы (прямые указатели, быстрый доступ), так и огромные (косвенные указатели).

### 8. Стратегии дискового планирования

Когда поступает много запросов к диску (особенно случайные чтения), ОС должна решить, в каком порядке их обрабатывать.

#### 8.1 FCFS (First Come, First Served)

Обрабатываем запросы в порядке поступления.

**Недостаток:** Головка диска может "скакать" по всему диску, медленно.

#### 8.2 SSTF (Shortest Seek Time First)

Обрабатываем запрос, ближайший к текущей позиции головки.

**Недостаток:** Starvation — запросы к дальним секторам могут ждать очень долго.

#### 8.3 SCAN (Elevator Algorithm)

Головка двигается в одном направлении, обслуживая все запросы на пути, потом разворачивается.

**Плюсы:** Нет starvation, предсказуемое время ожидания.

#### 8.4 Linux I/O Schedulers

Современный Linux использует:
- **mq-deadline** — deadline-based (гарантия максимального времени ожидания)
- **bfq** (Budget Fair Queueing) — справедливое распределение между процессами
- **kyber** — для NVMe SSD
- **none** — для очень быстрых устройств (NVMe) без планирования

**Посмотреть текущий планировщик:**
```bash
cat /sys/block/sda/queue/scheduler
# [mq-deadline] kyber bfq none
#      ↑ текущий
```

```c
           usage.ru_minflt, usage.ru_majflt);
}

int main() {
    size_t size = 100 * 1024 * 1024;  // 100 MB
    char *arr = malloc(size);

    print_page_faults();

    // Последовательный доступ
    for (size_t i = 0; i < size; i += 4096) {  // По одной странице
        arr[i] = 'A';
    }
    print_page_faults();

    // Случайный доступ
    for (int i = 0; i < 10000; i++) {
        arr[rand() % size] = 'B';
    }
    print_page_faults();

    free(arr);
    return 0;
}
```

**Анализ:**
- Почему при последовательном доступе больше page faults?
- Почему major faults появляются (или нет)?
- Как изменится поведение при повторном запуске?

## Практика: Memory Profiler

Реализуйте утилиту `memory_profiler`, которая принимает PID процесса и выводит:

### Минимальные требования:

1. **Метрики памяти:**
   - VSZ, RSS, PSS, USS
   - Shared vs Private память
   - Количество page faults (minor/major)

2. **Карта памяти:**
   - Визуализация сегментов из `/proc/[PID]/maps`
   - Группировка: heap, stack, libraries, anonymous

3. **Динамический мониторинг:**
   - Обновление метрик каждую секунду
   - Вывод изменений (delta)

### Расширенные возможности (*):

4. **Граф использования памяти:**
   - ASCII-график изменения RSS во времени
   - Или сохранение в CSV для построения графика

5. **Анализ разделяемой памяти:**
   - Какие библиотеки используются
   - Сколько процессов разделяют каждую библиотеку

6. **Сравнение процессов:**
   - `memory_profiler --compare PID1 PID2`
   - Показать общую/уникальную память

### Пример использования:


### Подсказки по реализации:

**Парсинг /proc/[PID]/maps:**
```c
FILE *f = fopen("/proc/1234/maps", "r");
char line[256];
while (fgets(line, sizeof(line), f)) {
    unsigned long start, end;
    char perms[5], path[128];
    sscanf(line, "%lx-%lx %s %*s %*s %*s %[^\n]",
           &start, &end, perms, path);
    // start, end — границы сегмента
```

## Подсказки и советы

### 1. Работа с большими числами
При выводе размеров памяти используйте человекочитаемый формат:
```c
void print_size(unsigned long bytes) {
    if (bytes < 1024)
        printf("%lu B", bytes);
    else if (bytes < 1024*1024)
        printf("%.1f KB", bytes/1024.0);
    else if (bytes < 1024*1024*1024)
        printf("%.1f MB", bytes/1024.0/1024.0);
    else
        printf("%.1f GB", bytes/1024.0/1024.0/1024.0);
}
```

### 2. Парсинг /proc файлов
Используйте `sscanf()` для парсинга структурированных данных:
```c
FILE *f = fopen("/proc/self/status", "r");
char line[256];
while (fgets(line, sizeof(line), f)) {
    if (strncmp(line, "VmRSS:", 6) == 0) {
        unsigned long rss_kb;
        sscanf(line, "VmRSS: %lu kB", &rss_kb);
        printf("RSS: %.1f MB\n", rss_kb/1024.0);
    }
}
fclose(f);
```

### 3. Замер времени
Для точных замеров используйте `clock_gettime()`:
```c
#include <time.h>

struct timespec start, end;
clock_gettime(CLOCK_MONOTONIC, &start);

// ... ваш код ...

clock_gettime(CLOCK_MONOTONIC, &end);
double elapsed = (end.tv_sec - start.tv_sec) +
                 (end.tv_nsec - start.tv_nsec) / 1e9;
printf("Time: %.3f seconds\n", elapsed);
```

### 4. Проверка ошибок
Всегда проверяйте возвращаемые значения:
```c
int fd = open("file.txt", O_RDONLY);
if (fd == -1) {
    perror("open failed");

void *ptr = mmap(NULL, size, PROT_READ, MAP_PRIVATE, fd, 0);
if (ptr == MAP_FAILED) {
    perror("mmap failed");
    close(fd);
    return 1;
}
```

### 5. Цветной вывод (опционально)
