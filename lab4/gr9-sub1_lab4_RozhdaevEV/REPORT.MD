1. Цель работы

Изучение механизмов управления памятью в ОС Linux, анализ использования памяти процессами, сравнение различных методов работы с памятью и файлами.
2. Теоретическая часть
2.1 Виртуальная память в Linux

Linux использует виртуальную память для изоляции процессов и эффективного управления физической памятью. Каждый процесс имеет собственное виртуальное адресное пространство.
2.2 Метрики памяти

    VSZ (Virtual Size) - полный размер виртуальной памяти процесса

    RSS (Resident Set Size) - физическая память, занимаемая процессом в ОЗУ

    PSS (Proportional Set Size) - RSS с учётом разделяемых библиотек

    USS (Unique Set Size) - уникальная память процесса

2.3 Page Faults

    Minor faults - страница в памяти, но не в таблице страниц процесса

    Major faults - страница не в памяти, требуется загрузка с диска

2.4 Методы ввода-вывода

    read()/write() - системные вызовы

    mmap() - отображение файлов в память

    fwrite()/fread() - буферизованный ввод-вывод

3. Реализация и эксперименты
3.1 memory_info - анализ структуры памяти

Команда:
bash

./memory_info

Результаты:

    Выделено 4 типа памяти: stack (1KB), heap (10MB), anonymous mmap (50MB), file-backed mmap (5MB)

    VSZ: 67.5 MB, RSS: 66.5 MB - разница небольшая, так как память активно используется

    Data/Heap: 60.2 MB - основная часть памяти

    В карте памяти видны сегменты: код программы, heap, mmap регионы, библиотеки, stack

Анализ:
Программа успешно демонстрирует разные типы выделения памяти и показывает их расположение в виртуальном адресном пространстве.
3.2 page_faults_demo - анализ страничных нарушений

Команда:
bash

./page_faults_demo

Результаты:
Демонстрация	Minor Faults	Major Faults	Примечания
Allocation without access	+3	0	malloc без доступа почти не вызывает faults
Sequential access	+49	0	49 faults на 100MB (ожидалось 25600)
Full memory write	+25	0	memset вызывает меньше faults
Random access	+49	0	Случайный доступ аналогичен последовательному
Re-reading memory	+0	0	Повторное чтение не вызывает faults
calloc vs malloc	+12288	0	calloc вызывает много faults при записи

Анализ:

    malloc() без доступа почти не вызывает page faults - память выделяется виртуально

    calloc() использует оптимизацию copy-on-write, что вызывает много faults при первой записи

    Повторный доступ к памяти не вызывает новых faults

3.3 mmap_vs_read - сравнение методов чтения

Команда:
bash

./mmap_vs_read test.bin --create-file 100
./mmap_vs_read test.bin

Результаты:
Метод	Время (сек)	Page Faults	Производительность
read()	0.224	1	446.43 MB/s
mmap()	0.214	1600	467.29 MB/s
mmap()+madvise	0.213	1600	469.48 MB/s

Анализ:

    mmap() немного быстрее read() для больших файлов

    mmap() вызывает больше page faults, так как отображает файл в память

    madvise(SEQUENTIAL) даёт незначительное ускорение

3.4 io_benchmark - сравнение методов записи

Команда:
bash

./io_benchmark --size 100

Результаты:
Метод	Время (сек)	Производительность
fwrite()	0.036	2761.37 MB/s
write()	0.090	1105.17 MB/s
write(O_SYNC)	1.400	71.43 MB/s
mmap()	0.104	961.97 MB/s

Влияние размера буфера:

    Маленькие буферы (512B-4KB): 576-1033 MB/s

    Оптимальные буферы (8KB-64KB): 1074-1111 MB/s

    Большие буферы (1MB): 1089 MB/s - дальнейшего роста нет

Анализ:

    fwrite() самый быстрый благодаря буферизации в userspace

    write(O_SYNC) очень медленный - каждая запись ждёт сброса на диск

    Оптимальный размер буфера 8-64KB

3.5 memory_profiler - профилирование процессов

Базовый анализ:
bash

./memory_profiler $$

    VSZ: 10.5 MB, RSS: 7.0 MB, PSS: 2.9 MB, USS: 2.6 MB

    PSS < RSS из-за разделяемых библиотек

Сравнение процессов:
bash

./memory_profiler 1 --compare $$

    systemd (PID 1): VSZ 24.0 MB, RSS 13.8 MB

    zsh (текущая оболочка): VSZ 24.0 MB, RSS 13.8 MB

    systemd имеет больше major faults (113) - загрузка с диска

Анализ Firefox:
bash

./memory_profiler $(pgrep firefox) --map

    VSZ: 11.4 GB - огромное виртуальное пространство

    RSS: 689.0 MB - реально используемая память

    PSS: 525.0 MB - с учётом разделяемых ресурсов

    3260 записей в карте памяти - сложная структура

4. Ответы на вопросы из кода
4.1 Почему VSZ > RSS?

VSZ включает всю виртуальную память (код, данные, библиотеки, mmap), а RSS - только резидентные страницы в ОЗУ. В демонстрации: VSZ 67.5 MB vs RSS 66.5 MB.
4.2 Когда происходят page faults?

    При первом обращении к странице (minor fault)

    При загрузке страницы с диска (major fault)

    В демонстрации: malloc + доступ = faults, повторный доступ = 0 faults

4.3 Разница calloc vs malloc?

calloc использует zero-page оптимизацию, что вызывает много page faults при первой записи (copy-on-write).
4.4 Самый быстрый метод I/O?

fwrite() - 2761 MB/s благодаря буферизации в userspace.
5. Выводы

    Разные методы выделения памяти имеют различные характеристики производительности и использования ресурсов

    mmap() эффективен для больших файлов, но вызывает больше page faults

    Буферизованный I/O (fwrite) показывает наилучшую производительность для последовательной записи

    PSS метрика более точно отражает реальное использование памяти, чем RSS

    Оптимальный размер буфера для write() составляет 8-64 KB

    calloc() оптимизирован через механизм copy-on-write
