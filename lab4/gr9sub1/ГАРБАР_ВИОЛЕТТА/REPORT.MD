### Задание A: Анализ виртуальной памяти процесса

**ЦЕЛЬ ЗАДАНИЯ А** заключается в том, чтобы исследовать различные способы выделения памяти в Linux и проанализировать метрики виртуальной памяти процесса с использованием интерфейса /proc.

**Терминология**
Сегмент (Segment) — непрерывная область памяти с определёнными свойствами (код, данные, стек и т.д.).

VSZ (Virtual Memory Size) — полный размер виртуального адресного пространства процесса.Включаетв себя: код программы (text), данные (data, bss), стек и кучу (heap), разделяемые библиотеки, memory-mapped файлы, неиспользуемые зарезервированные области.

RSS (Resident Set Size) — размер физической памяти (RAM), которую процесс реально занимает в данный момент. Включает в себя: анонимные страницы (heap, stack), файловые страницы (memory-mapped файлы, загруженный код), разделяемые библиотеки (полностью, даже если используются другими процессами)

PSS (Proportional Set Size) — более точная метрика, которая делит разделяемую память пропорционально между процессами. PSS — лучшая метрика для понимания реального вклада процесса в потребление памяти системы.
```
Формула:
PSS = (private pages) + (shared pages / number of processes sharing)
```
USS (Unique Set Size) — память, используемая только этим процессом (приватные страницы). USS показывает, сколько памяти освободится, если завершить этот процесс.

**Методы выделения память**
1. Стек (Stack) 
```
char stack_var[1024];
```
Распологается в верхней части адресного пространства. Для стека характерно автоматическое управление и быстрый доступ.

2. Куча (Heap) - malloc
```
char *heap_var = malloc(1024*1024);
```
Cегмент [heap] располагается в адресном пространстве. Для кучи характерно динамическое выделение, ручное управление.
3. Memory Mapping - mmap
```
char *mmap_var = mmap(NULL, 1024*1024, PROT_READ|PROT_WRITE,
                     MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
```
Распологается в средней части адресного пространства.Отображается в виртуальную память и эффективно в использовании для больших блоков

- Почему VSZ намного больше RSS?
VSZ (Virtual Size) = 4804 KB

- Где находятся разные типы памяти в адресном пространстве?
Структура адресного пространства (от низких к высоким адресам):
    Текст программы (6242be6db000-6242be6e0000) --> исполняемый код, права доступа: read/execute

    Anonymous mmap (71c1ee1ff000-71c1ee400000) --> память, выделенная через mmap
                                               --> располагается рядом с библиотеками
    Стек --> обычно в самой верхней части адресного пространства
         --> растет в сторону низких адресов

### Задание B: Буферизованный vs Небуферизованный I/O

**ЦЕЛЬ ЗАДАНИЯ B** 
    Сравнить производительность между стандартной библиотеки C: `fopen()`, `fwrite()`, `fread()`, системными вызовами: `open()`, `write()`, `read()`, системными вызовами с буфером разного размера (512 байт, 4 KB, 64 KB).

**Терминология**
    Уровни буферизации:
```
Application
    ↓ fprintf(), fwrite()
[User-space buffer (stdio)]  ← Буфер библиотеки C (обычно 8 KB)
    ↓ fflush() / автоматически при заполнении
System Call (write())
    ↓
[Kernel buffer (page cache)]  ← Кеш страниц ядра
    ↓ fsync() / периодически
Disk Controller
    ↓
[Disk cache]  ← Кеш на уровне диска
    ↓
Physical Disk
```

    Три режима Stdio буферизации (FILE*):
        Fully buffered —> данные пишутся на диск только когда буфер заполнен или при `fflush()`. Используется для файлов.
        Line buffered —> данные пишутся при встрече `\n`. Используется для терминалов (stdout).
        Unbuffered —> данные пишутся немедленно. Используется для stderr.

    *Page Cache* — кеш страниц в оперативной памяти, используемый ядром для ускорения дискового I/O.
    Принцип работы:
        - При чтении файла данные сначала загружаются в page cache
        - Повторные чтения берутся из кеша (без обращения к диску)
        - При записи данные сначала попадают в page cache (dirty pages)
        - Периодически или при `fsync()` dirty pages сбрасываются на диск
```
Просмотр page cache:
free -h
#               total        used        free      shared  buff/cache   available
# Mem:           15Gi       2.3Gi       8.1Gi       467Mi       5.2Gi        12Gi
#                                                                ↑
#                                                          Page cache
Чтобы обойти page cache
int fd = open("file.dat", O_RDWR | O_DIRECT);
// Чтение/запись идут напрямую с диска, минуя кеш ядра - Прямой I/O (O_DIRECT)
```
    Когда использовать O_DIRECT:
        - Базы данных (у них свой кеш)
        - Потоковое видео (данные не будут читаться повторно)
    *НО:*
        - Требует выравнивания буферов (обычно 512 байт или 4 KB)
        - Медленнее для маленьких случайных операций

### Задание C: Дисковый I/O и планирование

**ЦЕЛЬ ЗАДАНИЯ С**
Проанализировать дисковую активность системы, изучить работу I/O планировщиков и оптимизировать производительность дисковых операций через мониторинг и настройку параметров системы.

**Терминология**
Уровни дискового I/O в Linux:
```
Application
    ↓ write()/read()
[VFS (Virtual File System)]
    ↓
[Page Cache] ← Буферизация на уровне ядра
    ↓
[Block Layer] ← I/O планировщики
    ↓
[Device Driver]
    ↓
Physical Disk
```
Ключевые метрики дискового I/O:
- **r/s, w/s** - операции чтения/записи в секунду (IOPS)
- **rkB/s, wkB/s** - скорость чтения/записи (KB/s)
- **%util** - утилизация диска
- **await** - среднее время ожидания I/O операций
- **aqu-sz** - средняя длина очереди запросов

I/O Planning (Планировщики ввода-вывода):
- **mq-deadline** - гарантированное время выполнения (deadline-based)
- **bfq** (Budget Fair Queueing) - справедливое распределение между процессами  
- **kyber** - для быстрых SSD устройств
- **none** - без планировщика (для очень быстрых накопителей)

## Вопросы для отчёта 

### Виртуальная память:
**1. Что такое виртуальная память и зачем она нужна?** 
Виртуальная память — это абстракция, позволяющая каждому процессу иметь собственное изолированное адресное пространство. Она обеспечивает:
- Изоляцию процессов
- Упрощение программирования
- Эффективное использование RAM
- Разделяемую память
- Copy-on-Write после fork()
**2. Чем отличаются VSZ, RSS, PSS, USS? Какая метрика наиболее точная?** 
- **VSZ** — размер виртуального адресного пространства (не отражает реальное использование RAM) 
- **RSS** — сколько физической памяти реально занимает процесс 
- **PSS** — пропорциональное распределение разделяемой памяти между процессами 
- **USS** — уникальная память, используемая только этим процессом 
- **PSS** — наиболее точная метрика для оценки реального потребления памяти.
**3. Что такое страница, кадр, таблица страниц?** 
- **Страница** — единица виртуальной памяти (обычно 4 KB) 
- **Кадр** — единица физической памяти того же размера 
- **Таблица страниц** — структура, сопоставляющая виртуальные страницы с физическими кадрами
**4. Как работает MMU и TLB? Что при промахе TLB?** 
- **MMU** — аппаратный блок, переводящий виртуальные адреса в физические 
- **TLB** — кеш трансляций адресов 
- При промахе TLB: MMU обращается к таблице страниц, что замедляет доступ к памяти
**5. Что такое Copy-on-Write и где применяется?** 
Copy-on-Write — механизм, при котором после fork() родитель и потомок используют одни и те же страницы. Копирование происходит только при попытке записи.

### Page Faults:
**6. Minor vs Major Page Fault** 
- **Minor** — страница уже в RAM, просто не отмечена в таблице 
- **Major** — страница отсутствует в RAM, требуется загрузка с диска
**7. Почему malloc вызывает page fault при первом обращении?** 
malloc выделяет виртуальную память, но физические кадры не назначаются. Первое обращение вызывает **minor page fault**.
**8. Как уменьшить количество page faults?** 
- Использовать локальные данные 
- Уменьшить использование swap 
- Предзагрузка данных 
- Увеличить RAM
**9. Demand Paging и Page Replacement** 
- **Demand Paging** — страницы загружаются по мере обращения 
- **Page Replacement** — вытеснение страниц из RAM при нехватке памяти

### Memory Mapping:
**10. mmap vs read/write. Когда эффективнее?** 
- **mmap** — отображает файл в память, без копирования 
- Эффективнее при работе с большими файлами, повторном доступе, разделяемом использовании
**11. MAP_PRIVATE vs MAP_SHARED** 
- **MAP_PRIVATE** — изменения видны только текущему процессу 
- **MAP_SHARED** — изменения видны всем и записываются в файл
**12. Что если обратиться за пределы отображённого файла?** 
Произойдёт ошибка **SIGBUS** — доступ к несуществующей области.
**13. Как работает page cache и зачем он нужен?** 
- Кеширует страницы файлов в RAM 
- Ускоряет повторные чтения 
- Записи сначала идут в кеш, потом сбрасываются на диск

### Файловый I/O:
**14. Зачем нужна буферизация? Уровни буферизации?** 
- Уменьшает количество системных вызовов 
- Уровни:
  - Буфер stdio (user-space)
  - Буфер ядра (page cache)
  - Буфер диска
**15. Почему маленький буфер замедляет I/O?** 
Маленький буфер вызывает частые обращения к ядру и диску → больше накладных расходов.
**16. Что такое O_DIRECT и O_SYNC? Когда использовать?** 
- **O_DIRECT** — минует page cache 
- **O_SYNC** — запись сразу на диск 
Используются в базах данных, потоковом видео, когда важна консистентность или кеш не нужен.
**17. fwrite vs write** 
- **fwrite()** — буферизованный, через stdio 
- **write()** — системный вызов, напрямую в ядро

### Файловая система:
**18. Что такое inode и что в нём хранится?** 
Inode — структура с метаданными файла: права, владелец, размер, временные метки, указатели на блоки.
**19. Почему имя файла не хранится в inode?** 
Имя хранится в директории, а inode — это абстракция, позволяющая одному inode иметь несколько имён (жёсткие ссылки).
**20. Жёсткая vs символьная ссылка** 
- **Жёсткая** — указывает на тот же inode 
- **Символьная** — отдельный файл, содержащий путь к оригиналу
**21. Как ext4 хранит большие файлы?** 
Через;
- Прямые указатели 
- Косвенные 
- Двойные и тройные косвенные указатели

### Дисковое планирование:
**22. Зачем нужны I/O schedulers?** 
Для оптимизации порядка обработки запросов к диску, уменьшения времени ожидания и повышения производительности.
**23. FCFS vs SSTF vs SCAN** 
- **FCFS** — по порядку 
- **SSTF** — ближайший запрос 
- **SCAN** — "лифт": в одном направлении, потом обратно
**24. Какие планировщики в Linux?** 
- **mq-deadline** 
- **bfq** 
- **kyber** 
- **none** (для NVMe)
**25. Почему для SSD планирование менее критично?** 
SSD не имеет механической головки → время доступа почти одинаково для всех блоков.

### Производительность:
**26. Фрагментация памяти: внутренняя vs внешняя** 
- **Внутренняя** — неиспользуемое пространство внутри блока 
- **Внешняя** — свободные блоки, но не подряд
**27. Как swap влияет на производительность?** 
Swap медленнее RAM → при активном использовании может сильно замедлить систему.
**28. Что такое thrashing и как избежать?** 
Состояние, когда система тратит больше времени на обмен страницами, чем на выполнение задач. 
Избегать: увеличить RAM, уменьшить количество процессов.
**29. Почему последовательный доступ быстрее случайного?** 
- Лучше кешируется 
- Меньше промахов TLB 
- Эффективнее для дисков и page cache
**30. Что такое cache-friendly код?** 
Код, который использует данные, близкие по адресу, минимизируя промахи кеша и повышая производительность.
