### Ответы на вопросы

1. **Почему VSZ намного больше RSS?**
   - **VSZ**: Полный размер виртуального адресного пространства (2748 КБ до выделения, 5824 КБ после), включая код, данные, стек, кучу, библиотеки (`libc.so.6` ~2 МБ). Включает зарезервированные, но не загруженные страницы.
   - **RSS**: Физическая память в RAM (1404/4732/1764 КБ). VSZ больше из-за ленивого выделения (lazy allocation) и разделяемых страниц библиотек.

2. **Где находятся разные типы памяти?**
   - **Код**: Низкие адреса, `00005abcc7be1000-00005abcc7be6000`, права `r--p`, `r-xp`, `rw-p` (для `/home/vboxuser/BSU-OS-2025/lab4/memory_info`).
   - **Heap**: `00005abce7487000-00005abce74a8000` (132 КБ, `rw-p`), после выделения появляется `0000787d820ff000-0000787d82400000` (3076 КБ, `rw-p`), объединяющий 2 МБ кучи и 1 МБ mmap.
   - **Stack**: Верхние адреса, `00007ffdd05c1000-00007ffdd05e2000`, права `rw-p`.
   - **Mmap (анонимный)**: Включён в `0000787d820ff000-0000787d82400000` (3076 КБ, `rw-p`), помечен как `[heap]` вместо `[anon]`.
   - **Библиотеки**: `0000787d82400000-0000787d8261f000` для `libc.so.6`, права `r--p`, `r-xp`, `rw-p`.

3. **Как изменился RSS при выделении 2 MB через malloc vs 1 MB через mmap?**
   - **До выделения**: RSS = 1404 КБ.
   - **После выделения**:
     - `malloc` (2 МБ): Увеличивает `VmData` на ~3076 КБ (с 224 до 3300 КБ). RSS увеличивается на ~3328 КБ (до 4732 КБ), что больше ожидаемого 3076 КБ из-за накладных расходов (метаданные кучи, выравнивание).
     - `mmap` (1 МБ): Включён в сегмент `0000787d820ff000-0000787d82400000` (3076 КБ, `rw-p`).
     - **Общий эффект**: RSS вырос на 3328 КБ, что соответствует 2 МБ кучи + 1 МБ mmap с учетом системных накладных расходов (~256 КБ).
   - **После освобождения**: RSS = 1764 КБ (выше начального на 360 КБ из-за кэширования страниц).

## Анализ

1. **Page faults = 0**  
   * Файл 100 МБ полностью помещается в **page cache** (SSD + ≥8 ГБ RAM).  
   * При первом `read()` данные уже загружены в память → **ленивая загрузка не вызывает новых fault**.  
   * `mmap()` использует тот же кэш → **Δ = 0**.

2. **Время почти одинаково**  
   * На современных системах с **SSD** и достаточной RAM разница между `read()` и `mmap()` **минимальна** при **однократном линейном чтении**.  
   * `read()` читает из кэша → **нет копирования из kernel buffer**.  
   * `mmap()` не даёт выигрыша, т.к. нет частичного доступа или переиспользования.

3. **Когда `mmap()` выигрывает?**  
   * Файлы **> RAM** → принудительная подкачка.  
   * **Многократный** или **случайный** доступ.  
   * Частичное чтение (только нужные куски).

## 7. Ответы на ключевые вопросы

### 7.1. Почему при последовательном доступе больше page faults?

**Ответ:**  
При последовательном чтении файла (например, 100 МБ):

```c
for (i = 0; i < size; i += 4096) {
    sum += buf[i];  // доступ к каждой странице
}
```

→ **Каждая новая страница (4 КБ) вызывает 1 minor page fault.**  

**Расчёт:**  
- Файл: **100 МБ**  
- Размер страницы: **4 КБ**  
- Количество страниц: `100 × 1024 / 4 = 25 600`  
→ **25 600 minor page faults**

**Вывод:**  
> **Последовательный доступ → 1 PF на страницу → максимум PF**

---

### **7.2. Почему major faults появляются (или не появляются)?**

| Условие | Major Faults |
|--------|-------------|
| **Файл в RAM (page cache)** | **0** |
| **Файл выгружен (swap/диск)** | **>0** |
| **Очистка кэша:** `echo 3 > /proc/sys/vm/drop_caches` | **>0 при первом доступе** |

**В нашем случае:**  
- `bash` **уже загружен**.  
- Все библиотеки **в page cache**.  
- **Нет I/O с диска** → **major faults = 0**

**Как вызвать major faults:**

```bash
# Очищаем кэш страниц (выгружает файлы из RAM)
sudo sh -c 'echo 3 > /proc/sys/vm/drop_caches'

# Мониторим процесс bash
./memory_profiler $(pgrep bash | head -1) --watch 1
```

→ При первом доступе → **major fault**

### **7.3. Как изменится поведение при повторном запуске?**

| Запуск               | Minor PF | Major PF | Причина                              |

| **1-й запуск**       | **25 600** | **0**    | Файл загружается в RAM               |
| **2-й запуск**       | **0**    | **0**    | Файл **уже в page cache**            |
| **После `drop_caches`** | **25 600** | **>0**   | Кэш очищен → подкачка с диска        |

**Вывод:**  
> **Повторный запуск → 0 PF**, если данные **в page cache**.

## Ответы на вопросы

### Виртуальная память

1. Что такое виртуальная память и зачем она нужна?
Виртуальная память - это абстракция, позволяющая процессам иметь изолированное адресное пространство. Нужна для:
- Изоляции процессов
- Упрощения программирования  
- Эффективного использования RAM
- Поддержки разделяемой памяти

2. Чем отличаются VSZ, RSS, PSS, USS?
- VSZ - весь виртуальный размер (включая неиспользуемые страницы)
- RSS - резидентный размер (фактически в RAM)
- PSS - пропорциональный размер (делит shared память)
- USS - уникальный размер (только приватные страницы)

Наиболее точная метрика - PSS, так как учитывает разделяемую память.

3. Что такое страница, кадр, таблица страниц?
- Страница - единица виртуальной памяти (обычно 4KB)
- Кадр - единица физической памяти того же размера
- Таблица страниц - структура, отображающая виртуальные страницы на физические кадры

4. Как работает MMU и TLB?
- MMU (Memory Management Unit) - аппаратный блок для трансляции адресов
- TLB (Translation Lookaside Buffer) - кеш трансляций
- При промахе TLB происходит поиск в таблице страниц, что медленнее

5. Что такое Copy-on-Write?
Оптимизация, когда при fork() родитель и ребенок изначально используют одни страницы, а копирование происходит только при записи.

### Page Faults

1. Minor vs Major page faults
- Minor - страница в RAM, но не в таблице страниц (быстро)
- Major - страницы нет в RAM, нужно загружать с диска (медленно)

2. Почему при malloc() происходит page fault?
malloc() только резервирует виртуальную память. Физические страницы выделяются при первом обращении (page fault).

3. Как уменьшить количество page faults?
- Использовать calloc() вместо malloc()+memset()
- Предварительное чтение данных
- Оптимизация алгоритмов доступа

4. Что такое demand paging и page replacement?
- Demand paging - страницы загружаются по требованию
- Page replacement - алгоритмы вытеснения страниц (LRU, Clock)

### Memory Mapping

1. mmap() vs read()/write()
- mmap() - отображает файл в память, доступ как к массиву
- read()/write() - последовательные операции
- mmap эффективнее для случайного доступа к большим файлам

2. MAP_PRIVATE vs MAP_SHARED
- PRIVATE - изменения видны только процессу (Copy-on-Write)
- SHARED - изменения видны всем процессам и записываются в файл

3. Обращение за пределами отображенного файла
Вызывает SIGBUS - ошибка шины.

4. Page cache
Кеш страниц в ядре для ускорения дискового I/O.

### Файловый I/O

1. Уровни буферизации
- User-space (stdio)
- Kernel (page cache) 
- Disk controller

2. Почему маленький буфер медленный?
Больше системных вызовов, больше контекстных переключений.

3. O_DIRECT и O_SYNC
- O_DIRECT - обходит page cache
- O_SYNC - синхронная запись на диск
- Используются в БД, когда свой кеш эффективнее

4. fwrite() vs write()
- fwrite() - буферизованный, уровень stdio
- write() - небуферизованный, системный вызов

### Файловая система

1. Inode
Хранит метаданные файла (права, размер, временные метки), но не имя.

2. Почему имя не в inode?
Имена хранятся в директориях для поддержки жестких ссылок.

3. Жесткая vs символьная ссылка
- Жесткая - другая запись для того же inode
- Символьная - отдельный файл с путем к оригиналу

4. Хранение больших файлов в ext4
Использует прямые, косвенные, двойные и тройные указатели.

### Дисковое планирование

1. Зачем нужны I/O schedulers?
Для оптимизации порядка обработки запросов к диску.

2. FCFS, SSTF, SCAN
- FCFS - в порядке поступления
- SSTF - ближайший к головке
- SCAN - "лифт" в одном направлении

3. I/O schedulers в Linux
- mq-deadline, bfq, kyber, none

4. Почему для SSD менее критично?
SSD нет механических частей, случайный доступ почти так же быстр как последовательный.

### Производительность
1. Фрагментация памяти
- Внутренняя - неиспользуемое пространство внутри выделенного блока
- Внешняя - свободная память разбита на маленькие фрагменты

2. Влияние swap
Замедляет работу при активном использовании (major faults).

3. Thrashing
Ситуация когда система тратит больше времени на подкачку страниц чем на полезную работу.

4. Последовательный vs случайный доступ
Последовательный лучше из-за prefetching и кеширования.

5. Cache-friendly код
Использует локальность данных, последовательный доступ.
