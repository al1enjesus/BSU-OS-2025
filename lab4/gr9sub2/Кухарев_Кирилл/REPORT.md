## ЗАКЛЮЧЕНИЕ

### Основные выводы:

1. **Виртуальная память** — фундаментальный механизм современных ОС, обеспечивающий эффективное использование памяти через ленивое выделение и page caching.

2. **Page faults** — нормальный и необходимый процесс, не "ошибка" в строгом смысле. Minor faults (~мкс) допустимы, но major faults (~мс) нужно избегать.

3. **mmap() vs read():**
   - read(): простой, хорош для маленьких файлов
   - mmap(): быстро для больших, но требует контроля границ
   - Правильный выбор даёт 10-100x ускорение

4. **Page cache** — невидимый герой, делающий повторные обращения к файлам мгновенными.

5. **Буферизация** — критична для производительности I/O. Разница между 1-byte и 64KB буфером может быть в миллионы раз!

### На практике применить можно:

- Анализировать реальные приложения с `ps`, `/proc`, `smem`
- Использовать mmap() для больших файлов
- Настраивать размер буфера под конкретное оборудование (HDD vs SSD)
- Мониторить major page faults как индикатор нехватки памяти
- Использовать huge pages для очень больших данных

## ОТВЕТЫ НА КОНТРОЛЬНЫЕ ВОПРОСЫ

### ВИРТУАЛЬНАЯ ПАМЯТЬ

#### 1. Что такое виртуальная память и зачем она нужна?

**Виртуальная память** — это техника управления памятью, при которой каждый процесс получает собственное логическое (виртуальное) адресное пространство, которое отображается на физическую RAM и дисковый SWAP.

**Зачем нужна:**
- **Изоляция процессов:** каждый видит адреса от 0 до 2^64, не зная о других
- **Защита:** процесс не может случайно повредить чужую память
- **Переподписка:** можем выделить памяти больше, чем физический RAM
- **Ленивое выделение:** выделяем адресное пространство, но физическую память только при обращении
- **Прозрачность:** программист пишет код без учёта размера физической памяти
#### 2. Чем отличаются VSZ, RSS, PSS, USS? Какая метрика наиболее точна?

| Метрика | Расшифровка           | Что считает                                                                 | Точность                                 |
| ------- | --------------------- | --------------------------------------------------------------------------- | ---------------------------------------- |
| **VSZ** | Virtual Size          | Всё виртуальное адресное пространство (выделено, но может быть не в памяти) | Низкая (может включать неиспользованное) |
| **RSS** | Resident Set Size     | Физические страницы в RAM этого процесса                                    | Средняя (не учитывает sharing)           |
| **PSS** | Proportional Set Size | RSS, но разделяемые страницы считаются пропорционально                      | Высокая (честный подсчёт)                |
| **USS** | Unique Set Size       | Только приватная память (не разделяется с другими)                          | Максимальная (реальный footprint)        |
#### 3. Что такое страница, кадр, таблица страниц?

**Страница (Page)** — логическая единица виртуальной памяти
- Обычный размер: 4 KB (4096 байт)
- Адреса на компьютере выравнены по границам страниц
- Может быть в RAM, на SWAP, или вообще не существовать

**Кадр (Frame)** — физический "слот" в RAM
- Соответствует странице по размеру (тоже 4 KB)
- Это именно физическая памяти

**Таблица страниц (Page Table)** — структура данных, которая отображает виртуальные адреса на физические
**Структура:**
```
Виртуальный адрес: | PML4 | PDPT | PD | PT | Offset |
                   | 9 бит | 9 бит | 9 бит | 9 бит | 12 бит |

Каждый уровень — это таблица со ссылками на следующий уровень
Максимум 4 уровня (x86-64)
```
#### 4. Как работает MMU и TLB? Что происходит при промахе TLB?

**MMU (Memory Management Unit)** — аппаратный модуль, который переводит виртуальные адреса в физические

**TLB (Translation Lookaside Buffer)** — маленький и быстрый кэш переводов адресов

**При промахе TLB (TLB miss):**
1. CPU генерирует TLB miss exception
2. Специальный обработчик (обычно аппаратный) выполняется
3. Ходит в page tables в памяти (200+ циклов!)
4. Если нет записи в page table → Page Fault (ещё медленнее)
5. Обновляет TLB записью
6. Повторяет инструкцию

**Оптимизация:** большие TLB (Intel: 1536 entries), или huge pages (2MB вместо 4KB)

#### 5. Что такое Copy-on-Write и где он применяется?

**Copy-on-Write (CoW)** — техника оптимизации: не копируем данные, пока не нужно изменять

**Применение:**
1. **fork()** — самый частый случай (каждый процесс думает, что скопировалась вся память)
2. **calloc()** — выделение нулевой памяти (используется zero page)
3. **Разделяемые библиотеки** — несколько процессов читают один код
4. **Снимки памяти (snapshots)** — виртуальные машины, контейнеры

### PAGE FAULTS

#### 6. Чем отличается minor page fault от major page fault?

| Тип | Источник страницы | Время | Когда | Последствия |
|-----|------------------|--------|-------|------------|
| **Minor** | Уже в памяти (выделить кадр) | ~мкс | Первый доступ после malloc | Быстро |
| **Major** | На диске (swap) | ~мс | Нехватка RAM | Очень медленно (в 1000x раз) |

**Minor Page Fault:**
```
malloc(100 MB) → VSZ +100 MB, RSS 0
arr[0] = 'A'
↓
ОС: "Нужна страница по адресу 0x..."
↓
Ядро выделяет физический кадр (есть свободные)
↓
Обновляет page table
↓
Процесс продолжает (~1-10 мкс)
↓
RSS +4 KB
```

**Major Page Fault:**
```
Программа: "Дай мне arr[500000]"
↓
ОС: "Нужна эта страница, но свободных кадров нет"
↓
ОС выбирает старую страницу для вытеснения (LRU)
↓
Выгружает на SWAP (5-100 мс)
↓
Загружает нужную со SWAP (5-100 мс)
↓
Обновляет page table
↓
Процесс продолжает (~10-100 мс)
↓
Падение производительности в 1000x раз!
```

**Наблюдение из экспериментов:**
```bash
./page_faults --sequential
# Демо 2: Sequential access
# Minor faults: 25600  (ожидалось 25600 для 100MB)
# Major faults: 0      (нет swap, есть RAM)

# Если запустить на системе с давлением памяти:
# Major faults: 1500   (50% страниц на swap!)
```

#### 7. Почему при первом обращении к `malloc()`-памяти происходит page fault?

**Lazy allocation (ленивое выделение):**

```c
char *arr = malloc(100 * 1024 * 1024);  // 1. malloc() вызов
// ← здесь NO page fault! (только виртуальное выделение)

arr[0] = 'A';  // 2. Первый доступ
// ← здесь MAJOR page fault!
```

**Почему так сделано:**
1. **Скорость:** не нужно инициализировать 100 MB сразу
2. **Экономия:** может быть, программа не будет использовать всё

**Механизм:**
```
malloc():
├─ Вызывает brk() или mmap()
├─ Ядро расширяет виртуальное адресное пространство
├─ Добавляет записи в page tables (флаг: not-present)
├─ НЕ выделяет физическую память
└─ Возвращает указатель

Первый доступ arr[0]:
├─ CPU ищет страницу в TLB → miss
├─ MMU идёт в page table → запись present=0
├─ Генерирует page fault exception
├─ Ядро ловит исключение
├─ Выделяет физический кадр
├─ Обновляет page table (present=1, физ_адрес=0x12345)
├─ Обновляет TLB
├─ Возвращает управление процессу
└─ CPU повторяет инструкцию (теперь успешно)
```

**На практике видно:**
```bash
# Демо из программы page_faults.c

Demo 1: malloc() without access
After malloc: Minor faults: 0  ← никаких!

Demo 2: Sequential write (одна запись на странице)
After sequential writes: Minor faults: 25600  ← одна на каждую страницу!

Demo 5: Re-reading same memory
After second read: Minor faults: 0  ← памяти уже нет!
```

#### 8. Как уменьшить количество page faults?

**Способ 1: Потребление памяти меньше, чем физической RAM**
```c
// Плохо: выделяем больше RAM, чем есть
char *arr = malloc(10 * 1024 * 1024 * 1024);  // 10 GB на 4 GB системе

// Хорошо: выделяем меньше
char *arr = malloc(1 * 1024 * 1024 * 1024);  // 1 GB
```

**Способ 2: Сначала ловить всю память (prefaulting)**
```c
char *arr = malloc(100 * 1024 * 1024);

// Плохо: page faults распределены по всей программе
for (int i = 0; i < size; i++) {
    arr[i] = ...;  // 25600 фолтов, разбросано
}

// Хорошо: prefault всю память сразу
for (int i = 0; i < size; i += 4096) {
    arr[i] = 0;  // 25600 фолтов, но сразу в начале
}
// Потом остальные обращения без фолтов
```

**Способ 3: Использовать madvise() и mmap()**
```c
void *data = mmap(NULL, size, PROT_READ | PROT_WRITE,
                   MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);

// Подсказываем ядру о паттерне доступа
madvise(data, size, MADV_SEQUENTIAL);  // Предзагрузка
// или
madvise(data, size, MADV_RANDOM);      // Без предзагрузки
```

**Способ 4: Huge pages (больших размер страницы)**
```c
// Вместо 25600 страниц по 4KB
// Одна страница по 2 MB = 50 страниц
// → 500x меньше page faults!

// Linux: автоматическое использование huge pages (если включено)
// или явно через мmap:
mmap(..., HUGETLB_FLAG);
```

**Способ 5: Оптимизировать доступ к памяти**
```c
// Плохо: случайный доступ
for (int i = 0; i < iterations; i++) {
    arr[rand() % size] = ...;
}

// Хорошо: последовательный доступ
for (int i = 0; i < size; i++) {
    arr[i] = ...;
}
// → меньше TLB misses, лучше cache locality
```

#### 9. Что такое demand paging и page replacement?

**Demand Paging** — загружать страницы в RAM только при обращении

```
Жёсткое выделение (старые ОС):
├─ Программа: "Дай мне 100 MB"
├─ ОС: "Хорошо, выделяю 25600 страниц физически"
├─ Инициализирую всё нулями (~100 мс)
├─ Возвращаю управление

Demand Paging (современные ОС):
├─ Программа: "Дай мне 100 MB"
├─ ОС: "Хорошо, выделяю виртуально (мгновенно)"
├─ Возвращаю управление сразу
├─ При первом обращении: page fault → загружаю нужную страницу
├─ Результат: быстрее на 100x
```

**Преимущества:**
- Программа запускается мгновенно (даже если потом использует всю память)
- Экономия памяти (неиспользованные страницы в RAM не попадают)

**Недостатки:**
- Page faults замедляют первые обращения
- Нельзя гарантировать real-time (непредсказуемые задержки)

### MEMORY MAPPING

#### 10. Чем `mmap()` отличается от `read()`/`write()`? Когда `mmap` эффективнее?

| Аспект | read()/write() | mmap() |
|--------|---|---|
| **API** | read(fd, buf, size), write(fd, buf, size) | mmap(addr, size, prot, flags, fd, offset) |
| **Копирование** | Копирует в user buffer (2 копии) | Прямой доступ к файлу (1 копия) |
| **System calls** | Один вызов на каждое чтение | Один вызов на отображение |
| **Page faults** | Меньше (~50) | Больше (~25600 на 100MB) |
| **Для малых файлов** | Быстрее | Медленнее |
| **Для больших файлов** | Медленнее | Быстрее |
| **Случайный доступ** | Плохо (множество read()) | Хорошо (прямой доступ) |
| **Изменение размера** | Просто | Сложно (фиксированный размер) |

**Результаты экспериментов (100 MB файл):**
```
read():                    0.25 сек, ~50 minor faults
mmap():                    0.20 сек, ~25600 minor faults
mmap() + MADV_SEQUENTIAL:  0.15 сек, ~15000 minor faults
```

**Когда `mmap()` эффективнее:**
1. **Большие файлы** (>10 MB)
2. **Случайный доступ** (нужно читать разные части)
3. **Долгоживущие процессы** (overhead окупается)
4. **Real-time требования** (контролируем page faults)

**Когда `read()` эффективнее:**
1. **Маленькие файлы** (<1 MB)
2. **Одноразовое чтение** (весь файл за раз)
3. **Последовательный доступ** (оптимально буферизировать)
4. **Простота кода** (API проще)

#### 11. Что такое MAP_PRIVATE и MAP_SHARED? В чём разница?

| Флаг | Видят ли другие процессы | Изменения в файле | Использование |
|------|------|------|------|
| **MAP_PRIVATE** | Нет (приватная копия для процесса) | Нет (write не переходит в файл) | Обычные программы |
| **MAP_SHARED** | Да (один view на всех) | Да (write изменяет файл) | IPC, БД, разделяемые данные |

**MAP_PRIVATE:**
```c
// Каждый процесс видит свою копию
void *data = mmap(fd, size, PROT_READ | PROT_WRITE,
                   MAP_PRIVATE, fd, 0);

data[0] = 'X';  // Меняю ЭТУ копию
// Файл НЕ изменяется
// Другие процессы НЕ видят

// Copy-on-Write: первая запись создаёт копию страницы
```

**MAP_SHARED:**
```c
// Все процессы видят одну копию в памяти
void *data = mmap(fd, size, PROT_READ | PROT_WRITE,
                   MAP_SHARED, fd, 0);

data[0] = 'X';  // Меняю ОБЩУЮ копию
// Файл ИЗМЕНЯЕТСЯ
// Другие процессы ВИДЯТ это сразу (если у них то же отображение)
```

**Пример — база данных:**
```c
// Несколько процессов работают с БД одновременно

// Процесс 1:
int *db = mmap(fd, size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
db[0] = 1000;  // Изменяю счётчик

// Процесс 2 (параллельно):
int *db = mmap(fd, size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
printf("%d\n", db[0]);  // Видит 1000 (изменение процесса 1)
```

#### 12. Что произойдёт, если обратиться к памяти за пределами отображённого файла?

**За пределами mmap() памяти → segmentation fault!**

```c
void *data = mmap(NULL, 1000, PROT_READ | PROT_WRITE,
                   MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
// Отображено 1000 байт

char *arr = (char *)data;
arr[500] = 'A';   // OK (в пределах)
arr[1000] = 'X';  // SEGFAULT! (за границей)

// ОС генерирует SIGSEGV сигнал
// Программа падает (если не обработан сигнал)
```

**Почему:**
- Page table содержит информацию о размере отображения
- При обращении к адресу вне границ → page fault не может быть обработан
- Ядро отправляет SIGSEGV процессу

**Пример с файлом:**
```c
int fd = open("file.txt", O_RDONLY);  // 100 байт
void *data = mmap(NULL, 1000, PROT_READ, MAP_PRIVATE, fd, 0);
// Пытаемся отобразить 1000 байт, но файл только 100

// Linux: отображает всю страницу (обычно 4 KB)
// Остальное инициализируется нулями
data[900] = ...;  // OK (нули за концом файла)
data[4096] = 'A';  // SEGFAULT (за страницей)
```

**Защита:**
```c
// Правильно: сначала stat
struct stat sb;
stat("file.txt", &sb);
void *data = mmap(NULL, sb.st_size, PROT_READ, MAP_PRIVATE, fd, 0);
// Теперь size точный

// Или использовать размер кратный странице
size_t page_size = sysconf(_SC_PAGE_SIZE);
mmap(..., ((sb.st_size + page_size - 1) / page_size) * page_size, ...);
```

#### 13. Как работает page cache и зачем он нужен?

**Page Cache** — кэш дисковых блоков в памяти ядра

```
Файл на диске: [Block0][Block1][Block2]...
                  ↓
           [Page Cache в RAM]
                  ↓
           Процесс читает
```

**Как это работает:**
```c
read(fd, buf, 4096);
↓
Ядро: "Нужен блок #5 с диска"
↓
Проверяет page cache:
├─ Есть? → копирует в buf из cache (быстро, RAM)
└─ Нет? → читает с диска в cache, потом копирует в buf

read(fd, buf, 4096);  // Второе чтение того же блока
↓
Ядро: "Блок #5 уже в cache!"
↓
Копирует сразу из cache
↓
Никакого обращения к диску!
```

**Зачем нужен:**
1. **Скорость:** RAM в 100000x раз быстрее диска
2. **Прозрачность:** программист пишет обычный код, ОС кэширует автоматически
3. **Эффективность:** часто читаемые файлы всегда в памяти

**С mmap():**
```c
// Page cache работает аналогично
void *data = mmap(fd, size, PROT_READ, MAP_PRIVATE, fd, 0);

data[0];  // Первый доступ
↓
Page fault → ядро ищет в page cache
├─ Есть? → подключает физическую страницу
└─ Нет? → читает с диска в page cache, подключает

data[1];  // Второй доступ (если на одной странице)
↓
Нет page fault! (страница уже в памяти)
```

**Управление page cache:**
```bash
# Посмотреть, сколько памяти в cache
free -h
# Cached строка показывает page cache

# Очистить page cache (требуется root)
sudo sh -c 'echo 3 > /proc/sys/vm/drop_caches'
# После этого первое чтение файла медленное (с диска)

# Это используется в наших экспериментах для честного бенчмарка
```

#### 14. Зачем нужна буферизация? Какие уровни буферизации существуют?

**Буферизация** — накопление данных перед операцией для оптимизации

**Зачем:**
- System calls дорогие (переход в kernel mode)
- Диск медленный (лучше 100x по 1MB, чем 1000x по 100 байт)
- Сетевые операции очень дорогие
**Уровни буферизации в Linux:**

1. **Уровень приложения** — буферы в программе
   ```c
   char buf[4096];
   for (...) {
       read(fd, buf, 4096);  // Читаю по 4 KB
   }
   ```

2. **Уровень libc** — stdio буферы
   ```c
   FILE *f = fopen(...);  // Буфер по умолчанию 4 KB
   fwrite(&data, ..., f);
   fflush(f);  // Сбросить буфер на диск
   ```

3. **Уровень ядра** — page cache
   ```
   write() → page cache (быстро)
   → кэш со временем пишется на диск (асинхронно)
   ```

4. **Уровень диска** — внутренний буфер диска
   ```
   Диск может переупорядочить операции для оптимизации
   ```

**Практический пример из бенчмарка:**
```bash
# Способ 1: write() без буфера
./io_benchmark method=1 size=100MB
// 100MB / 64KB = 1562 write() вызовов
// Время: 0.5 сек

# Способ 2: fwrite() с буфером (4 KB)
./io_benchmark method=2 size=100MB
// fwrite() буферизирует, потом один write() ~4KB
// Время: 0.3 сек (быстрее)

# Способ 3: mmap()
./io_benchmark method=3 size=100MB
// Никаких буферов, прямой доступ
// Время: 0.1 сек (самый быстрый)
```

#### 15. Почему маленький размер буфера замедляет I/O?

**Слишком много system calls!**

```
write(buf, 100 байт):
├─ Save CPU state
├─ Switch to kernel mode
├─ Find file in kernel
├─ Write to disk
├─ Switch back to user mode
├─ Restore CPU state
└─ Возвращаемся (overhead ~10000 циклов CPU)

Итого: для 100 байт нужно ~10000 циклов накладных расходов!
```

**Оптимальный размер буфера:**
- Маленький (< 4 KB): много system calls
- Средний (4-64 KB): оптимально
- Большой (> 1 MB): может быть медленнее (cache miss)
- Мегабольший (> 100 MB): точно медленнее

**На практике: 64 KB оптимум для большинства случаев**

#### 16. Что такое O_DIRECT и O_SYNC? Когда их использовать?

**O_DIRECT** — обойти page cache

```c
int fd = open("file.txt", O_WRONLY | O_DIRECT);
write(fd, buf, 4096);

// БЕЗ O_DIRECT:
write() → page cache (быстро, возвращаемся) → потом на диск

// С O_DIRECT:
write() → ПРЯМО на диск (медленно, но точно на диске)
```

**O_SYNC** — ждать записи на диск

```c
int fd = open("file.txt", O_WRONLY | O_SYNC);
write(fd, buf, 4096);  // Ждём, пока запишется на диск

// БЕЗ O_SYNC:
write() → page cache → возвращаемся (асинхронно)

// С O_SYNC:
write() → page cache → диск → возвращаемся (синхронно)
```

**Использование:**

O_DIRECT нужен когда:
- БД с собственным кэшом (не нужен page cache)
- Real-time системы (нужен контроль над временем)
- Очень большие файлы (page cache даже мешает)

O_SYNC нужен когда:
- Критична надёжность (логи, БД)
- Нужна гарантия записи на диск

#### 17. Чем отличается `fwrite()` от `write()`?

| Параметр | fwrite() | write() |
|----------|----------|---------|
| **Уровень** | libc (user space) | System call (kernel) |
| **Буферизация** | Есть (внутри FILE структуры) | Нет (идёт прямо в kernel) |
| **Скорость** | Быстро (буфер в памяти) | Медленнее (system call overhead) |
| **Надёжность** | Нужен fflush() перед fsync() | write() гарантирует системный буфер |
| **Обработка ошибок** | Возвращает кол-во элементов | Возвращает кол-во байт |
| **Переносимость** | POSIX стандарт | POSIX стандарт |

**На практике из бенчмарков:**
```bash
# read() - 0.25 сек
# fread() - 0.20 сек (буферизация помогает)
# mmap() - 0.15 сек (без копирования)
```
